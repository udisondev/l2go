# r0 — Архитектура игрового сервера L2 Interlude (онлайн 10k+)

Заметки по дизайну. Цель: эмулятор L2 Interlude (C5) на Go, онлайн 10k+, **один процесс / одна
коробка** (распределёнка сознательно отвергнута). Фокус — архитектура мира, а не язык.

## TL;DR

- Язык — ~15% задачи. Потолок Mobius (~3–5k) определяют **архитектура** и объём
  реверс-инжиниринг-знания, а не «Java медленная».
- 10k на одной коробке — это задача **single-process актор-меша**, а не распределёнки. Весь
  distributed-кошмар (сериализация, partial failure, консенсус, ребалансировка) отпадает.
- Главная развилка дизайна: **общий мир + мьютексы (путь в стену)** vs **актор-меш**. Целевой
  гибрид — **single-writer + двойная буферизация снапшотов**.
- «Синхронизация мира» сводится к одной механике: публикация иммутабельного снапшота + атомарный
  свап указателя на тик.
- Изоляция осады живёт в **модели тика** (общий барьер vs независимые тики), а не в шардинге.

---

## Почему не «просто другой язык»

Куда реально уходит CPU/латенси в L2-сервере (и кто из этого лечится языком):

1. **Квадратичный бродкаст (knownlist, «проблема города»)** — O(n²) пакетов при толпе в точке.
   Алгоритмическая стена, язык не лечит.
2. **GC-паузы под нагрузкой** — рвут тик. (Go GC суб-мс, но давление при млн сущностей остаётся.)
3. **Lock contention** в модели мира — лечится архитектурой (см. ниже).
4. **AI-тики тысяч мобов**, геодата/пасфайндинг, спатиальные запросы.
5. **Запись в БД** — амплификация апдейтов; лечится батчингом, не языком.
6. Сериализация пакетов + Blowfish/XOR крипта.

Mobius упирается в потолок из-за 2 + 3 + одно-поточных хот-путей, а не из-за «медленной Java».

---

## Переформулировка проблемы для single-process

«Осада не должна влиять на мир» в одном процессе — это **не шардинг**, а **уничтожение всех точек
глобальной синхронизации**. Go-шедулер сам даёт изоляцию нагрузки: горячий регион, жрущий 2 ядра,
не тормозит пустой регион на другом ядре — *если пустой его нигде не ждёт*. Враги на охоту:

- глобальный тик-барьер (один `world.Tick()`, ждущий все регионы);
- общие мьютексы на структурах мира;
- единый канал/воркер, через который всё проходит воронкой;
- глобальные локи: RNG, мапа сущностей, спатиальный индекс.

Убрать их → «осада не трогает мир» получается почти бесплатно.

## Три слоя, которые нельзя склеивать

Главная концептуальная ошибка — приравнять «кого симулирую» = «кого вижу» = «что пространственно».

1. **Simulation shards (authority by location).** Грид регионов (фикс-сетка). Каждый регион —
   *актор*: мейлбокс + один обработчик → внутри региона **локов нет**, всё последовательно. Регион
   — единственный авторитет над сущностями, физически в нём находящимися.

2. **Interest management / replication (AoI).** Что видит клиент — это **не** его регион, а
   объединение регионов в радиусе обзора (knownlist 3×3). Слой подписки поверх симуляции,
   **пересекает границы шардов**. Игрок у границы симулируется в A, но подписан на A+B+C.

3. **Non-spatial services.** Чат, клан, пати, маркет, олимп, аукцион — **не в гриде**. Сервисы,
   шардированные по entity-id, а не по координате. Пати на три региона живёт здесь.

Осада по этой логике → выделенный шард со своим бюджетом тика, либо инстанс (как олимп).

## Ключевой инвариант

**Ровно один авторитет на сущность в каждый момент.** Все мутации идут через владельца
последовательно → гонок нет by construction. Кросс-сущностные действия — **сообщения владельцу**, не
прямой доступ к чужой памяти. Это актор-модель.

Следствие по консистентности: **глобальной консистентности нет и не нужно** — есть per-owner
сериализация + eventual consistency между владельцами. Устаревание позиции соседа на тик — норма для
MMO (и так сетевой лаг).

Где eventual НЕ годится: **обмен предметами/деньгами, передача владения** → мини-2PC
(reserve → commit/abort) между владельцами, иначе **дюп**. Всё остальное (урон, аггро, бродкаст) —
fire-and-forget.

## Кросс-региональное взаимодействие — инструментарий

«Синхронизация мира» распадается на 4 механики:

- **Ghost / border-реплики.** Сущности у границы реплицируются read-only в соседние регионы. Сосед
  резолвит «кто рядом» включая заграничных без синхронного запроса. Авторитет пушит апдейты.
- **Action-to-owner.** Атака/скилл через границу: A шлёт `ApplyDamage` в мейлбокс B, B применяет в
  своём порядке. AoE на границе → расщепить spatial-запрос и разослать N сообщений владельцам.
- **Handoff при пересечении границы.** Самое опасное место. Атомарно: source замораживает →
  (в одном процессе) передаёт структуру в горутину target → target становится авторитетом → source
  форвардит запоздавшие сообщения и удаляет у себя. Хазарды: хэндофф посреди каста, посреди трейда,
  во время боя (атакующий в A, цель ушла в B). **Двойного владельца нельзя ни на тик** (= дюпы).
- **Логические часы.** Независимые тики шардов → кросс-шард события упорядочивать по
  timestamp/логическому счётчику. Внутри взаимодействия авторитетен порядок владельца цели.

В single-process хэндофф — это передача структуры между горутинами, а не сетевой протокол.

## Динамическая нагрузка (загруженные vs пустые регионы)

- **Пустые регионы стоят ноль.** Нет игроков и активных мобов → регион *спит*, тика нет, просыпается
  по входу. Тысячи регионов почти даром.
- **Горячим — изоляцию, а не справедливость.** Осаде — отдельный пул воркеров / бюджет ядер, чтобы
  не делила планировщик с обычным миром. Вопрос «не затормозит ли всех» снимается топологией.

---

## Главная развилка в одном процессе: shared-lock vs actor

В одном процессе ты *физически можешь* дёрнуть указатель на чужую сущность — это путь обратно в ад
локов и гонок Mobius. Две принципиально разные модели:

- **A. Общий мир + мьютексы.** Один спатиальный индекс, общие структуры, лок регионов/сущностей.
  Кросс-регион тривиален, но — ад порядка локов и контеншн под осадой. Путь в стену.
- **B. Актор-меш.** Регион = горутина + канал, общего мутабельного состояния нет, кросс-регион =
  сообщения. Локов нет, изоляция бесплатна. Цена — плумбинг кросс-региональных чтений.

### Целевой гибрид: single-writer + двойная буферизация снапшотов

Классический паттерн игровых серверов, идеально ложится на Go:

- Регион — **единственный писатель** своих сущностей, мутирует только в своей горутине. Локов на
  запись нет by construction.
- В конце тика регион **публикует иммутабельный снапшот** публичного состояния (позиции, hp, флаги
  видимости) через `atomic.Pointer.Store` (свап указателя).
- Соседи, собирая knownlist через границу, читают снапшоты **lock-free** через `atomic.Pointer.Load`.
  Снапшот иммутабелен → гонок нет, хотя память общая.
- Мутации через границу (урон, аггро) — по-прежнему сообщения в мейлбокс владельца.

**Вся «синхронизация мира» = публикация снапшота + атомарный свап указателя на тик.**
Кросс-региональная видимость дешёвая и lock-free, ценой устаревания на один тик.

## Где живёт изоляция осады — модель тика

- **Глобальный тик-луп** (воркер-пул по активным регионам, барьер на кадр). Проще, снапшоты
  консистентны (все на тике N). Но осада, не уложившаяся в бюджет кадра, **держит барьер всем** — тут
  изоляция протекает.
- **Независимые тики на регион.** Идеальная изоляция (осада тормозит только себя), но снапшоты
  соседей разъезжаются по времени и сложнее рассуждать о порядке.

**Прагматичный компромисс:** основной мир на общем тик-лупе с воркер-пулом (консистентно и просто),
**осаду/инстансы выносить с него** — отдельный тик, отдельный бюджет, не участвуют в общем барьере.
Пустые регионы в луп не попадают (спят).

## Стоимость акторов и сон регионов

Тысячи регионов = тысячи горутин — **не проблема**. Это не та ось, где стоимость.

- **Запаркованная горутина (заблокирована на `<-mailbox`) не шедулится** — стоит только стек ~2–4 КБ.
  Go держит сотни тысяч / млн спящих горутин (по горутине на коннект — его хлеб). Тысячи спящих
  регионов = единицы МБ и **ноль CPU**.
- Дорого не существование горутины, а **работа на тик**. Цель дизайна: «большинство регионов не
  делают per-tick работу».
- **«Спать» = выпасть из тик-сета, а не умереть.** Регион живёт, но `select` на двух каналах:

```go
for {
    select {
    case msg := <-r.mailbox:   // вход игрока, урон через границу, ...
        r.handle(msg)          // может перевести регион в active → подписать на тики
    case <-r.tick:             // приходит ТОЛЬКО активным регионам
        r.step()
        if r.idle() { sched.deactivate(r) } // отписался → дальше только мейлбокс
    }
}
```

- Тик-планировщик шлёт сигнал **только активным**. Пустой не получает тиков → не просыпается →
  бесплатен. Активен регион, если: есть игроки, ИЛИ активные мобы (агро/движение/респ-таймер), ИЛИ
  отложенные события. Стоящий заполненный спавн без игроков — квиесцируется на wake-таймер.
- Числа для L2: достижимых ячеек — низкие тысячи; при 10k игроки **кластеризуются** (города, споты,
  осады). Активных в моменте — сотни, не тысячи. Итого ~сотни runnable + пара тысяч запаркованных.
- **Goroutine-per-region** — целевой выбор: из него **бесплатно выпадает single-writer**. Воркер-пул
  даёт контроль CPU-бюджета, но теряет халявный single-writer (следить, чтобы регион не обрабатывали
  два воркера).
- Нюанс — **память спящего региона**: не преаллоцировать в пустом регионе жирный спатиальный индекс и
  слайсы; состояние минимально и лениво аллоцируется при активации.

## Бой между регионами

**Не edge-case, а горячий путь:** кайт/чейз в PvP постоянно пересекает границу. Должен быть дёшев и
корректен by design. A в RA, B в RB, дерутся через границу.

### Базовый поток удара

1. **Видимость/таргет.** A видит B через снапшот RB (lock-free, устаревание на тик). Range-чек идёт
   против снапшота — при скорости атаки в сотни мс и лаге 50–150 мс тик незаметен.
2. **Удар = сообщение владельцу цели (action-to-owner).** Автоатака A резолвится в тике RA, но **RA
   не трогает HP B** — шлёт `ApplyDamage` в мейлбокс RB. HP B мутирует только RB (single-writer).
3. **Урон считается раздельно** (формуле нужны и оффенс атакующего, и дефенс цели — они в разных
   регионах): оффенсивная часть (patk, крит-ролл, мощность скилла) — со стороны RA, едет в сообщении;
   финал + применение (pdef, щит, баффы B) — на стороне RB. Каждый регион авторитетен над статами
   своей сущности.

```
RA.tick:   swing := A.computeOffense(targetID=B)
           send(RB.mailbox, ApplyDamage{from:A, to:B, swing})
RB.tick:   if B.validTarget(from, swing.pos) {        // re-валидация!
               dmg := B.finalize(swing)                // дефенс B
               B.hp -= dmg; B.broadcastHP()
               if B.dead() { send(RA.mailbox, KillCredit{killer:A, victim:B}) }
           }
```

### Валидация на применении (анти-эксплойт + лечит стейл-снапшот)

A бьёт по снапшоту на тик старше — B мог выйти из радиуса. **Оптимистично у отправителя, авторитетно
у владельца:** RB при применении перепроверяет по своей актуальной позиции B (в радиусе, жив, не
телепортнулся). Не прошло — урон дропается. Закрывает и рассинхрон, и эксплойты по стейл-позиции.

### Двунаправленность и консистентность

Обратное — тоже сообщения владельцу: kill credit (счётчик PvP A → пишет RA), флаг/карма B → пишет RB.
Для боя **eventual достаточно** (урон аддитивен, латенси в тик ничтожна против скорости атаки).
**Транзакции не нужны** — 2PC только для передачи ресурсов (трейд), не для дамага.

### Тонкое место — хэндофф во время боя

B под атакой убегает RB→RC; владение переезжает посреди боя, нельзя ни потерять, ни задвоить
`ApplyDamage`:

1. **Адресация по стабильному id**, не по указателю на регион.
2. **Директория `id → owner`** (sharded map / `sync.Map`, в одном процессе — in-memory лукап).
   Мутируется только на хэндоффе (редко), читается на отправку — read-mostly, не лок на хот-пути.
3. **Атомарный хэндофф без щелей:**
   ```
   RB: пометить B = migrating       // входящие к B в этом окне — буферить, не применять
   RB: сериализовать B → send RC
   RC: установить B, стать активным, ack
   directory: flip B: RB → RC        // последний шаг
   RB: grace-период forwarding       // ApplyDamage к B пересылать в RC
   RB: forget B
   ```
   `migrating` → не задвоить; grace-forwarding → не потерять сообщения от отправителей, прочитавших
   директорию за миг до флипа.

### Дрожание на границе — две защиты

- **Гистерезис / deadzone:** B остаётся за текущим регионом, пока не зайдёт в соседа с запасом —
  граница владения «липкая». Иначе джиттер по линии = хэндофф каждый тик (шторм).
- **Ghosting развязывает видимость и владение:** B у границы реплицирован read-only в соседа →
  виден и атакуем с обеих сторон независимо от владельца. Дрожание не рвёт видимость, гистерезис
  гасит шторм хэндоффов.

**Правило боя:** видимость — через снапшоты соседа; удар — сообщением владельцу цели; оффенс от
атакующего, дефенс+применение+смерть от цели; валидация на применении; хэндофф — по id через
директорию с migrating + grace-forwarding; граница липкая (гистерезис) + ghosting для видимости.

## Residual-сложность (что осталось решать)

Не «распределёнка», а ровно два вопроса:

1. **Дисциплина single-writer** — не поддаться соблазну дёрнуть чужой указатель на запись.
2. **Модель тика** — где граница между общим барьером и независимыми тиками (= где изолируется
   осада).
