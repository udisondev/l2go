# r4 — Референсы владельца: interlude и la2go

Разбор двух ранних Go-эмуляторов владельца — [github.com/udisondev/interlude](https://github.com/udisondev/interlude)
и [github.com/udisondev/la2go](https://github.com/udisondev/la2go) — на предмет переноса в
la2. Выполнен по запросу владельца (сессия 2026-09-09) как вход к P0.9. Клоны: `_refs/` вне
репозитория (в проект не коммитятся).

## TL;DR

- «Очень хорошая модель владения пакетом данных с минимальными аллокациями» — это **interlude**:
  серверные пакеты — чистые функции-писатели в буфер вызывающего, клиентские — представления над
  буфером коннекта. Замер: полный 40-байтовый пакет — **4.6 нс / 0 аллокаций** (стек) — против
  340 нс на один `WriteInt` у пул-Writer'а la2go. Модель переносится в la2 как конвенция фазы 1
  и как паттерн слэбов энкод-стадии (ADR-0004).
- la2go силён другим: культура производительной работы (bench-CI, профилирование, журнал
  оптимизаций), DB-слой (pgx + goose), e2e/интеграционные тесты, крипта с бенчмарками.
- Мировая архитектура обоих (регионы/видимость/системы) **не переносится** — замещена
  ADR-0002/0003/0004.
- RPC: yamux-стик LS↔GS (interlude) заменяется **gRPC**. Топология владельца: LoginServer —
  всегда один отдельный процесс на все миры, GameServer — процесс на каждый мир; стык
  login↔game — всегда сетевой (gRPC, с фазы 3), как и admin-API/harness. Внутри game-процесса
  RPC нет (один процесс, r0).

## Репозитории в двух словах

| | interlude | la2go |
|---|---|---|
| Протокол | Interlude 746 | Interlude (порт L2J Mobius) |
| Состав | LS + GS, pkg/-слои: packet/bufpool/crypto/opcode/rpc/l2client | LS + GS + gslistener (LS↔GS), internal/-слои |
| Пакеты | **модель владения буфером** (см. ниже) | пул Writer/Reader (sync.Pool + bytes.Buffer) |
| Перф | дисциплина в CLAUDE.md, бенчей в репо нет | bench-CI, profiling-скрипты, OPTIMIZATION_LOG |
| Данные | PostgreSQL (pgx), spawn/skill/npc генераторы, каталог 494 опкодов | PostgreSQL (pgx + goose), миграции |
| Тесты | юнит по пакетам | юнит + integration + e2e |
| Агентность | CLAUDE.md + .claude/skills (проект писался агентами) | обычная разработка |

Оба без LICENSE-файла; авторство — владелец la2; перенос разрешён (фиксация — эта запись,
сессия 2026-09-09). Переносимый код входит в GPLv3-проект; значимые порты помечаются
источником (`// ported from udisondev/interlude` / `la2go`), по тем же правилам, что и
GPL-референсы ADR-0001. la2go — порт Mobius (GPL): его перенос подчиняется ADR-0001 в полной
мере.

## Модель владения пакетом (interlude) — разбор

Конвенция (зафиксирована в CLAUDE.md проекта):

- **Серверный пакет** — `func Name(buf []byte, args ...) int`: пишет в буфер вызывающего,
  возвращает число записанных байт. Нет структуры, нет интерфейса, нет Get/Put на уровне
  пакета — владение буфером остаётся у вызывающего.
- **Клиентский пакет** — `type Name []byte` + геттеры (`readD/readH` по офсетам): нулевая копия,
  представление над буфером коннекта; валидация длины на диспетчере (`ValidPayload`).
- **Буферы:** малые пакеты — стековый массив (`var buf [29]byte`, escape-анализ держит его на
  стеке); крупные — `bufpool.BytePool`: бакеты 128/256/512/1024/2048/4096 (по распределению
  размеров L2-пакетов), пер-bucket sync.Pool, статистика Get/Put/overflow; всё >4096 — прямая
  аллокация.
- **Отправка:** `SendEncrypted()` копирует в коннект — вызывающий может переиспользовать буфер
  сразу; дисциплина `pool.Put()` обязательна на горячих путях.

Замеры (эта машина, Go 1.27.1, AMD Ryzen 9 8945HS; бенч interlude добавлен в клон локально):

```
interlude  Attack (40 B, полный пакет):  стек   4.6 нс / 0 B / 0 allocs
                                    пул  29.5 нс / 24 B / 1 alloc  (холодный пул; steady ~0)
la2go      Writer.WriteInt (4 байта!):   340 нс / 0 B / 0 allocs
           Writer.WriteByte:              176 нс
           Writer.MixedPacket:              8.1 нс / 0 allocs
           Reader zero-copy read:          4.9 нс / 0 allocs
```

Почему модель interlude лучше для нас: владение буфером у вызывающего = конвейер ADR-0004
(compose-стадия собирает кадры в пер-клиентские слэбы, энкод — стейтлес-стадия) ложится на неё
без швов: пакет-писатель пишет прямо в слэб кадра; для broadcast-пакетов побайтово одинаковых
всем наблюдателям — естественная точка encode-once (эволюция фазы 6 из ADR-0004). Методный
Writer (la2go) требует pool-дисциплины на каждый пакет и мешает стек-аллокации малых.

Оговорка: числа la2go взяты его же бенчмарками (методика может завышать), но порядок разницы
устойчив: модель interlude — быстрее на порядок и аллокационно чище на малых пакетах (а их ~65%
по каталогу).

## Что переносим

**Из interlude (фаза 1 — протокол, и P0.9 — конвенция слэбов):**

1. Модель владения пакетом: writer-функции + views + BytePool. Пакет `pkg/bufpool` — кандидат
   на перенос почти как есть (GPLv3, атрибуция).
2. `docs/opcodes.md` — каталог **494 опкодов** протокола 746 с готовностью (✅/⬜) — стартовая
   таблица опкодов для фазы 1 (сверить по Mobius/aCis перед фиксацией каждого).
3. `pkg/l2client` (login/game/packet) — задел headless-клиента: наш главный актив фазы 1.
4. `cmd/pcap-analyzer` — инструмент разбора дампов живого трафика: источник golden-фикстур.
5. Крипта (`pkg/crypto`) и helpers (writeD/H/Q/F/UTF16, readD/H) — кандидаты на порт с
   golden-тестами.
6. CLAUDE.md-культура (конвенции пакетов как правила для агентов) — у нас уже есть AGENTS.md;
   из их правил возьмём формулировки про «всегда Put обратно» и «SendEncrypted копирует».

**Из la2go (фазы 1–5 по мере наступления):**

1. Performance-инфраструктура: `.github/workflows/benchmarks.yml`, `scripts/bench.sh`,
   `profile.sh`, `docs/performance/*` (гайды + OPTIMIZATION_LOG с форматом записи
   «проблема→диагностика→решение→результат»). Активируем по фазам (ворота фазы 4/6 в ci.yml
   уже помечены заглушками).
2. Крипта с бенчмарками (Blowfish ~864 нс/шифр на их машине) — сверка наших реализаций.
3. DB-слой: pgx + goose-миграции — паттерн для персиста фазы 5 (у нас write-behind + WAL поверх
   БД — слой la2go пригодится формой, не моделью).
4. e2e/integration-тесты (`tests/e2e`, `testutil`) — паттерны для walking skeleton фазы 3.

## Что НЕ переносим

- **Мировая архитектура обоих**: регионы/visibility/systems la2go (`internal/world`,
  gslistener) и interlude (`internal/game`: dispatcher, loop_*, region) — замещены моделью
  ADR-0002 (метроном) / ADR-0003 (ящики/чемоданы) / ADR-0004 (AoI). Разбор их решений —
  полезен как «до/после», код — нет.
- **yamux RPC LS↔GS** (interlude `pkg/rpc` + la2go gslistener): транспорт (yamux + net/rpc +
  самописное рукопожатие) не переносится. Топология владельца (2026-09-09): LoginServer —
  всегда один отдельный процесс на все миры; GameServer — отдельный процесс на каждый мир
  («game server» в L2 = отдельный мир); стык login↔game — всегда сетевой, с фазы 3 —
  **gRPC** (RegisterSession/Kick/онлайн — семантика из pkg/rpc переносится как спецификация
  стыка). Внутри game-процесса — один процесс (r0): RPC внутри мира отсутствует по
  построению. Инвариант: gRPC живёт в пограничных компонентах (loginlink/admin/harness),
  пакеты мира его не импортируют.
- DB-центричная модель персонажа (сохранение синхронно в PostgreSQL) — противоречит
  write-behind/WAL из ADR-0003 §8.

## Следствия для P0.9 (карта компонентов)

- Энкод-стадия исходящего (ADR-0004) и gateway/net фиксируют модель interlude: кадр = слэб
  вызывающего, пакеты-писатели `func(buf []byte, ...) int`, малые — стек, крупные — BytePool.
- Компонент loginlink (клиент стыка login↔game в game-процессе) + admin (+ harness-управление)
  — gRPC API; в карте зависимостей — листы, вверх не импортируются, из мира не импортируются
  (только через шины сообщений/шлюз). Login — отдельный процесс: один на все game-процессы.
- Каталог опкодов и l2client/pcap-analyzer — входы фазы 1, в P0.9 только упоминаются как
  границы protocol-компонента.
