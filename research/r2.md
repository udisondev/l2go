# r2 — Дорожная карта: от ресерча к надёжной реализации на Go

План пути от [r0.md](r0.md) (архитектура мира) и [r1.md](r1.md) (geodata/движение) к работающему
эмулятору L2 Interlude. Построен под **агентскую разработку**: цель — чтобы на выходе был
качественный код, а не правдоподобный.

## TL;DR

- r0/r1 закрывают ~15% риска (архитектуру мира — и закрывают хорошо). Реальные риски проекта
  по смертельности: **(1) объём реверс-инжиниринг-знания** (тысячи формул/скиллов/AI-правил — об
  это умирают проекты), **(2) корректность протокола** (клиент не прощает кривых пакетов, всё выше
  проводов бесполезно), **(3) агентский дрейф** (агент отлично пишет по проверяемой спецификации
  и уверенно галлюцинирует игровые механики по непроверяемой).
- Главный принцип порядка работ: **если это не проверяется машиной — считай, агент этого не
  делал.** Каждая фаза превращает порцию проблемы в механически проверяемый контракт и производит
  **актив проверки**, который потребляет следующая фаза.
- Порядок — от наиболее проверяемого к наименее: чистые функции (протокол, данные) → интеграция
  (walking skeleton) → конкурентность (бой, ядро r0) → консистентность (экономика) → полнота
  (контент) → производительность (последней и только по измерениям ботов).

## Карта фаз

| Фаза | Артефакт на выходе | Закрываемый риск |
|---|---|---|
| 0. Инфраструктура доверия | CI + ADR + AGENTS.md | агентский дрейф |
| 1. Протокол + headless-клиент | кодек пакетов, golden-тесты | корректность проводов |
| 2. Датапак + geodata | типизированные данные, отчёты валидации | контент как данные |
| 3. Walking skeleton | реальный клиент бегает по миру | интеграционный риск |
| 4. Бой + ядро r0 | боты в CI, кросс-региональный бой | архитектура встречает реальность |
| 5. Предметы/трейд | 2PC, WAL, анти-дюп тесты | консистентность экономики |
| 6. Контент и масштаб | скиллы, AI, осады, 10k ботов | полнота и производительность |

## Фаза 0 — Инфраструктура доверия

**Что:** Go-модуль; CI-конвейер (build, vet, staticcheck, `go test -race`, fuzz-корпус, бюджеты
бенчмарков); каталог ADR (Architecture Decision Records); AGENTS.md с инвариантами. Каждый
нерешённый вопрос из ревью r0/r1 (см. раздел ниже) становится ADR с решением и его ценой. В
AGENTS.md — непреложные инварианты из r0: мутации сущности только в горутине региона-владельца;
кросс-регион — только сообщения; никаких мьютексов внутри региона; структура пакетов; требования
к тестам; как гонять CI локально.

**Зачем:** самая дешёвая точка для установки качества — навешивать CI на 100k строк потом —
смерть. Для агентов ADR — долгосрочная память: каждая сессия начинается с чтения решений, а не с
реверса кода и угадываний.

**Фундамент:** всё дальнейшее ревьюится против инвариантов автоматически.

**ADR-0001 (обязательно до первой строчки кода) — лицензионная позиция.** Код L2J/aCis — GPL;
датапак и geodata — производные проприетарных файлов NCsoft. Порттировать семантику наблюдением —
одна серая зона, копировать код — другая. Решение зафиксировать письменно.

## Фаза 1 — Протокол и headless-клиент (оракул-харнесс)

**Что:** Blowfish/XOR-крипта, хендшейк, кодек пакетов Interlude, таблица опкодов, флоу логина.
Плюс **headless-клиент на Go** — тестовый харнесс: подключаться, логиниться, входить в мир,
декодировать трафик в читаемый лог. Golden-тесты кодирования/декодирования против байтовых
дампов; fuzz на раундтрип.

**Зачем:** корректность проводов бинарна — либо пакет верен, либо клиент молча отваливается.
Референсы фактуры: [ruk33 — эмулятор на C, детали протокола](https://ruk33.github.io/creating-a-server-emulator-in-c-for-lineage-2),
исходники [Mobius](https://github.com/MobiusDev/L2J_Mobius) (ветка Interlude) и aCis.

**Фундамент:** headless-клиент — главный актив проекта: из него вырастут боты (фаза 4),
дифференциальные тесты против L2J и вся регрессионная защита. Сам протольный слой — чистые
функции без состояния: свойство «закодировал→раскодировал→получил то же» проверяется механически —
идеальная почва для агентов.

## Фаза 2 — Статические данные: датапак и geodata

**Что:** парсеры датапака L2J (предметы, скиллы, NPC, спавны, зоны) в типизированные Go-структуры
с **отчётами валидации** (каждый дроп ссылается на существующий предмет, каждый спавн — на
существующего NPC; разрыв = ошибка сборки данных). Парсер geodata → mmap-представление из r1,
юнит-тесты против поведения референсного парсера.

**Зачем:** контент — это данные, а не код; «тысячи скиллов» превращаются в таблицы. Отчёты
валидации мгновенно ловят агентские ошибки, которые компилятор не видит.

**Фундамент:** по r1 статика иммутабельна → глобально шарится без локов. Огромная поверхность
безопасной агентской работы: датасет фиксирован, ошибки воспроизводимы, ничего не течёт и не
гонится.

## Фаза 3 — Walking skeleton: войти и пробежаться

**Что:** минимальный игровой сервер: авторизация → выбор персонажа → вход в мир → спавн →
движение с geo-валидацией из r1 → видимость второго клиента (простейший knownlist) → чат → логаут
с персистом. Один регион-актор, без боя. Каркас конкурентности из r0 (горутина региона, мейлбокс,
тик) ставится здесь — в минимальной экспозиции. Это паттерн «walking skeleton» (Alistair
Cockburn): крошечная end-to-end реализация, через которую проходит одна функция.

**Зачем:** момент, когда «сервер работает» впервые доказуемо — **реальным клиентом Interlude**.
Весь интеграционный риск (протокол ↔ данные ↔ мир ↔ персист) снимается на минимальном объёме
кода, а не на максимуме.

**Фундамент:** дальше каждая фича — «расширить скелет»; у агентов всегда есть запускаемая система.
Лечит классическую агентскую смерть: строить этаж на непроверенном подвале.

## Фаза 4 — Бой и горячий путь r0

**Что:** статы и формулы (портирование из L2J — с **дифференциальными тестами**: те же входы →
те же числа урона, что у L2J-оракула); автоатака; смерть/XP/лут; затем кросс-региональный бой
(action-to-owner, валидация на применении — r0), хэндофф с гистерезисом и директорией, снапшоты.
Плюс **рой ботов**: харнесс-клиенты, сценарии — бегать и драться; нагрузочный смоук в CI с
утверждением бюджета тика и памяти; race detector; pprof.

**Зачем:** здесь архитектура r0 встречает реальность. Дифф-тесты превращают самый
агентско-опасный труд («портируй формулу») в агентско-дружелюбный («сходись с оракулом»). Боты в
CI делают регрессии производительности видимыми на каждом коммите.

**Фундамент:** жизненный цикл сущностей, боевой цикл, ядро региона — ствол, на который вешается
весь контент. Обязан закалиться до того, как на него навалят тонну фич.

## Фаза 5 — Острова консистентности: предметы, трейд, персистентность

**Что:** модель владения предметами (граница «item в регионе» vs «item в сервисе» — открытый
вопрос, см. ниже); инвентарь; трейд как мини-2PC из r0; пати/XP; дроп/подбор; персистентность
write-behind + WAL для предметных транзакций. Тесты: инъекция краша (`kill -9` посреди трейда),
переупорядочивание сообщений, хэндофф посреди трейда, property-тесты «дюп невозможен».

**Зачем:** кода мало, ставки максимальные — дюп убивает сервер доверия игроков сильнее любого
бага в бою. Единственная фаза, где спецификации обязаны писаться и ревьюиться человеком, а агент
только реализует к спеке.

**Фундамент:** примитивы передачи ресурсов, на которые садятся склад, почта, аукцион — без
пересмотра основ.

## Фаза 6 — Контент и масштаб

**Что и в каком порядке:** AI мобов (аггро, спавн-движок) → скиллы как table-driven движок
эффектов поверх датапака → инстансы и олимп с собственным бюджетом тика (r0) → осады.
Оптимизация knownlist («проблема города», шаг «б» из r0) решается **здесь, по измерениям ботов**,
а не заранее; flow-field из r1 — только если появится реальный сценарий NPC-орды (в Interlude
толпа на осаде — игроки, которых серверу не пафиндить). Финал — 10k ботов, тюнинг GC снапшотов,
обсервабилность, админ-инструменты.

**Зачем:** к этому моменту контент — конвейер: паттерны установлены, каждый новый скилл — данные
плюс маленький код эффекта; агенты тиражируют их с высокой надёжностью. Производительность —
последней: запас даёт архитектура (r0), а оптимизировать без измерений ботов — враньё себе.

## Агентская система качества (сквозная, не фаза)

1. **Spec-first.** Задача агенту = спецификация с фальсифицируемыми критериями приёмки + тесты до
   кода. Практики: [how to write a good spec (Addy Osmani)](https://addyosmani.com/blog/good-spec/),
   [GitHub spec-kit](https://github.blog/ai-and-ml/generative-ai/spec-driven-development-with-ai-get-started-with-a-new-open-source-toolkit/),
   [разбор SDD-инструментов (Martin Fowler)](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html).
2. **ADR-дисциплина.** Решение не зафиксировано — его не существует. Агент обязан уложиться в
   ADR; PR без ссылки на релевантный ADR не мержится.
3. **AGENTS.md с инвариантами:** single-writer, сообщения через границы, обработка ошибок,
   структура пакетов, требования к тестам, локальный запуск CI.
4. **CI-ворота:** race, vet, staticcheck, fuzz-смоук, бюджеты бенчмарков (регресс p99 тика =
   красный билд), нагрузочный смоук с ботами.
5. **Оракул-тестирование против L2J** — противоядие от галлюцинированных игровых семантик,
   главный агентский риск этого домена.
6. **Тонкие вертикальные слайсы**, частые посадки в trunk; сессия агента = один слайс. Второй
   агент-ревьюер против ADR+AGENTS.md перед мержем — дешёвый предфильтр.
7. **Человеческие контрольные точки:** ADR-конформность, фаза 5 целиком, всё про дюпы и
   безопасность.

## Открытые вопросы ревью r0/r1 → кандидаты в ADR (фаза 0)

Блокирующие для следующего захода:

1. **Модель тика** (противоречие в r0: воркер-пул+барьер vs goroutine-per-region): что конкретно
   ломается, если снапшоты соседей разъезжаются на тик? Нужен ли барьер вообще — или только общий
   pacing без ожидания завершения?
2. **Knownlist / проблема города** — убийца №1 по CPU в r0 и единственный TODO без дизайна. Форма
   решения определяет форму снапшотов и всего AoI-слоя.
3. **Per-entity FIFO при хэндоффе** (directory flip + grace-forwarding допускает инверсию
   порядка сообщений; для предметов/трейда — дюп): seq-numbers per entity / drain-before-flip /
   epoch в директории?

Остальные (решить в своих фазах): дублирование ghost-реплик и снапшотов (два механизма для одной
задачи); семантика канала тика под отставанием (cap-1 + drop/generation); GC-давление снапшотов
(per-entity vs per-region блоб; публиковать dirty, а не каждый тик); где живут предметы (регион
vs сервис: аукцион/склад/почта существуют при спящем регионе); владение петом при хэндоффе
хозяина; динамическая геометрия (двери/ворота поверх иммутабельной geodata) + LOS через них;
пороги снап-бэка против ложных срабатываний у легитимных игроков с лагом; сетевой backpressure
(outbound-бюджет на клиента под бродкаст-лавиной); модель персистентности (write-behind, WAL,
допустимый откат по крашу); таймеры/отложенные события (respawn, кулдауны, баффы).

## Почему именно такой порядок

- Каждая фаза производит **актив проверки**, который потребляет следующая: headless-клиент (1) →
  боты (4) → нагрузочные тесты (6); отчёты валидации данных (2) → ловят ошибки контента навсегда;
  дифф-тесты (4) → расширяются на каждый новый движок.
- Порядок — от наиболее проверяемого к наименее: чистые функции → интеграция → конкурентность →
  консистентность → полнота. Агент всегда работает в зоне, где его ошибки ловит машина; человек
  тратит внимание только там, где ставки нельзя делегировать.

## Калибровка трудозатрат (честная)

- Фазы 0–3 — недели…пара месяцев; выход: «можно зайти и побегать».
- Фазы 4–5 — месяцы.
- Фаза 6 — долгий конвейер (у Mobius/aCis шёл годами), но по устоявшимся паттернам — ровно там,
  где агентская разработка сильнее всего.
