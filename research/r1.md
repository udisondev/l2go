# r1 — Geodata / geomap: server-side движение и анти-чит

Серверная geodata для L2 Interlude: валидация движения, отлов wall-pass / fly / teleport / speed,
LOS. Продолжение [r0.md](r0.md) (архитектура мира). Geodata-сетка — **отдельная** от
симуляционных регионов-акторов из r0 (другие размеры, другая цель).

## TL;DR

- Geodata — **статика, read-only после загрузки** → самый лёгкий случай для конкурентной модели:
  **глобально шаренная, lock-free, без снапшотов и single-writer**.
- Держать через **mmap, off-heap** — НЕ как Go-кучу (GC не должен сканировать ~ГБ).
- Главный анти-чит — **не «ловить пакет», а симулировать движение**: сервер авторитетен над
  позицией, клиент шлёт намерение, сервер двигает по geo-валидированному пути и бродкастит **свою**
  позицию. Тогда wall/fly/tp/speed структурно невозможны.
- Geodata необходима, но недостаточна: speedhack/tp-внутри-зоны ловит **кинематика** (dist/time),
  не geodata.
- Geodata-сетка ≠ симуляционная сетка; LOS через границу регионов — бесплатно (глобальная geo +
  снапшот соседа из r0).

## Структура L2 geodata

Мир нарезан в сетку коллизий:

- **cell** — 16×16 игровых юнитов, базовая гранулярность движения.
- **block** — 8×8 ячеек = 128×128 юнитов.
- **geodata region** — файл, тайл из блоков.

Три типа блока:

1. **flat** — весь блок одна высота (один Z). Дешевле всего.
2. **complex** — у каждой из 64 ячеек свой Z + флаги.
3. **multilayer** — у ячейки **несколько слоёв** `(Z, NSWE)` (мосты, многоэтажки, пещеры, арки). Это
   и есть 3D: под мостом или на мосту.

Два куска данных на ячейку, которые ловят хаки:

- **NSWE-флаги** — можно ли шагнуть на North/South/West/East-соседа. Флаг выключен → **стена**.
  Это и есть данные про «проход сквозь стену».
- **Z / высота слоя** — высота земли в ячейке. Ловит «полёты»: заявленный Z далеко от валидного слоя.

> ⚠️ Точные константы (16/128, раскладка флагов, формат файла) зависят от источника geodata —
> **l2off Interlude** vs **L2J-конвертнутый** различаются. Сверять по парсеру-референсу (aCis /
> L2J `GeoEngine`), не по памяти.

## Главный принцип анти-чита: симулировать движение, а не валидировать пакет

Ошибка — пытаться «поймать» читерский пакет. Правильно: **сервер авторитетен над позицией**, клиент
шлёт только *намерение* (destination), сервер сам двигает сущность по geo-валидированному пути с её
реальной скоростью и **бродкастит свою позицию, а не клиентскую**.

Тогда wall/fly/teleport/speed-хаки **структурно невозможны** — максимум для хакнутого клиента это
рассинхрон на *своём* экране, который сервер поправит. Geodata делает «авторитетный путь»
геометрически корректным.

Реальная L2-модель — гибрид (чистый server-authoritative без клиентского предсказания лагает):
клиент предсказывает для плавности, периодически шлёт `ValidatePosition`, сервер сверяет с geodata +
кинематикой, при дрейфе > порога шлёт коррекцию (телепорт назад). «predict client, validate+correct
server».

## Три примитива поверх структуры

- **`canMove(from, to)` → дальняя достижимая точка.** Линейный проход по ячейкам (coords = world/16,
  Bresenham); на каждом шаге cell→cell проверяешь NSWE текущей ячейки в сторону следующей.
  Заблокировано → клампишь до последней валидной ячейки. Ловит **стены и out-of-bounds**. Диагональ —
  нельзя срезать угол: нужны оба ортогональных флага открыты.
- **`getNearestZ(x,y,z)` + step-height.** Резолвишь слой, ближайший к текущему Z; разница Z между
  соседними ячейками в пределах порога (ступенька — ок, прыжок на стену — нет). Отличает лестницу от
  **fly-hack**, валидирует заявленный Z.
- **`canSee(from, to)` (LOS).** 3D-трейс: линия не упирается в рельеф выше неё. Для скиллов/атак и
  против «стрельбы сквозь стену».

Чего geodata **НЕ** ловит: **speedhack** (нужна dist/time ≤ maxSpeed·dt·tolerance) и **teleport
внутри проходимой зоны** (непрерывность пути + dist/time). Geodata необходима, но недостаточна —
паруй с кинематикой.

## Интеграция с архитектурой r0

- **Иммутабельна → глобально шаренная, lock-free, без снапшотов/single-writer.** Иммутабельные данные
  безопасно шарить между всеми горутинами-регионами. Противоположность динамическому состоянию мира —
  синхронизация не нужна вообще.
- **mmap, не Go-heap.** Полная geodata — сотни МБ…~ГБ. НЕ держать как Go-кучу (GC ходил бы по
  гигабайту каждый цикл). `mmap` read-only → OS пейджит/кеширует, шарится между горутинами,
  **off-heap, GC не сканирует**. Лукап ячейки — O(1) индексная арифметика в mmap'нутый блок.
- **Geodata-сетка ≠ симуляционная сетка.** Региону-актору не нужно «владеть» своим куском geo — читает
  глобальную. Путь, пересекающий границу симуляц. региона, валидируется целиком против глобальной geo;
  смена владельца — это **хэндофф** из r0, отдельно.
- **LOS через границу — бесплатно.** Когда RA считает удар A по B (в RB), проверка LOS делается в RA:
  глобальная geo + позиция B из снапшота соседа. Без лишнего кросс-регионального сообщения.
- **Где исполняется валидация:** в тике региона-владельца движущейся сущности (он же single-writer её
  позиции). `MoveRequest` → мейлбокс R → R валидирует по geo → обновляет путь.

## Line-walk детально — это DDA (Amanatides–Woo), а не Bresenham

Поправка: для коллизии нужен **supercover-обход** — посетить *каждую* ячейку, которую задевает
отрезок. Чистый Bresenham пропускает диагонально-смежные ячейки → даёт срезать угол сквозь стену.
Инструмент — **Amanatides–Woo (voxel traversal)**: марш по ячейкам вдоль луча с трекингом, какую
границу пересечём следующей.

```go
// world→cell: cx = (x - WORLD_MIN_X) >> 4   (cell = 16 units)
func lineWalk(ox, oy, oz, tx, ty float64) (rx, ry, rz float64, blocked bool) {
    cx, cy := cellOf(ox), cellOf(oy)
    ecx, ecy := cellOf(tx), cellOf(ty)
    dx, dy := tx-ox, ty-oy
    stepX, stepY := sign(dx), sign(dy)
    tMaxX := boundaryDist(ox, stepX) / absOrInf(dx) // t до первой верт. границы
    tMaxY := boundaryDist(oy, stepY) / absOrInf(dy)
    tDeltaX := 16.0 / absOrInf(dx)                  // t на одну ячейку
    tDeltaY := 16.0 / absOrInf(dy)
    curZ := oz

    for cx != ecx || cy != ecy {
        switch {
        case approxEq(tMaxX, tMaxY): // луч через УГОЛ — анти-срез: оба ортогон. флага открыты
            if !passable(cx, cy, dirX(stepX)) || !passable(cx, cy, dirY(stepY)) {
                return cellCenter(cx, cy, curZ), true
            }
            nz, ok := stepZ(cx+stepX, cy+stepY, curZ)
            if !ok { return cellCenter(cx, cy, curZ), true }
            cx += stepX; cy += stepY; curZ = nz
            tMaxX += tDeltaX; tMaxY += tDeltaY
        case tMaxX < tMaxY:          // пересекаем верт. границу → шаг по X
            if !passable(cx, cy, dirX(stepX)) { return cellCenter(cx, cy, curZ), true }
            nz, ok := stepZ(cx+stepX, cy, curZ)
            if !ok { return cellCenter(cx, cy, curZ), true }
            cx += stepX; curZ = nz; tMaxX += tDeltaX
        default:                     // шаг по Y
            if !passable(cx, cy, dirY(stepY)) { return cellCenter(cx, cy, curZ), true }
            nz, ok := stepZ(cx, cy+stepY, curZ)
            if !ok { return cellCenter(cx, cy, curZ), true }
            cy += stepY; curZ = nz; tMaxY += tDeltaY
        }
    }
    return tx, ty, curZ, false
}
```

Три места, где реализация обычно багует:

- **`passable(cx,cy,dir)`** — NSWE-флаг ячейки в сторону шага. В geodata только 4 бита (N/S/W/E);
  **диагональной проходимости нет** — выводится: NE открыт ⇔ открыты и N, и E. Это и есть анти-срез в
  `approxEq`-ветке.
- **`stepZ(ncx,ncy,curZ)`** — резолв слоя в новой ячейке, ближайшего к `curZ`. Подъём `≤ MAX_STEP`
  (ступенька) — ок; спуск в пределах fall-лимита — ок; скачок вверх > step → стена (`ok=false`). В
  **multilayer** выбираешь ближайший *связный* слой — иначе «телепорт» на мост вместо прохода под ним.
- **угловая ветка** (`tMaxX≈tMaxY`) — луч ровно через угол ячейки; без проверки обоих ортогоналов
  читер просечёт L-образную стену по диагонали.

**LOS (`canSee`)** — тот же скелет, но вместо NSWE трекаешь Z линии (интерполяция `oz→tz` по `t`) и на
каждой ячейке проверяешь, что рельеф не поднимается выше линии. Поднялся → обзор перекрыт. Возврат:
дальняя достижимая точка (кламп) либо сам таргет. Сложность O(ячеек на пути) ≈ длина/16.

## Speed hack — кинематика, не геометрия

Ключ: **прямолинейное смещение ≤ длины пути ≤ maxSpeed·t** → проверка по straight-line честна (огибание
угла только удлиняет путь и укорачивает смещение, ложняка нет). Не проверять одиночный пакет (джиттер) —
**токен-бакет на сущность**:

```go
// каждый тик:
e.speedBudget = min(e.speedBudget+e.maxSpeed*dt, CAP) // CAP ~ 1–2 сек хода
// на ValidatePosition (смещение d за интервал):
e.speedBudget -= d
if e.speedBudget < -SLACK { flagSpeedHack(e); correct(e) }
```

`maxSpeed` — серверный авторитет (база × баффы/предметы, run/walk). `CAP` сглаживает лаг-спайки и
легитимные рывки, `SLACK` — порог. Бакет = амортизация джиттера без ложняка.

## Телепорты — флаг состояния, а не отдельная проверка

Два класса, различаются **происхождением**:

- **Легитимный** (Recall, GK, blink/shadow step, knockback, fear) — **server-authored**: сервер знает
  целевую точку, валидирует её geodata, ставит `authPos` и взводит `pendingTeleport`.
- **Хак** — клиент репортит позицию далеко от `authPos` без server-authored телепорта.

```go
switch {
case e.pendingTeleport:                       // сервер сам телепортнул
    if near(report, e.authPos) { e.pendingTeleport = false; e.speedBudget = CAP }
    else { correct(e) }
case d <= e.maxSpeed*dt*TOL && geoValid(path):
    accept(e, report)
default:
    flag(e); correct(e)                        // snap-back через ValidatePosition
}
```

Knockback/blink — тот же server-authored путь: валидируешь geo назначения, ставишь `authPos`, сбрасываешь
бакет. Телепорт не ломает speed-проверку, а легально обнуляет её на интервал.

## Синхронизация — всё это single-writer в тике региона-владельца

Вся валидация движения E крутится в горутине региона-владельца E (single-writer её позиции). Состояние
на сущности: `authPos`, `path/dest`, `speedBudget`, `pendingTeleport`, `lastValidate`. Входы из
мейлбокса: `MoveRequest{dest}`, `ValidatePosition{pos}`, `Teleport{target}` (server-authored).

**Синхронизация ≈ ноль:** geodata глобально-иммутабельна (читай без локов), мутабельное состояние
движения — single-writer внутри региона. Кросс-сущностной координации для валидации движения не нужно —
геометрия статична. Единственная кросс-региональная точка — путь пересёк границу региона → **хэндофф из
r0**, состояние движения едет в его пейлоаде.

## Батчинг: регион как единица, две фазы

«Много действий на шаг» — наполовину **иллюзия частоты**:

> Тяжёлый line-walk **НЕ** делается каждый тик на каждую сущность. Он event-driven: один раз на
> `MoveRequest` (провалидировать сегмент до цели и склампить). Между запросами сущность **коастит** по
> валидированному пути — дешёвая интерполяция, без geodata-трейса. LOS — на каст/атаку. ValidatePosition
> — раз в ~секунду, копеечная кинематика.

Реальный объём генерят **мобы** (тысячи AI, частый ре-пас/A*), не игроки. Батчить — **по региону** (не «со
всех», не «с одной»):

**Регион — естественная единица батча** (уже даёт r0: регион тикает свои сущности в своей горутине):

- **Cache locality:** сущности региона пространственно кучны → одни geodata-блоки → mmap-страницы горячи
  в кеше. Глобальный проход «по всем» это разрушил бы (и вернул глобальную точку синхронизации).
- **Изоляция:** нагрузка движения осады не трогает другие регионы.

**Внутри региона — две фазы за тик:**

```
Фаза A (дёшево, ВСЕ сущности, SoA-массивы, батч/SIMD):
    advance position по валидированному пути; обновить speedBudget.
    Это и есть per-tick стоимость — крошечная (чистая арифметика).

Фаза B (дорого, ТОЛЬКО очередь событий этого тика, с КАПОМ):
    обработать накопленные MoveRequest / re-path → line-walk / A*.
    Лимит K на тик; переполнение — defer на следующий тик
    (моб переживёт тик без ре-паса; игрокам приоритет).
```

Кап в фазе B = защита бюджета кадра из r0: регион с лавиной move-request (осада) не разнесёт барьер —
лишнее переносится на следующие тики.

Сверху два множителя:

- **Broad-phase перед line-walk:** старт и финиш в одном flat-блоке без стен → проходимо тривиально,
  walk пропускаем. Большинство коротких ходов — открытая местность; полный DDA только у стен / на
  границах блоков.
- **Мобам — медленный AI-такт** (1–2 Гц, не 10) + стаггер по тикам (round-robin). Наивное «все мобы
  пересчитывают путь каждый тик» — главный убийца.

**Ответ на «с одной или со всех»:** ни то, ни другое — **со всех в пределах региона (shard-level)**.
Per-entity теряет амортизацию, global — локальность и изоляцию. Регион — золотая середина, и он уже есть
в архитектуре.

## Pathfinding: A* и flow-field для осадной толпы

A* решает «один агент → одна цель», стоит O(агентов × поиск). На осаде сотни атакующих идут в **одну**
точку (замок/ворота/флаг) → задачу инвертируем: посчитать **раз на ячейку** направление к цели, агент
лишь читает стрелку. Стоимость на агента → **O(1), независимо от размера толпы**. Точка безубыточности
vs индивидуальный A* — ~10–20 агентов на общую цель; на осадных сотнях — разгром.

### Три стадии построения flow-field

1. **Cost field** — стоимость входа в ячейку из geodata: непроходимо (NSWE закрыт) = ∞, земля = 1,
   сложный рельеф больше. Статика, из той же проходимости, что и line-walk.
2. **Integration field** (Dijkstra-map) — **заливка Дейкстрой ОТ цели** по всем ячейкам: каждая ячейка
   получает суммарную стоимость дешевейшего пути до цели. Один Дейкстра, O(ячеек), **не** O(агентов).
   Дорогая стадия, но на всю толпу разом.
3. **Flow field** — для каждой ячейки берёшь соседа с мин. интегрированной стоимостью, сохраняешь вектор
   к нему. У каждой ячейки «стрелка под горку» к цели.

```go
// Стадия 2: integration field — Дейкстра от цели (мультиисточник для неск. ворот)
func buildIntegration(cost []uint16, goals []Cell) []uint32 {
    integ := fillAll(MAX)                          // ∞
    pq := minHeap{}
    for _, g := range goals { integ[g] = 0; pq.push(g, 0) }
    for pq.notEmpty() {
        c := pq.popMin()
        for _, nb := range neighbors8(c) {         // соседи по NSWE!
            if cost[nb] == WALL { continue }
            nc := integ[c] + cost[nb]*stepMul(c, nb) // diag дороже
            if nc < integ[nb] { integ[nb] = nc; pq.push(nb, nc) }
        }
    }
    return integ
}
// Стадия 3: flow field
func buildFlow(integ []uint32) []Dir {
    flow := make([]Dir, len(integ))
    for c := range integ {
        best, bd := c, integ[c]
        for _, nb := range neighbors8(c) {
            if integ[nb] < bd { bd = integ[nb]; best = nb }
        }
        flow[c] = dirTo(c, best)
    }
    return flow
}
// Потребление на агента (фаза A из «Батчинг») — O(1):
dir := flow[agent.cell]; agent.steer(dir)          // дальше coast/валидация как обычно
```

### Почему бьёт точно по worst-case r0

- Стоимость пасфайндинга осады становится **независимой от размера толпы**: вместо сотен A* — одна
  заливка поля.
- В терминах батчинга: взрыв фазы B (сотни ре-пасов) → **один build в фазе B** (редкий, амортизирован) +
  дешёвые лукапы в фазе A. Бюджет осадного шарда ограничен → изоляция r0 держится.

### Динамика

- **Статичная/медленная цель — идеально** (замок/ворота): поле строишь редко, переиспользуешь много
  тиков. Это и есть осада.
- **Движущаяся цель (погоня за игроком) — НЕ для flow-field** (поле под одного беглеца = rebuild каждый
  тик). Гибрид: flow-field на макро-марш «дойти до замка», локальный A*/steering — на последние метры боя.
- **Dirty-rebuild** на изменение геометрии (пали ворота → новый путь): переинтегрировать затронутую
  область или полный rebuild (на масштабе региона дёшево, амортизировано).
- **Мультиисточник:** засей нулём несколько целей (ворот) → каждый агент течёт к ближайшей, бесплатно из
  той же заливки.

### Локальное расталкивание — L2-поблажка

Flow-field даёт глобальное направление, но не разводит агентов между собой. В RTS поверх кладут
RVO/ORCA/boid-сепарацию. В L2 юниты обычно **стакаются** (нет жёсткой коллизии между ними) → локальное
избегание можно **пропустить** — одно поле двигает толпу.

### Стыковка с geodata / r0

- **Cost field** — из NSWE-проходимости (глобальная иммутабельная geodata), статика.
- **Integration + flow field** — динамический оверлей под цель, **владеет осадный шард** (single-writer
  r0): build в фазе B, чтение в фазе A. Память смешная: байт направления (3 бита/8 сторон) на ячейку;
  256×256 ≈ 64К ячеек ≈ десятки КБ на поле.
- **Морщина — multilayer** (этажи замка, мост): 2D-поля мало, нужен граф с переходами между слоями,
  поле считается на нём. Для штурма многоэтажного замка — требование, не теория.

**Итого:** осадная толпа = одно поле (Дейкстра от ворот, редкий rebuild) + O(1) лукап на моба; владелец —
изолированный осадный шард r0; cost-слой — из geodata.
