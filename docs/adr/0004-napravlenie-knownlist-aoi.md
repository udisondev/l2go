# ADR-0004: Направление knownlist/AoI — ячеечная репликация у владельца наблюдателя

**Статус:** accepted (владелец, 2026-09-09). v1.7 — направление прошло ревью-цикл (6 оптик,
4 раунда до нуля замечаний, §7) и независимый аудит трёх свежих агентов (доминирующих
альтернатив нет; единственная цепочка patch-on-patch удалена в источнике). Уровень —
**направление**, не детальный дизайн: выбираются механика подписки, форма снапшота, владение
outbound-состоянием и ограничители частоты; размеры ячеек, радиусы, числа троттлинга, формат
пакетов Interlude — фазы 2–6.

## Контекст

«Проблема города» — убийца №1 по CPU в r0: n игроков в точке взаимной видимости → O(n²)
fan-out апдейтов. Форма её решения определяет форму снапшотов и весь AoI-слой (r2 §Открытые
вопросы п.2 — единственный TODO r0 без дизайна). Входы:

- r0: три несмешиваемых слоя — симуляция (владение по регионам) / видимость (AoI, пересекает
  границы) / non-spatial сервисы; видимость ≠ владение; снапшот = иммутабельная публикация +
  atomic swap.
- r2: GC-давление снапшотов (per-entity против per-owner блоба; публиковать dirty, а не весь
  мир каждый тик); сетевой backpressure (outbound-бюджет на клиента под бродкаст-лавиной);
  knownlist обязана иметь минимальную реализацию в walking skeleton (фаза 3) и тюнится ботами
  (фаза 6).
- r3 §3: канонический механизм видимости — чтение снапшота соседа (ghost-реплики отдельным
  механизмом не строятся); ID переживает хэндофф → меняется источник данных, не видимость;
  дедуп по entity-ID.
- ADR-0003 (принят, §16 — прямые требования к этому ADR): AoI = соединение потоков с
  ограничителями частоты; дедуп по entity-ID **и** composite-ключу слуг `(ownerID, slot)`
  (слуги публикуются в `servants[]` снапшота хозяина под стабильным протокольным objectId,
  трупы слуг — там же); выбор источника при двойной публикации в окне переезда — по max-epoch;
  **hold-last** (источник старой эпохи держится до появления новой — анти-мигание); снапшот-типы
  инкапсулированы в модуле репликации; advisory-чтения логируются в порцию (D4), репликация к
  клиенту входом свёртки не является.

## Решение

Шесть осей; по каждой зафиксирован выбор, детали — своим фазам.

### 1. Кто вычисляет видимость: регион-владелец наблюдателя

Knownlist игрока P и его исходящий поток собирает регион-владелец P — тот же, кто читает ящик P
и компонует его клиентские пакеты. Отдельных репликационных акторов/пула нет: outbound-поток —
состояние мира, а состояние мира трогает только горутина-владелец (инвариант 7 / ADR-0002;
пассивность черновика — И8 ADR-0003). Нагрузка репликации **следует за наблюдателями, не за
толпой**: регион платит за своих клиентов, сколько бы их ни стояло в соседнем (изоляция —
топологией; горячий регион города лечится бюджетом оси 5, не переездом работы).

**View set** («кого клиент уже знает» + last-sent для дельт) и текущая подписка ячеек —
**пересобираемое outbound-состояние региона-владельца наблюдателя**: в модель сущности и в
чемодан НЕ входят (И3 не задета — чемодан несёт только игровое состояние), игровой логике
недоступны (геймплейные решения о видимости — только через advisory-API с логированием, D4),
в бит-в-бит реплей не входят. Пересборка дешева: O(#ячеек подписки) по заголовкам.

**Граница compose/энкод:** в тике региона — только сборка логического кадра (join + компоновка
апдейтов, single-writer); **слэбы кадра аллоцируются на кадр** (то же умолчание, что у блоба
оси 3: слэб, ушедший в стейтлес-стадию, не трогается — «свободный reuse = data race»).
Энкод, крипта и запись в коннект — **стейтлес-стадия вне тика** (r3 §2 прямо разрешает):
город 1000 × ~2 КБ/тик = ~2 МБ/тик, на ядро Blowfish-темпе это ~20 мс — весь бюджет, если
тащить в тик. Очередь энкод-стадии декларирует **per-client FIFO** — порядок кадров одного
клиента сохраняется («стейтлес» — про состояние мира, не про порядок кадров: параллельные
энкодеры без FIFO дали бы ретроградные позиции). Переиспользование слэбов — оптимизация
фазы 6: слэб передаётся во владение энкод-стадии и возвращается её очередью; нет свободного —
свежая аллокация, никогда не блокировать.

**Окно хэндоффа самого наблюдателя:** до флипа RB (владелец) ведёт исходящий **как обычно** —
view set его собственный, мутируется свободно, включая ввод новых объектов (слепоты окна
нет). **Обязанность удаления переезжает:** затравка — множество ключей известного клиенту
**K** (= view set RB на момент флипа: всё, введённое RB в исходящий конвейер, включая кадры
in-flight; ключи — единое пространство join: entity-ID сущностей, `(ownerID, slot)` слуг,
id записей лёгкого класса; ~8 КБ при knownlist 1000) — едет **в том же контрольном письме,
что и сигнал активации владения** RB→RC (одно письмо — переупорядочение непредставимо по
построению; приоритетная полоса с bounded-drain иначе допускала бы разрыв «активация есть,
затравки нет»). **Затравка применяется атомарно обработке этого письма** (view set := K —
установка базлайна указателем): эмиттер-владелец возникает только этой обработкой, «эмиттить
без применённой затравки» непредставимо по построению — флаг-гейт и таймауты непотребления
не нужны. Повторный переезд до первого тика — обычный хэндофф по единственному правилу
«затравка = view set владельца на момент флипа»: RC ничего не эмиттил, его view set = K —
письмо следующему владельцу само оказывается пересылкой K.
RC на первом тике читает заголовки нового стенсила (**M**) и сходится **единым
дельта-механизмом**: удаления K\M — **по семантике оси 4** (без маркера — DeleteObject; с
маркером переезда — hold-last до max-epoch/таймаута, иначе мигание на стыке двух переездов),
вводы M\K (спавны), для K∩M — продолжение обычного стрима (протокольные апдейты L2
самодостаточны/абсолютны — референс OQ-7; last-sent для корректности не нужен); last-sent у
RC накапливается с нуля — первый тик после переезда несёт выравнивающие апдейты, в худшем
случае (толпа стоячих, обязательные события вроде смерть→труп не «задиртятся» повторно) —
до O(|K∩M|) пакетов, режется бюджетом (фаза 6). Смена пространства ячеек (ось 2) —
вырожденный случай: K∩M = ∅ → удалить всё K, ввести всё M. Это **один** механизм конвергенции
(затравка + дельта), не два; дублей и мигания нет по построению — корректность не зависит от
идемпотентности спавн-пакетов (OQ-5 — свойство формата, не предпосылка). **Энкод-очередь
lossless до disconnect:** дроп кадра в очереди энкод-стадии = вечная невидимость введённого
или вечный фантом неудалённого; коалесинг — только в compose тика, не в очереди; backpressure
= TCP + порог disconnect в тиках (D1). Перевозка last-sent (полного view set) исключена из
базового механизма; допустимая эволюция фазы 6 — по метрикам выравнивающего шума на
пограничных боях. Осознанный трейд-офф: бёрст выравниваний редок, дёшев и режется бюджетом,
а перевозка волатильного кеша last-sent утяжелила бы протокол хэндоффа форматом, дрейфующим
с эволюцией апдейтов; при этом OQ-7 (абсолютность апдейтов) — блокирующий для фазы 4, и
fallback при его опровержении — досрочный подъём перевозки last-sent, не смена направления.
Обязательство «исходящий буфер самому замороженному жив» (ADR-0003 §5)
исполняется тривиально: владелец не менялся до флипа. При аборте затравка не шлётся (попытка
умерла, RC-черновик гасится — RB вёл K без разрыва).

### 2. Механика подписки: глобальная сетка ячеек мельче региона

Сетка AoI-ячеек глобальна и выровнена глобально (не по границам регионов). Правило размера:
ячейка ≥ радиуса обзора; подписка наблюдателя — **константный стенсил ячеек вокруг его ячейки**
(3×3 при ячейке, равной радиусу); «2×2…3×3» — оценка фактического покрытия круга, не размер
подписки. Сущности крайних ячеек стенсила за пределами радиуса отфильтровываются членством
(ось 5, гистерезис) — смена подписки не мерцает. Точный размер ячейки — фаза 6 по метрикам.

- Сущность публикуется **своим владельцем** в ячейку своей позиции; ячейка на стыке регионов
  просто имеет сущности от нескольких издателей — конфликта нет: каждая сущность публикуется
  ровно одним регионом (своим), ячейка — ключ подписки, не владелец.
- **Реестр издателей ячейки — статическая функция геометрии регионов основного мира с запасом
  на R_leash слуг** (ADR-0003 §6: leash ≤ глубины читаемых снапшотов): покрывает и
  издателей-негеометров — регион-владелец хозяина публикует запись слуги в ячейке позиции слуги
  (ось 3). Реестр остаётся статическим (геометрия + константа leash), динамических реестров нет;
  сегментация блоба удерживает цену чтения — читается только нужный сегмент. Инстансы и олимп
  публикуют в **собственные пространства ячеек** (координаты переиспользуют мировые — без
  разделения наблюдатели основного мира получали бы призраков). Осада Interlude — событие
  открытого мира (зрители на холмах, торговцы у стен): пока осада в открытом мире, у неё
  отдельные диспетчер и бюджет (r3 §1), но публикация — в общую сетку; отдельное пространство —
  только если будущий ADR переведёт осаду в инстанс.
- Наблюдатель подписан на стенсил вокруг своей ячейки; смена подписки — только при пересечении
  границы ячейки самим наблюдателем. Membership известности меняется событийно: пересечение
  границ, спавн/деспавн и **изменение входов предиката видимости** (флаги цели, атрибуты
  наблюдателя — ось 4), а не пересканированием толпы каждый тик; детект изменения членства
  обязан стоить O(#ячеек подписки) — генерация членства в заголовке ячейки либо события
  членства в dirty-потоке (требование к детальному дизайну фаз 3–4).
- **Смена пространства ячеек** (вход/выход из инстанса/олимпа) не наследует непрерывность:
  единый дельта-механизм оси 1 работает с вырожденным пересечением (K∩M = ∅ — удалить всё
  старое, ввести всё новое); фантомы старого пространства исключены механизмом, не обещанием.

### 3. Форма снапшота: per-owner SoA-блоб с полными пейлоадами, dirty-манифест

Регион в конце тика публикует **один** иммутабельный блоб (свап указателя, r0) с SoA-сегментами
по ячейкам: полный заголовок членства (дёшево читать состав, включая маркеры переезда — ось 4)
и **полные пейлоады записей**; dirty-марка — **манифест чтения** («что изменилось у издателя
с прошлого поколения»), а не дельта-носитель. Обработчик, идущий каждым тиком, трогает только
dirty-записи (экономия join-скана); **пропуск поколений безвреден по построению** — свежий
блоб самодостаточен, отставший читатель просто обрабатывает сегмент целиком; генерация в
заголовке остаётся счётчиком манифеста и метрикой пейсинга, механика дозагрузок не существует
(дельта-пейлоады — измеренная оптимизация фазы 6, вместе с ней вернулась бы и дисциплина
версионного ресинка). Цена дефолта — копирование: ~320 КБ/тик на горячем регионе города
(~5000 записей × ~64 Б ≈ 30–50 мкс memcpy, ~3 МБ/с) — на два порядка ниже бюджета шага; датчик
GC outbound-пути это видит. Свап происходит каждый тик — advisory-потребителям (range-чек
удара, r3 §3) нужна свежесть последнего завершённого тика издателя (при дропнутых тиках
издателя блоб стареет на N тиков — норма коалесинга ADR-0002).
**Аллокация:** по умолчанию блоб аллоцируется заново на каждый тик (1–2 аллокации на регион-тик
— на порядки меньше per-entity); переиспользование/пул — оптимизация фазы 6, требующая
дисциплины поколений (старая версия живёт до выхода последнего читателя, а время удержания
читателя в модели без барьера не ограничено — свободный reuse = data race).

**Контракт доступа (обязателен, иначе город не проходит по счёту):** записи в сегменте ячейки
занимают **стабильные плотные слоты**; реюз слота после деспавна детектируется вечным id
записи (И1 ADR-0003 — ID не переиспользуются) тем же O(1) array-indexed чтением; членство
читается битмапом слотов; на пару (наблюдатель, цель) — не более O(1) **array-indexed** операций
(хеш-lookup на пару запрещён: 0.5–1M пар/тик города × ~30 нс хеша = 15–30 мс — срыв бюджета;
структурный доступ 4–6 нс = 2.5–6 мс — проходит).

**Почему полные пейлоады, а не дельты (генеалогия):** дельта-пейлоады заставляли читателя
детектить пропуски поколений и дозагружать полные сегменты (генерация + last-read + resync +
кап с переносом против лупа перегрузки) — три механизма чинили одну экономию; на полных
пейлоадах проблема исчезает классом (пропуск безвреден, OQ-4 закрыт исчезновением).

Per-entity снапшоты (свой atomic-указатель на запись каждой сущности) отвергнуты — ось закрыта
(арена-аллокатор не спасает: манифест dirty всё равно нужен = заголовок блоба, а рассеянные
указатели — 1000 кеш-промахов на наблюдателя против последовательного SoA-скана).

Слуги — в блобе хозяина (`servants[]`, стабильный протокольный objectId), включая трупы (смерть
≠ деспавн). Запись слуги публикуется в сегмент ячейки **позиции слуги**: источник данных — блоб
хозяина, пространственный ключ — сам слуга (пет, отбежавший от хозяина, — обычный сценарий L2:
он виден и таргетируем там, где стоит); запись слуги несёт **эпоху хозяина** (ось 4).

**Предметы на земле и прочие динамические мировые объекты** (дроп с мобов, брошенное, осадные
флаги) — полноценные AoI-записи лёгкого класса: статичная позиция, itemID, count; публикуются
регионом-владельцем в ячейку позиции той же механикой (spawn/despawn/churn лута — обычные
события членства). Предмет — **не сущность транспорта**: decay/время жизни/владение — состояние
региона-владельца позиции (по образцу спавн-таймеров, ADR-0003 §3); подбор — только transfer
против владельцев персонажей (И9 не ослабляется); класс адресации — P0.10.

### 4. Join: дедуп, окно переезда, предикат видимости

Сбор видимости = union ячеек подписки из снапшотов издателей (до 9 регионов), с дисциплиной:

- **Дедуп:** entity-ID для сущностей; `(ownerID, slot)` для слуг. Сущность с уникальным ID
  встречается в снапшотах нескольких издателей только в окне переезда (замороженная копия у
  старого vs живая у нового) — источник выбирается по **max-epoch**; то же правило и та же
  защита действуют для записи слуги (по эпохе хозяина). Эпоха сущности: **новый владелец
  инкрементирует при активации, до первой своей публикации** (чемодан несёт k, RC публикует
  k+1 — завершённый переезд ADR-0003 §8; при аборте инкремента нет); замороженная копия старого
  владельца всегда строго младше; публикация одной записи двумя издателями с равной эпохой —
  инвариантное нарушение (алерт), тай-брейком не разрешается.
- **Семантика ухода из заголовка членства — два случая:** (i) **маркер переезда** — издатель
  ставит его в публикацию, где запись исчезает из его заголовка, и **только при граничном
  хэндоффе** (гистерезисный переход соседям должен быть бесшовным); телепорт, вход в инстанс и
  деспавн маркером не помечаются. Маркер переезда — единственный триггер **hold-last**: держим
  последнее известное состояние до публикации нового владельца по max-epoch или таймаута
  бюджета хэндоффа в тиках (D1) — нет delete→spawn-мигания на стыке. При аборте маркер не
  возникает вовсе (запись не исчезает — RB продолжает публиковать). (ii) **Отсутствие записи
  без маркера** — немедленное удаление у клиента (деспавн, движение/выход из обзора, телепорт —
  одинаково; как DeleteObject при телепорте в живом L2 — проверить по референсу, включая
  межрегиональный телепорт, OQ-6). Фантом на таймаут хэндоффа от телепортировавшегося —
  исключён конструкцией.
- **Видимость = предикат пары (наблюдатель, цель) — одна функция для обоих потребителей**
  (репликация и advisory): флаги цели (инвиз/GM/скрытность — за флаги авторитетен владелец
  цели в момент публикации) ∧ атрибуты наблюдателя (право видеть скрытое — GM;
  детект-скилл в Interlude — проверить по референсу, OQ-2). Отличия потребителей — только
  радиусом и явно документированными исключениями; расхождение «клиент видит, моб не видит»
  (аггро сквозь стену / радар за холмом) не может возникнуть как деталь реализации — только как
  осознанное решение. Радиус в предикате не дублируется: радиальная фильтрация живёт в
  членстве (ось 5, гистерезис enter/exit), предикат — флаги/атрибуты и будущий LOS.
  Предикат **переоценивается при изменении любого входа** — смена флага цели или атрибута
  наблюдателя = полноправное событие членства (переоценка всех пар, а не только новичков):
  предикат→false = удаление у клиента, →true = ввод. Иначе инвиз/GM-hide течёт неограниченно
  долго (утечка see-invis). **Гео-LOS в базовом предикате репликации нет — это документированное
  исключение, а не пробел:** живой Interlude ведёт известность дистанционно (сущность за
  стеной/холмом видна клиенту — сверить по референсу в фазе 3), гео-LOS (canSee) в референсе
  живёт в advisory-событиях — аггро, применение скиллов: редкие per-кандидат проверки, где
  честный raycast допустим; пер-парный LOS на тиковом пути запрещён в любом случае
  (0.5–1M пар × 1–10 мкс = секунды на тик). Введение гео-известности в репликацию (осознанное
  отклонение от живого клиента, например анти-радар) — только отдельным будущим ADR, который
  обязан: включить позицию обоих концов в число входов предиката с переоценкой (иначе утечка
  see-occluded) и консервативную аппроксимацию (ошибка — только в сторону недовыдачи, не
  утечки).
- Смерть ≠ исчезновение (труп виден до деспавна, ADR-0003 глоссарий).

У join два потребителя с разной дисциплиной (граница закреплена D4 ADR-0003):
**репликация к клиенту** (оси 1, 5) — выходной поток, в лог порций не входит, на свёртку не
влияет; **advisory-запросы геймплея** (аггро-скан моба, range-чек, перечисление целей AoE) —
вход свёртки, только через advisory-API модуля репликации с логированием. Один субстрат
(ячейки + снапшоты), два потребителя; радиусы разные (обзор клиента против аггро-радиуса) —
разные подписки на ту же сетку, не два механизма.

### 5. Ограничители частоты: LOD-тиры + per-client outbound budget

«Город» ограничивается на исходящем, не на членстве:

- **LOD-тиры по расстоянию** — политика на весь исходящий поток пары (наблюдатель, цель), не
  только на позиции: ближним — полный темп; дальним — позиция с пониженной частотой (клиент
  интерполирует), непозиционные события — по классу события (реестр обязательных к доставке —
  смерть→труп, деспавн, смена статуса витрины). Базовый рычаг привязки: **границы тиров =
  границы ячеек** (кольцо стенсила = тир) — дистанционная работа выносится в предвычисление
  по группе наблюдателей одной ячейки; тир меняется только при смене ячейки цели, осцилляция
  на границе ячейки меняет только темп (не членство) и закрывается числами фазы 6 — отдельного
  гистерезиса тиров нет. LOD приблизителен по природе, промах на кольцо меняет только темп;
  для толпы «в точке» (все в одной ячейке) тир-по-ячейкам вырождается — несущий рычаг там
  бюджетный ранний выход (ось 5, выборка) и обязательный битмап. Реализация тиров и бюджета —
  фаза 6 (до нагрузочного фальсификатора), фазы 3–4 — join без LOD.
- **Per-client outbound budget** (закрывает backpressure из r2), в тиках — пакетов/тик,
  байт/тик (D1: настенные часы вне шлюза не вводятся). При дефиците — детерминированный
  приоритет; порядок «спавн/деспавн > близость > свежесть > ID» — настраиваемый дефолт (состав
  классов и детерминированность — направление; порядок — тюнинг фазы 6); выборка — бакетами по
  дистанции за O(d), не кучей. Коалесинг позиций (побеждает последняя); «батчинг» = несколько
  протокольных пакетов в одном кадре записи/криптоблоке (нового формата пакета не вводится).
  Детерминированность приоритета нужна для тестируемости и анти-мерцания, не для реплея.
- **Защита бюджета от направленного исчерпания:** (а) пер-сорс троттлинг клиентских действий,
  порождающих членство-события (токен-бакет на выброс/подбор предметов, спавны слуг — числа
  фазы 6), распространяемый и на дёшево порождаемые клиентом события обязательного класса —
  «обязательный к доставке» не означает неограниченной скорости источника; (б) лёгкий класс
  (предметы на земле) — отдельная низкоприоритетная полоса, не «спавн» целиком; (в)
  зарезервированная доля бюджета за позиционными/ближними апдейтами, которую спавн-лавина
  съесть не может. Иначе мультибокс конвертирует дешёвые события в ослепление жертвы при
  «здоровом» сервере.
- **Гистерезис обязателен у членства** (enter/exit по двум радиусам — иначе бег по дуге на краю
  обзора = осцилляция spawn/despawn); на границах тиров — опция фазы 6 по метрикам; для бюджета
  гистерезис не определяется (нечему).
- **Жёсткий кап численности knownlist** — аварийный клапан за конфигом, по умолчанию выключен:
  честный режим — не капать членство (социалка города), а капать темп.

### 6. Минимальная экспозиция (фаза 3) и датчик финальной настройки (фаза 6)

Walking skeleton: один регион, одна ячейка, без LOD/бюджета — join вырождается в «все сущности
региона», но владельческая дисциплина, блоб, два случая ухода, контракт стабильных слотов
(детект реюза по вечному id) и предикат видимости — те же. Вся детализация (размер ячейки,
границы тиров, числа бюджета, порядок приоритетов) — фаза 6 по измерениям ботов; датчики и
сигналы пересмотра — в «Проверке решения».

## Отвергнутые альтернативы

1. **Отдельный слой репликации (AoI-акторы/пулы-шарды).** Шов self-потока (инвентарь/HP/системные
   сообщения компонует владелец из приватного состояния — либо второй писатель в исходящий
   буфер клиента, либо хоп письмом с правилом порядка отправителей поверх И5); вторая точка
   владения outbound-состоянием; новый компонент и домен отказа. CPU-стены не снимает: стена
   «N в точке» у шарда и у выбранного направления общая (полный скан и там, и там проваливает
   бюджет; спасает один и тот же бюджетный ранний выход оси 5) — шард даёт только изоляцию,
   которую внутри направления дублирует бюджет. Держится кандидатом-запасом за явным
   фальсификатором («Проверка решения»); после v1.3 (пересобираемый view set) и v1.4 (затравка)
   переход механически дешевле — join-функция та же; в мире шардов затравка не нужна вовсе
   (шард-подписчик переживает флипы наблюдателя без переноса известности).
2. **Push издателя в чужие клиентские буферы** (владелец сущности сам рассылает апдейты
   наблюдателям). Кросс-региональная запись в состояние чужого наблюдателя — нарушает
   single-writer (инвариант 1) и адресацию ADR-0003; ломит изоляцию (издатель города инжектит
   работу соседям) и свежесть advisory.
3. **Per-entity снапшоты (включая арена-аллокатор).** GC-аргумент арена снимает лишь
   наполовину: манифест dirty всё равно нужен (= заголовок блоба), а чтение — рассеянные
   указатели и кеш-промахи против последовательного SoA-скана.
4. **Подписка регионами целиком (3×3 региона) как механика.** Membership поддерживается сканом
   популяции девяти регионов на наблюдателя; ячейки дают событийное членство. 3×3 остаётся
   верхней границей числа издателей в join, не механикой подписки.
5. **Ghost-реплики с собственной симуляцией / двойная симуляция соседа.** Отвергнуто r3 §3:
   ghost = снапшот; симулирует один владелец.
6. **Жёсткий кап knownlist как основной механизм.** Ломает видимость города (социалка, торг);
   кап — только аварийный клапан (ось 5).
7. **Троттлинг публикации снапшотов (реже тика).** Ломает свежесть advisory (range-чекам нужен
   последний завершённый тик издателя, r3 §3); троттлится исходящее к клиенту, не публикация.
8. **AoI на клиенте (клиент запрашивает интерес).** Формально самая большая экономия CPU
   (−100% join-стадии), но инвертирует серверную авторитетность видимости (r1): радар
   обслуживается сервером по запросу, инвиз/GM-скрытость течёт, запросный DoS; стоковый клиент
   Interlude такого протокола не имеет. Ошибка уровня продукта, не дизайна.
9. **Зонная/room-based известность поверх зон датапака.** Зоны — перекрывающиеся полигоны
   (точка одновременно в городе, мире и осаде — «комната» не определена), размер ≠ радиусу
   обзора, дикость зонами не покрыта — нужен геометрический fallback = вторая система.
10. **Дифф-потоки издателя вместо блоба с заголовком.** Требуют retention/офсетов подписчиков
    и ресинка; advisory нужен произвольный доступ к текущему состоянию (материализация = блоб);
    hold-last/max-epoch пришлось бы переопределять поверх порядка доставки. Эквивалентна как
    эволюция фазы 6 — уже явно разрешена, стартово не выбирается.
11. **Динамические круговые подписки (без стенсила, «подписка на круг»).** Состав круга требует
    пространственного индекса, обновляемого каждым движением, и читаемого чужими регионами —
    либо общий мутабельный индекс (= №12), либо снапшот индекса на тик (= блоб с лишним
    копированием); churn непрерывной метрики выше, чем у дискретной границы ячейки; в городе
    состав круга ≈ состав стенсила — экономии ноль именно там, где больно.
12. **Общий mutable spatial index (RCU/seqlock).** Четвёртый вид синхронизации сверх
    инварианта 3 AGENTS; контеншн в точке максимального churn (город); seqlock на обычных
    чтениях либо краснит ворота `-race`, либо требует atomic-чтений и теряет выгоду.
    Иммутабельный свап указателя уже есть Go-идиоматичный RCU.
13. **Гибрид «ячейки для членства + апдейты прямым push-потоком издатель→подписчики».**
    Сводится к комбинации №1 (вторая сторона владения outbound) + №2 (push в чужие буферы):
    4000+ писем/тик в городском регионе дороже чтения, которое они заменяют; ломает изоляцию
    («толпа топит только свои регионы») и свежесть advisory (push под капом drain отстаёт от
    pull-чтения последнего завершённого тика).

## Последствия

- **P0.9:** в карте компонентов появляется модуль репликации/AoI (снапшот-типы, ячеечная сетка,
  advisory-API с инжектируемым швом для реплей-харнесса — снапшот-типы инкапсулированы там по
  ADR-0003 §16) и энкод-стадия исходящего (стейтлес-пул вне тика, per-client FIFO, дисциплина
  владения слэбами); библиотеки внутри регионов/конвейера, собственных горутин-владельцев
  состояния мира не имеют.
- **P0.10:** в таксономию добавляется класс исходящих (outbound) сообщений клиента с декларацией
  очереди-бюджета (единая декларация очередей ADR-0003 §4), класс адресации предметов на
  земле и контрольное письмо-затравка (множество известных ID) в протоколе хэндоффа наблюдателя;
  в черновик формата снапшота — эпоха сущности в записи, генерация блоба и маркеры переезда в
  заголовке членства. View set и подписка ячеек в модель сущности НЕ входят (outbound-состояние
  региона-владельца, пересобираемое).
- **Фаза 3:** knownlist walking skeleton — вырожденная конфигурация той же механики (ось 6), не
  отдельный throwaway-код; синтетический join-бенч (см. «Проверку»); сюда же переносится
  референсный ресёрч knownlist-семантик (числа гистерезиса enter/exit, детект-инвиз, поведение
  трупа пета, мгновенность DeleteObject при телепорте, дистанционность известности и
  абсолютность апдейтов — OQ-1/2/3/5/6/7/8 — GPL-референсы). Тест-обязательства: join =
  set-equality по населению региона, уход из членства → DeleteObject, предикат (включая
  переоценку по смене флагов), дисциплина публикации блоба (только владелец, свап после шага,
  иммутабельность), недоступность view set игровой логике.
- **Фаза 4:** снапшоты и advisory уже потребляются боем; join-стадия входит в бюджет шага
  региона (первоклассная метрика — см. «Проверку»); механика окна хэндоффа наблюдателя
  (затравка + дельта); property-тесты: дедуп по entity-ID и `(ownerID, slot)` (не более одной
  копии на запись в join; равные эпохи → алерт), hold-last без delete→spawn на стыке,
  гистерезис против осцилляции enter/exit, независимость детекта членства от толпы
  (O(#ячеек подписки)), конвергенция «множество известного клиента = view set» после
  затравки-дельты; кейсы: «затравка применена до первого эмитта RC», «двойной переезд до
  первого тика (затравка = view set = K, ничего не эмиттировано)», «уход члена K с маркером
  переезда в окне (hold-last, не DeleteObject)», «K∩M сходится без выравнивающего ре-спавна»
  (детектор OQ-7 — блокирующего).
- **Фаза 6:** реализация LOD-тиров и per-client budget (до нагрузочного фальсификатора) и их
  тюнинг; допустимые эволюции, не меняющие направления: дельта-пейлоады блоба (с дисциплиной
  версионного ресинка), пул с дисциплиной поколений, перевозка last-sent в чемодане
  (досрочный подъём — fallback OQ-7), encode-once предсериализация broadcast-пакетов у
  издателя (сериализация — единственная часть энкод-стадии, масштабирующаяся с событиями, а
  не с клиентами; держать вне контракта блоба), пер-ячеечный мягкий кап предметов лёгкого
  класса (деспавн старейших — owner-side предохранитель от коллективного раздувания сегментов
  многими источниками; L2-аутентичен, decay и так существует).
- **Не влияет:** пати-окно (UI-подписка по partyID, r3 §4), чат/клан/маркет (non-spatial
  слой), статические объекты мира (датапак по позиции — не поток; динамическая геометрия —
  отдельный открытый вопрос r2).

## Цена решения

- Join-работа живёт в тике региона-владельца наблюдателя: нагрузка следует за наблюдателями —
  регион города с тысячей своих клиентов платит за всех них (изоляция — фича, но концентрация
  клиентов в одном регионе — горячая точка; лечится бюджетом оси 5, не переездом работы).
- View set — память outbound-состояния: в городе ~1000 записей × ~48 Б ≈ 48 КБ на клиента
  (больше инвентаря в 2–4 раза), worst-case 10k городских ≈ сотни МБ; переезд наблюдателя стоит
  контрольное письмо-затравку (ID-множество, ~8 КБ при knownlist 1000) и выравнивающие апдейты
  первого тика (last-sent накапливается с нуля) — в худшем случае (стоячая толпа, обязательные
  события) до O(|известных|) пакетов, режется бюджетом (фаза 6); типичный случай (движущаяся
  толпа) поглощается dirty-потоком.
- Граница compose/энкод: энкод и крипта — вне тика (стейтлес-стадия), значит исходящий конвейер
  — ещё один компонент с собственной очередью и декларацией (r3 §2), per-client FIFO и
  дисциплиной владения слэбами; рассинхрон «собрано / отправлено» — новая наблюдаемая точка.
- Глобальная ячеечная сетка — ещё одна структура с дисциплиной (выравнивание, размер, границы,
  отдельные пространства инстансов, стабильные слоты с детектом реюза по вечному id) и ещё один
  источник событийности (пересечения границ ячеек) — код, который надо написать и
  протестировать; вырожденная конфигурация фазы 3 сетку почти не отрабатывает.
- Исходящий поток недетерминирован по времени **и побайтовому составу** (батчинг по бюджету,
  интерливинг свапов издателей): реплей воспроизводит серверную свёртку бит-в-бит (D1–D6),
  но не исходящий поток — golden-тесты фаз 1+ кладутся на свёртку и кодек, не на outbound;
  корректность исходящего (нет пакетов при false-предикате, нет двойников, обязательные классы
  в срок) покрывается контракт-тестами через ботов (фазы 3–4), не реплеем.

## Проверка решения

**Фаза 3 — синтетический join-бенч** (заглушка-блоб + join-цикл): главный бет направления —
константа ~7–11 нс/пара — меряется до постройки AoI-стека, порядок величины и тренд, не ворота;
join-доля шага — первоклассный датчик с фазы 4 (не ждать фазы 6).

Фаза 6, сценарии: «город» (100/300/1000 ботов в радиусе взаимной видимости), «пограничный бой»
(толпа на границе двух регионов — join-нагрузка переездов + выравнивающие апдейты) и
контрольный «лес» (равномерное рассеяние). Метрики-датчики:

- p99/p999 шага региона и доля join-стадии в нём (профилированием) при 10 Гц; **якорь сигнала
  пересмотра направления — фальсификатор** (ниже); «join-стадия >30% бюджета» — warning-датчик,
  «>70% + промах p99» — сигнал тюнинга (прикидка проходной конфигурации города-1000:
  скан 2.5–6 мс + компоновка ~4.5 мс + выборка ~0.3 мс ≈ 8–11 мс из 20 мс — около половины
  бюджета; порог 30% горит в зоне успеха — числа первого порядка, фаза 6 их заменит);
  сериализация join в одной горутине региона — единственное место, где направление может
  упереться: доля join-стадии читается как главный сигнал, фальсификатор и кандидат-запас
  (§5-1) для этого есть;
- пакеты/тик и байты/тик на клиента против бюджета; доля коалесированных позиций; аллокации/с
  и GC-паузы **всего outbound-пути** (блобы + пакеты + слэбы; порог GC-паузы < 1 мс); объём
  выравнивающих апдейтов и затравок на переезд (датчик решения о перевозке last-sent);
  глубина и латентность compose→socket энкод-очереди (lossless — растёт только глубина,
  потеря = алерт);
- p99 размера view set; churn membership на пересечении границ ячеек; **доля полных повторов
  сегментов** (пропуски поколений — датчик здоровья пейсинга читателей; систематический рост —
  регион перегрет, смотреть вотчдог ADR-0002).

Сигналы пересмотра **чисел**: membership-churn доминирует над dirty-работой; коалесинг съедает
большинство позиционных апдейтов (тиры грубее, чем нужно); warning-порог join-стадия.
**Фальсификатор направления:** при 1000+ ботах в точке p99 шага не лезет в бюджет при
исчерпанных рычагах оси 5 — несущий рычаг толпы-в-точке это бюджетный ранний выход выборки +
обязательный битмап (тир-по-ячейкам в точке вырождается — все в одной ячейке; он работает на
растянутых толпах); оценка рычагов обязана предшествовать пересмотру. Прикидка стены без
рычагов — по полной пер-парной константе (скан + компоновка + выборка ≈ 7–11 нс/пара):
√(бюджет / константа) ≈ 1000–1700 в точке при бюджете 10–20 мс; при SIMD-скане — выше;
якорь первого порядка, фаза 6 заменит числами. Если фальсификатор сработал — направление
«join у владельца наблюдателя» пересматривается новым ADR; кандидат-запас — репликационные
шарды с собственным бюджетом (альтернатива 1, сегодня отвергнута).

### Цикл 5 (шесть критиков, контроль v1.4) (→ v1.5)

Вердикты всех: «принять с правками», КРИТ нет; 4 СРЕДН (одна — упорядочивание затравки,
найдена независимо четырьмя критиками) + ~9 НИЗК; верифицированы координатором — приняты все.
Простота: затравка-дельта подтверждена минимальной формой (тумбстоуны не покрывают телепорт
наблюдателя и смену пространства — потребовали бы второго механизма). Альтернативы: доминанты
нет; баланс «направление ≥ шарды» восстановлен (бэрст-цена v1.3 умерла).

| # | Замечание (оптика) | Решение |
|---|---|---|
| 1 | [Б,КК,ПР,А СРЕДН] порядок «затравка ↔ активация RC» не прошит: приоритетная полоса + bounded-drain допускают «владелец есть, затравки нет» → фантомы K\M и дубли; при повторном переезде до потребления — затравка ∅ | ось 1: затравка едет в том же контрольном письме, что и сигнал активации (одно письмо); гейт применения — флаг-состояние (И6): без затравки не эмиттить и не мигрировать; непотреблённая пересылается следующему владельцу как есть; таймаут непотребления — алерт; кейсы — в тесты фазы 4 |
| 2 | [ПК СРЕДН] безусловное удаление K\M противоречило hold-last (член с маркером переезда) | ось 1: удаления K\M — по семантике оси 4 (маркер → hold-last); кейс в тесты фазы 4 |
| 3 | [П СРЕДН] очередь энкод-стадии не декларирована lossless — дроп кадра = вечная невидимость/фантом (в v1.3 самолечилось рефрешем, в v1.4 — нет) | ось 1: энкод-очередь lossless до disconnect; коалесинг только в compose; backpressure = TCP + порог disconnect в тиках; метрика глубины/латентности compose→socket |
| 4 | [КК,ПР,ПК] домен ключей K не назван (слуги/предметы выпадали); «известных клиенту» ≠ «доставленных» (in-flight) | ось 1: K = view set RB на флипе (включая in-flight); ключи — единое пространство join (entity-ID, (ownerID,slot), лёгкий класс) |
| 5 | [ПК НИЗК] выравнивающие апдейты занижены («чуть сверх нормы») — худший случай O(\|K∩M\|) (обязательные события не повторяются) | ось 1/«Цена»: до O(\|известных\|) в худшем случае; режется бюджетом (фаза 6) |
| 6 | [П НИЗК] единственная счётно-проходимая форма LOS не названа (пер-парный raycast = секунды/тик) | ось 4: ячейко-парная предвычисленная таблица (O(1) lookup); пер-парный raycast на тиковом пути запрещён |
| 7 | [Б НИЗК] «апдейты L2 абсолютны» — непроверенная посылка | OQ-7 (референс реестра knownlist-пакетов, фаза 3) + кейс «K∩M без ре-спавна» в фазу 4 |
| 8 | [А НИЗК] якорь стены считался по скан-константе, компоновка тоже квадратична | «Проверка»: стена по полной константе ≈1000–1700 |
| 9 | [ПК НИЗК] энкод-стадия выпала из P0.9-карты; [А НИЗК] §5-1/v1.4-неточность и «в мире шардов затравки нет»; [ПК] §5-12 seqlock-формулировка противоречива | «Последствия» → P0.9 + энкод-стадия; §5-1 уточнён (v1.3/v1.4, клауза шардов); §5-12 переформулирован |

### Цикл 6 (контрольный) (→ v1.6) — СХОДИМОСТЬ

Производительность, альтернативы, конкурентность: «принять», **замечаний не осталось**
(конкурентность: однописьменная затравка легла на третий хоп §5 ADR-0003 без TOCTOU; гейт —
законная идиома И6; альтернативы: доминанты нет, баланс «направление ≥ шарды» подтверждён
независимым пересчётом). Безопасность и план — по одному НИЗК, простота — одно упрощающее
СРЕДН; все три верифицированы и внесены:

| # | Замечание (оптика) | Решение |
|---|---|---|
| 1 | [ПР СРЕДН] гейт-кластер (флаг, «непотреблено», пересылка «как есть», таймаут) — четыре микро-сущности, устраняемые той же однописьменной конструкцией | ось 1: затравка применяется атомарно письму активации (view set := K); эмиттер-владелец возникает только этой обработкой — «эмиттить без затравки» непредставимо; повторный переезд = обычный хэндофф (затравка = view set = K) |
| 2 | [Б НИЗК] направление консервативности LOS-таблицы не зафиксировано (аппроксимация могла течь в сторону утечки) | ось 4: таблица консервативна — спорное = скрытие; ошибка только в сторону недовыдачи |
| 3 | [ПК НИЗК] «Цена» не согласована с осью 1 по выравниваниям | «Цена»: до O(\|известных\|) в худшем случае, режется бюджетом; типичный случай — dirty-потоком |

**Итог ревью-цикла ADR-0004:** шесть оптик × четыре цикла; динамика КРИТ/СРЕДН:
1К+11С → 3С+5Н → 4К+4С (один класс) → 4С(один класс)+9Н → 0 (три оптики чисто) → 0 КРИТ/СРЕДН,
остаточные НИЗК внесены. **ADR-0004 v1.6 готов к акцепту владельца.**

### Независимый аудит (3 свежих агента, без истории циклов) (→ v1.7)

По требованию владельца (подозрение «натягивания реализации под ревью») ADR передан трём
независимым агентам: ревизор patch-on-patch, конкурентный проектировщик (спроектировал своё
решение до чтения ADR), аудитор выброс-теста (22 механизма). Сводка вердиктов:

- **Конкурентный проектировщик:** строго доминирующей архитектуры нет; его независимый дизайн
  сошёлся к тому же скелету (владелец-наблюдатель, pull из снапшотов, дедуп+эпохи+hold-last,
  бюджеты, лёгкий класс) — скелет навязан инвариантами; во всех расхождениях ADR лучше.
- **Ревизор:** архитектура целостна; натянут один кластер — граница v1.3 «не возить view set»
  (three цикла правок поверх); рекомендация — перевозка last-sent в базу или явное обоснование.
- **Аудитор:** 17 несущих, 3 удобства, 2 компенсации, мёртвых нет; динамика циклов — удаляющая.
  Одна неоправданная цепочка: dirty-дельты → {генерация+дозагрузка+кап+OQ-4} — источник дешевле
  компенсации.

Внесено в v1.7 (после верификации координатором — арифметика и референс-основания проверены):

| # | Находка (агент) | Решение |
|---|---|---|
| 1 | [Аудитор ТОП-1, Ревизор—косвенно] dirty-дельта-пейлоады порождали механику дозагрузок (генерация+last-read+resync+кап+OQ-4) — три механизма чинили одну экономию | ось 3 инвертирована: **полные пейлоады + dirty-манифест**; пропуск поколений безвреден по построению; дозагрузка/кап/OQ-4 удалены; дельты — фаза-6-оптимизация; цена (+~320 КБ/тик memcpy на горячем регионе ≈ 30–50 мкс) записана |
| 2 | [Аудитор ТОП-2] LOS в предикате репликации — три обязательства (таблица, консервативность, позиция-вход) ради расширения, которого живой L2 не делает (известность дистанционная) | ось 4: гео-LOS — документированное исключение (живёт в advisory: аггро/скиллы, per-кандидат raycast); гео-известность — только будущим ADR с обязательствами (позиция-вход+переоценка, консервативность); OQ-8 (референс дистанционности, фаза 3) |
| 3 | [Ревизор] OQ-7 держал корректность, будучи «качеством» | OQ-7 — блокирующий для фазы 4 (тест-детектор уже был); fallback — досрочная перевозка last-sent |
| 4 | [Ревизор] «перевозка last-sent в базу или явное обоснование» | явное обоснование трейд-оффа в оси 1 (бёрст редок/дёшев/режется бюджетом; last-sent — волатильный кеш, дрейфующий формат); в базу не поднимается без владельца |
| 5 | [Ревизор, Аудитор ТОП-3] join-доля — не warning-шум: сериализация join в одной горутине — единственное место упора направления | «Проверка»: синтетический join-бенч в фазу 3 (до постройки стека), join-доля — первоклассный датчик с фазы 4 |
| 6 | [Проектировщик (б)-1/(б)-2] encode-once предсериализация broadcast-пакетов; пер-ячеечный мягкий кап предметов | «Последствия» → фаза 6: оба — разрешённые эволюции |

Отклонено ничего; занесено всё. Подозрение «натягивания» подтвердилось частично и локально:
ровно одна цепочка (находка №1 — выбор самого первого черновика, обросший тремя костылями)
— удалена в источнике.
