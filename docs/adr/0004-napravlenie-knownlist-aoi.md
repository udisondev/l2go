# ADR-0004: Направление knownlist/AoI — ячеечная репликация у владельца наблюдателя

**Статус:** draft (v1.2 — правки циклов 1–2 ревью, §7; ждёт акцепта владельца). Уровень —
**направление**, не детальный дизайн: выбираются механика подписки, форма снапшота, владение
outbound-состоянием и ограничители частоты; размеры ячеек, радиусы, числа троттлинга, формат
пакетов Interlude — фазы 2–6.

## Контекст

«Проблема города» — убийца №1 по CPU в r0: n игроков в точке взаимной видимости → O(n²)
fan-out апдейтов. Форма её решения определяет форму снапшотов и весь AoI-слой (r2 §Открытые
вопросы п.2 — единственный TODO r0 без дизайна). Входы:

- r0: три несмешиваемых слоя — симуляция (владение по регионам) / видимость (AoI, пересекает
  границы) / non-spatial сервисы; видимость ≠ владение; снапшот = иммутабельная публикация +
  atomic swap.
- r2: GC-давление снапшотов (per-entity против per-owner блоба; публиковать dirty, а не весь
  мир каждый тик); сетевой backpressure (outbound-бюджет на клиента под бродкаст-лавиной);
  knownlist обязана иметь минимальную реализацию в walking skeleton (фаза 3) и тюнится ботами
  (фаза 6).
- r3 §3: канонический механизм видимости — чтение снапшота соседа (ghost-реплики отдельным
  механизмом не строятся); ID переживает хэндофф → меняется источник данных, не видимость;
  дедуп по entity-ID.
- ADR-0003 (принят, §16 — прямые требования к этому ADR): AoI = соединение потоков с
  ограничителями частоты; дедуп по entity-ID **и** composite-ключу слуг `(ownerID, slot)`
  (слуги публикуются в `servants[]` снапшота хозяина под стабильным протокольным objectId,
  трупы слуг — там же); выбор источника при двойной публикации в окне переезда — по max-epoch;
  **hold-last** (источник старой эпохи держится до появления новой — анти-мигание); снапшот-типы
  инкапсулированы в модуле репликации; advisory-чтения логируются в порцию (D4), репликация к
  клиенту входом свёртки не является.

## Решение

Шесть осей; по каждой зафиксирован выбор, детали — своим фазам.

### 1. Кто вычисляет видимость: регион-владелец наблюдателя

Knownlist игрока P и его исходящий поток собирает регион-владелец P — тот же, кто читает ящик P
и компонует его клиентские пакеты. Отдельных репликационных акторов/пула нет: outbound-поток —
состояние мира, а состояние мира трогает только горутина-владелец (инвариант 7 / ADR-0002;
пассивность черновика — И8 ADR-0003). Изоляция нагрузки — топологией: толпа топит только свои
регионы (та же логика, что у осады в r0).

Per-observer **view set** («кого клиент уже знает» + last-sent для дельт) и текущая подписка
ячеек — поля состояния наблюдателя: едут в чемодане при хэндоффе (ADR-0003 §5), новый владелец
продолжает с того же множества — у наблюдателя нет мигания knownlist на его собственных
переездах. View set/last-sent — **outbound-состояние**: читается только репликационным слоем;
игровой логике недоступен (геймплейные решения о видимости — только через advisory-API с
логированием, D4); в бит-в-бит реплей не входит.

**Замороженный наблюдатель** (окно хэндоффа самого наблюдателя): с момента упаковки чемодана
его view set неизменен (состояние уже в чемодане, И3), но наполнение его исходящего не
останавливается до флипа — RB (владелец до флипа) продолжает join-рассылку **в обход view set**
и **не вводя клиенту новых объектов**: только апдейты и удаления уже входящих во view set
(односторонний learn исключён — конвергенция с view set гарантирована; новые объекты клиенту
вводит RC после разморозки). От флипа до первого тика RC наполнение стоит (≤1–2 тика), затем RC
продолжает от view set чемодана, при первом тике посылая рефреш — **повторные спавн-пакеты
известных objectId без предварительного DeleteObject** (повторный спавн клиент обрабатывает как
обновление, не ре-спавн — L2J-практика повторных CharInfo/NpcInfo; проверка по живому клиенту —
OQ-5): мигание известности исключено. Обязательство «исходящий буфер самому замороженному жив»
(ADR-0003 §5) исполняется так: конвейер и наполнение живы у RB до флипа. Механика окна и её
профильный тест — фаза 4 (вместе с хэндоффом); идемпотентность спавн-пакетов как свойство
формата — фаза 1+.

### 2. Механика подписки: глобальная сетка ячеек мельче региона

Сетка AoI-ячеек глобальна и выровнена глобально (не по границам регионов). Правило размера:
ячейка ≥ радиуса обзора; подписка наблюдателя — **константный стенсил ячеек вокруг его ячейки**
(3×3 при ячейке, равной радиусу); «2×2…3×3» — оценка фактического покрытия круга, не размер
подписки. Сущности крайних ячеек стенсила за пределами радиуса отфильтровываются предикатом
видимости (ось 4) — смена подписки не мерцает. Точный размер ячейки — фаза 6 по метрикам.

- Сущность публикуется **своим владельцем** в ячейку своей позиции; ячейка на стыке регионов
  просто имеет сущности от нескольких издателей — конфликта нет: каждая сущность публикуется
  ровно одним регионом (своим), ячейка — ключ подписки, не владелец.
- **Реестр издателей ячейки — статическая функция геометрии регионов основного мира с запасом
  на R_leash слуг** (ADR-0003 §6: leash ≤ глубины читаемых снапшотов): покрывает и
  издателей-негеометров — регион-владелец хозяина публикует запись слуги в ячейке позиции слуги
  (ось 3). Реестр остаётся статическим (геометрия + константа leash), динамических реестров нет;
  сегментация блоба удерживает цену чтения — читается только нужный сегмент. Инстансы и олимп
  публикуют в **собственные пространства ячеек** (координаты переиспользуют мировые — без
  разделения наблюдатели основного мира получали бы призраков). Осада Interlude — событие
  открытого мира (зрители на холмах, торговцы у стен): пока осада в открытом мире, у неё
  отдельные диспетчер и бюджет (r3 §1), но публикация — в общую сетку; отдельное пространство —
  только если будущий ADR переведёт осаду в инстанс.
- Наблюдатель подписан на стенсил вокруг своей ячейки; смена подписки — только при пересечении
  границы ячейки самим наблюдателем. Membership известности меняется событийно (пересечение
  границ, спавн/деспавн в ячейках подписки), а не пересканированием толпы каждый тик; детект
  изменения членства обязан стоить O(#ячеек подписки) — генерация членства в заголовке ячейки
  либо события членства в dirty-потоке (требование к детальному дизайну фаз 3–4).

### 3. Форма снапшота: per-owner SoA-блоб, сегментированный по ячейкам, dirty-марки

Регион в конце тика публикует **один** иммутабельный блоб (свап указателя, r0) с SoA-сегментами
по ячейкам. Внутри тика записи помечаются dirty; блоб несёт полный заголовок членства по ячейкам
(дёшево читать состав, включая явные маркеры ухода — ось 4) и dirty-пейлоады (дельты).
Свап происходит каждый тик — advisory-потребителям (range-чек удара, r3 §3) нужна свежесть
последнего завершённого тика издателя (при дропнутых тиках издателя блоб стареет на N тиков —
норма коалесинга ADR-0002). Экономия достигается dirty-содержимым, а не пропуском публикации.
**Аллокация:** по умолчанию блоб аллоцируется заново на каждый тик (1–2 аллокации на регион-тик
— на порядки меньше per-entity); переиспользование/пул — оптимизация фазы 6, требующая
дисциплины поколений (старая версия живёт до выхода последнего читателя, а время удержания
читателя в модели без барьера не ограничено — свободный reuse = data race). Дозагрузка полного
состояния ячейки при новой подписке (версионированные сегменты / периодический полный кадр /
полный кадр по запросу) — детальный дизайн фазы 3–4.

Per-entity снапшоты (свой atomic-указатель на запись каждой сущности) отвергнуты — ось закрыта.

Слуги — в блобе хозяина (`servants[]`, стабильный протокольный objectId), включая трупы (смерть
≠ деспавн). Запись слуги публикуется в сегмент ячейки **позиции слуги**: источник данных — блоб
хозяина, пространственный ключ — сам слуга (пет, отбежавший от хозяина, — обычный сценарий L2:
он виден и таргетируем там, где стоит).

**Предметы на земле и прочие динамические мировые объекты** (дроп с мобов, брошенное, осадные
флаги) — полноценные AoI-записи лёгкого класса: статичная позиция, itemID, count; публикуются
регионом-владельцем в ячейку позиции той же механикой (spawn/despawn/churn лута — обычные
события членства). Предмет — **не сущность транспорта**: decay/время жизни/владение — состояние
региона-владельца позиции (по образцу спавн-таймеров, ADR-0003 §3); подбор — только transfer
против владельцев персонажей (И9 не ослабляется); класс адресации — P0.10.

### 4. Join: дедуп, окно переезда, предикат видимости

Сбор видимости = union ячеек подписки из снапшотов издателей (до 9 регионов), с дисциплиной:

- **Дедуп:** entity-ID для сущностей; `(ownerID, slot)` для слуг. Сущность с уникальным ID
  встречается в снапшотах нескольких издателей только в окне переезда (замороженная копия у
  старого vs живая у нового) — источник выбирается по **max-epoch**. Эпоха сущности
  инкрементируется атомарно с флипом (ADR-0003 §5 шаг 6 — точка завершения переезда): первая и
  все последующие публикации нового владельца несут строго бо́льшую эпоху, чем замороженная
  копия старого; публикация одной сущности двумя издателями с равной эпохой — инвариантное
  нарушение (алерт), тай-брейком не разрешается.
- **Семантика ухода из заголовка членства — три случая:** (i) деспавн — явный маркер удаления;
  (ii) уход хэндоффом — маркер переезда у издателя: это и только это триггерит **hold-last**
  (держим последнее известное состояние до публикации нового владельца по max-epoch или таймаута
  бюджета хэндоффа в тиках, D1 — нет delete→spawn-мигания на стыке); (iii) пропажа без
  маркеров — обычный выход из обзора (движение, телепорт) — немедленное удаление у клиента, как
  DeleteObject при телепорте в живом L2 (проверить по референсу, OQ-6). Фантом на таймаут
  хэндоффа от телепортировавшегося — исключён конструкцией.
- **Видимость = предикат пары (наблюдатель, цель):** позиция ∧ флаги цели (инвиз/GM/
  скрытность — за флаги авторитетен владелец цели в момент публикации) ∧ атрибуты наблюдателя
  (право видеть скрытое — GM; детект-скилл в Interlude — проверить по референсу). Предикат
  расширяем LOS-проверкой по geodata (гео-известность «за холмом») — детализация фаз 2+,
  стоимость canSee на join — фаза 4–6. Смерть ≠ исчезновение (труп виден до деспавна,
  ADR-0003 глоссарий).

У join два потребителя с разной дисциплиной (граница закреплена D4 ADR-0003):

- **репликация к клиенту** (оси 1, 5) — выходной поток, в лог порций не входит, свёртку не
  влияет;
- **advisory-запросы геймплея** (аггро-скан моба, range-чек, перечисление целей AoE) — вход
  свёртки, только через advisory-API модуля репликации с логированием.

Один субстрат (ячейки + снапшоты), два потребителя; радиусы у них разные (обзор клиента против
аггро-радиуса моба) — это разные подписки на ту же сетку, не два механизма.

### 5. Ограничители частоты: LOD-тиры + per-client outbound budget

«Город» ограничивается на исходящем, не на членстве:

- **LOD-тиры по расстоянию** — политика на весь исходящий поток пары (наблюдатель, цель), не
  только на позиции: ближним — полный темп; дальним — позиция с пониженной частотой (клиент
  интерполирует), непозиционные события — по классу события (реестр обязательных к доставке —
  смерть→труп, деспавн, смена статуса витрины — фиксируется в фазе 2). Тир пересчитывается при
  пересечении границы тира.
- **Per-client outbound budget** (закрывает backpressure из r2), выражается в тиках —
  пакетов/тик, байт/тик (D1: настенные часы вне шлюза не вводятся). При дефиците —
  детерминированный приоритет; порядок «спавн/деспавн > близость > свежесть > ID» — настраиваемый
  дефолт (состав классов и детерминированность — направление; порядок — тюнинг фазы 6), плюс
  коалесинг позиций (побеждает последняя) и батчинг (один пакет несёт много апдейтов).
  Детерминированность приоритета нужна для тестируемости и анти-мерцания, не для реплея.
- **Гистерезис** на границах тиров, бюджета **и членства**: вход в knownlist по меньшему
  радиусу, выход по большему (в ячеечной форме — enter с запасом против exit) — иначе бег по
  дуге на краю обзора = осцилляция spawn/despawn; числа — по референсу (aCis/L2J KnownList),
  фаза 2.
- **Жёсткий кап численности knownlist** — аварийный клапан за конфигом, по умолчанию выключен:
  честный режим — не капать членство (социалка города), а капать темп.

### 6. Минимальная экспозиция (фаза 3) и датчик финальной настройки (фаза 6)

Walking skeleton: один регион, одна ячейка, без LOD/бюджета — join вырождается в «все сущности
региона», но владельческая дисциплина, блоб, маркеры удаления и предикат видимости — те же.
Вся детализация (размер ячейки, границы тиров, числа бюджета, порядок приоритетов) — фаза 6 по
измерениям ботов; датчики и сигналы пересмотра — в «Проверке решения».

## Отвергнутые альтернативы

1. **Отдельный слой репликации (AoI-акторы/пул).** Вторая точка владения outbound-состоянием,
   новая конкурентная структура; прикладной пул для состояния мира запрещён (инвариант 7).
   Изоляция нагрузки уже обеспечивается топологией регионов; если фаза 6 докажет обратное —
   пересмотр новым ADR (см. «Проверку решения»).
2. **Push издателя в чужие клиентские буферы** (владелец сущности сам рассылает апдейты
   наблюдателям). Кросс-региональная запись в состояние чужого наблюдателя — нарушает
   single-writer (инвариант 1) и адресацию ADR-0003.
3. **Per-entity снапшоты.** GC-давление (десятки тысяч короткоживущих аллокаций на тик) и
   промахи кеша против одного блоба на регион; вопрос r2 закрыт (ось 3).
4. **Подписка регионами целиком (3×3 региона) как механика.** Membership поддерживается сканом
   популяции девяти регионов на наблюдателя; ячейки дают событийное членство. 3×3 остаётся
   верхней границей числа издателей в join, не механикой подписки.
5. **Ghost-реплики с собственной симуляцией / двойная симуляция соседа.** Отвергнуто r3 §3:
   ghost = снапшот; симулирует один владелец.
6. **Жёсткий кап knownlist как основной механизм.** Ломает видимость города (социалка, торг);
   кап — только аварийный клапан (ось 5).
7. **Троттлинг публикации снапшотов (реже тика).** Ломает свежесть advisory (range-чекам нужен
   последний завершённый тик издателя, r3 §3); троттлится исходящее к клиенту, не публикация.

## Последствия

- **P0.9:** в карте компонентов появляется модуль репликации/AoI (снапшот-типы, ячеечная сетка,
  advisory-API — снапшот-типы инкапсулированы там по ADR-0003 §16); библиотека внутри регионов,
  собственных горутин не имеет.
- **P0.10:** в таксономию добавляется класс исходящих (outbound) сообщений клиента с декларацией
  очереди-бюджета (единая декларация очередей ADR-0003 §4); в модель сущности явно входят view
  set (членство + last-sent) и текущая подписка ячеек — часть пейлоада хэндоффа «всё состояние».
- **Фаза 2:** реестр обязательных к доставке событий; числа гистерезиса членства и детект-
  семантика инвиза — по GPL-референсам.
- **Фаза 3:** knownlist walking skeleton — вырожденная конфигурация той же механики (ось 6),
  не отдельный throwaway-код.
- **Фаза 4:** снапшоты и advisory уже потребляются боем; join-стадия входит в бюджет шага
  региона (метрика — отдельно); здесь же — механика окна хэндоффа наблюдателя (обход view set
  у RB, рефреш после разморозки) и её профильный тест (ось 1).
- **Фаза 6:** тюнинг ячейки/тиров/бюджетов; допустимая эволюция формы публикации (dirty-блоб →
  дифф-потоки, пул с дисциплиной поколений) не меняет направления — это не владение и не
  подписка.
- **Не влияет:** пати-окно (UI-подписка по partyID, r3 §4), чат/клан/маркет (non-spatial
  слой), статические объекты мира (датапак по позиции — не поток; динамическая геометрия —
  отдельный открытый вопрос r2).

## Цена решения

- Join-работа живёт в тике региона-владельца наблюдателя: городской регион платит за свою толпу
  (изоляция — фича, но и концентрация: центр Адена — горячий регион; лечится бюджетом оси 5,
  не переездом работы).
- View set — состояние наблюдателя: чемодан тяжелеет на размер knownlist (сотни записей
  last-sent; пренебрежимо против инвентаря, но это цена переездов в толпе). Плюс окно
  хэндоффа наблюдателя требует идемпотентных отправок и рефреша после разморозки — профильный
  тест фазы 4 (вместе с хэндоффом).
- Глобальная ячеечная сетка — ещё одна структура с дисциплиной (выравнивание, размер, границы,
  отдельные пространства инстансов) и ещё один источник событийности (пересечения границ
  ячеек) — код, который надо написать и протестировать; вырожденная конфигурация фазы 3 её
  не отрабатывает.
- Исходящий поток недетерминирован по времени **и побайтовому составу** (батчинг по бюджету,
  интерливинг свапов издателей): реплей воспроизводит серверную свёртку бит-в-бит (D1–D6),
  но не исходящий поток — golden-тесты фаз 1+ кладутся на свёртку и кодек, не на outbound.

## Проверка решения

Фаза 6, сценарий «город»: 100/300/1000 ботов в радиусе взаимной видимости + контрольный «лес»
(равномерное рассеяние). Метрики-датчики:

- p99/p999 шага региона и доля join-стадии в нём (профилированием) при 10 Гц;
- пакеты/тик и байты/тик на клиента против бюджета; доля коалесированных позиций;
- аллокации/с и GC-паузы на публикацию блобов;
- p99 размера view set и churn membership на пересечении границ ячеек.

Сигналы пересмотра **направления** (не только чисел): join-стадия устойчиво >30% бюджета
горячего региона; membership-churn доминирует над dirty-работой; коалесинг съедает большинство
позиционных апдейтов (тиры настроены грубее, чем нужно). Фальсификатор: если при 1000 ботах в
точке p99 шага не лезет в бюджет ни при каких числах оси 5 — направление «join у владельца
наблюдателя» пересматривается новым ADR; кандидат-запас — репликационные шарды с собственным
бюджетом (альтернатива 1, сегодня отвергнута).

## Открытые вопросы (в свои фазы)

1. Труп пета при уходе/рессе/телепорте хозяина — проверить по референсу (aCis
   L2PetInstance.doDie → decay); фаза 2.
2. Детект-семантика инвиза в Interlude (есть ли не-GM детект) — референс; фаза 2.
3. Числа гистерезиса членства (радиусы enter/exit) — референс aCis/L2J KnownList; фаза 2.
4. Дозагрузка полного состояния ячейки при новой подписке — версионированные сегменты /
   периодический полный кадр / по запросу; фазы 3–4.
5. Идемпотентность спавн-пакетов (повторный спавн = обновление, не ре-спавн) — свойство формата,
   фаза 1+; рефреш после разморозки без DeleteObject и механика окна хэндоффа наблюдателя —
   фаза 4 (вместе с хэндоффом).
6. Мгновенность удаления из известности при телепорте (DeleteObject в L2J TeleportToLocation) —
   референс; фаза 2.
