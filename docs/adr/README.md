# ADR — архитектурные решения

Каталог решений (Architecture Decision Records). Правило слоёв проекта: `research/` отвечает
«почему так» (теория), `план/` — «что и в каком порядке делаем» (исполнение), `docs/adr/` —
«что решили и какой ценой». При конфликте победитель — самый свежий accepted-ADR; r0–r3
читаются как его предыстория.

## Когда нужен ADR (любой из трёх триггеров)

1. Решение **коснётся больше одного пакета** (например, формат снапшота, который читают соседи).
2. Решение **фиксирует конкурентную модель или владение данными** (кто и где мутирует состояние).
3. Решение **необратимо без переделки** (менять дороже, чем решить заранее).

Не нужен ADR: локальная реализация внутри одного пакета, не влияющая на границы.

## Процесс

1. Следующий свободный номер: `NNNN-слаг.md` (0001–0003 заняты).
2. Статусы: `draft` → `accepted` → `superseded` (только в таком направлении).
3. Изменить суть принятого решения = **новый** ADR со ссылкой на старый; старый переводится в
   `superseded` и по существу не редактируется.
4. Решение, влияющее на поведение агентов, дублируется в `AGENTS.md` (агенты читают его первым).
5. ADR-нумерация не обязана быть сплошной: номер резервируется за темой (0001 — лицензия,
   0002 — модель тика, 0003 — доставка/владение при хэндоффе, 0004 — knownlist; см. план/p0.md).
