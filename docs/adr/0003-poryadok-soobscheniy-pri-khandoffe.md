# ADR-0003: Доставка сообщений при хэндоффе — эпохи + пер-сендерная последовательность

**Статус:** draft (v8 — после семи циклов ревью; правило завершения: до отсутствия замечаний;
отвергнутые фиксируются в §11).

## Контекст

Окно хэндоффа сущности между регионами допускает потерю, дублирование и переупорядочивание
сообщений к ней. Критические сценарии: трейд-2PC на бегу через границу (дюп); причинные цепочки
боя (стан → нук). Требования: граница маскируется интерполяцией и лагом (микролаги допустимы,
паттерн — нет); бой через границу — горячий путь (PvP-кайт, осадная стена); регионы-акторы,
single-writer, каналы надёжны (in-process), один процесс. **Несущие предположения из r0/r3:**
гистерезис границы; тик-модель ADR-0002 (флип — блок в тике актора, никто никого не ждёт).

## Решение

Два механизма: **эпохи** — «куда доставлять» (маршрутизация, at-most-once), **пер-сендерная
последовательность (seq)** — «в каком порядке применять» (упорядочивание, дедуп). Оба — в общем
транспортном компоненте (P0.9/P0.10), одна реализация для всех отправителей: регионы, сервисы,
gateway. Инвариант уровня AGENTS: **каждый отправитель — только через транспорт; сырой
channel-send мимо конверта ломает гарантии.**

### 1. Директория и конверт

- Директория (read-mostly): `id → {owner, epoch, domain}`. Эпоха растёт на каждой смене
  владельца: хэндофф, телепорт (GK/BSoE/Party Recall/Summon Friend), вход/выход
  инстанса/олимпа/фестиваля, логаут/деспавн. **Смерть владельца не меняет — не эпоха.** Записи
  не удаляются (tombstone `{owner=nil, epoch}`); **ID сущностей никогда не переиспользуются**.
- **Все флипы директории — CAS по паре {owner, epoch}** (нормальный хэндофф, флип-назад при
  ре-адопции, relocating): флип применяется только если текущая запись совпадает с ожидаемой.
  Провал CAS = владение уже перешло иначе = инициатор ничего не пишет и узнаёт новое состояние.
  Это единое правило, закрывающее цепочки владения в окне неподтверждённого ack (§3 recovery).
- Конверт: `{to, fromID, returnTo, epoch, seq, class, payload}`. `fromID` — **стабильный ID
  источника**: сущность, сервисная **шарда** (шардированный сервис адресуется шардой, не
  сервисом — иначе интерливинг счётчиков под одним fromID), gateway. `returnTo` — регион-якорь
  для возвратов/NACK (маршрут, не ключ). Пула конвертов нет (отвергнуто, §11-6).
- Outbox per (отправитель → цель): монотонный `seq` **u64**; счётчик вечен (GC чистит записи,
  не счётчики); запись о последней отсылке удерживается ≥ окна T_recover (для маршрутизационной
  пересылки «тот же seq»). Outbox — состояние отправителя: у сущности едет в её Adopt, у
  сервиса/шарды живёт в акторе вечно.

### 2. Приём: последовательность = состояние сущности

- Владелец держит `inSeq: {fromID → lastApplied}` — состояние сущности, едет в Adopt.
- `seq == expected` → применить; `seq > expected` → гэп → reorder-буфер (per-source, ограничен;
  переполнение → форс-декларация старшего гэпа мёртвым + алерт); `seq < expected` → дубль → дроп.
- **T_reorder — ассерт:** незакрываемый гэп = баг транспорта; скип = инцидент. Пропуск объявляется
  мёртвым только как финальный дроп с политикой класса (§5) и уведомлением; диапазон пропуска
  объявляется явно (в т.ч. при ре-адопции — см. §3 recovery). Инвариант: `expected` пересекает
  seq только применением или явным скип-с-уведомлением.
- Обработчики reliable/transfer идемпотентны по `(fromID, seq)` на входе. Стационар: одно
  сравнение, ноль аллокаций.
- Resync после idle-GC `inSeq`: якорь на max пришедших.

### 3. Хэндофф: флип на стороне источника

RB одним последовательным блоком в тике:

```
1. B.migrating = true; входящие для B → очередь B
2. payload = per-member {state, очередь, inSeq, outbox, dirty-флаги}
   компаунд: ЖИВЫЕ петы/саммоны (см. инвариант ниже)
   relocating-сообщения очереди резолвятся источником ДО отгрузки; резолв проходит ту же
   валидацию, что применение (инвентарь, кулдаун-журнал, состояние — атомарно у источника):
   нецелевой резолв → отмена эффекта с уведомлением по классу доставки, сущность отгружается
   в геометрический пункт как обычная
3. ФЛИП (CAS) директории: {RC, epoch+1} — для каждого члена компаунда в том же блоке
4. send Adopt → RC (канал FIFO); паника до send → повтор блока безопасен (CAS + идемпотентный
   install + мерж holdback по seq)
5. tombstone {B → RC@epoch} + замороженный B в снапшоте RB до install-ack
6. замороженная копия у RB до install-ack
```

Приём на RC:

```
- сообщения для B до Adopt → holdback (per-entity)
- install: идемпотентен по {id, epoch} + СВЕРКА С ДИРЕКТОРИЕЙ (owner==RC && epoch)
- replay очереди БЕЗ epoch-чека; holdback мержится всей линией по seq
- исходящие эффекты, порождаемые replay (KillCredit при смерти в replay и т.п.), складываются
  в буфер отложенных эффектов — часть install-контекста: flush при install-ack, discard при
  погашении ветви
- send install-ack → RB; RB убирает B из снапшота, забывает копию; B симулируется и порождает
  эффекты только после ack
```

- **Страгглеры:** tombstone-forward (перештамповка epoch на текущую, seq сохраняется).
- **Holdback-GC:** только когда владение B ушло из RC (сверка/Invalidate); перед NACK —
  консультация с директорией (защита от истёкшего tombstone).
- **Recovery (watchdog T_recover = 2–3 с):** нет ack → RB пытается **флип-назад CAS
  {RC@e+1} → {RB@e+2}**:
  - **CAS провалился** — владение ушло дальше по легитимной цепочке (RC успел установить и
    перегрузить B): линия жива, RB забывает копию, ничего не инвалидируется;
  - **CAS прошёл** — никто с момента флипа RB владение не менял: RB ре-адоптирует B и шлёт
    `Invalidate{B, deadEpoch}` **вытесненному владельцу ветви deadEpoch** (из результата CAS);
    RC гасит ветвь, **ответ на Invalidate несёт финальные inSeq И outbox погашенной ветви**
    (входящий и исходящий прогресс): RB объявляет диапазон `[frozen+1 .. finalIn]` мёртвым
    через механизм скип-с-уведомлением по классам (без переполнения reorder-буфера и без ложного
    T_reorder) и **подтягивает свои outbox-счётчики до max(свои, ветви) до разморозки** — новые
    исходящие пойдут с finalOut+1, окна повторного использования seq (тихий дроп-как-дубль) нет;
    сверка с журналом transferID мёртвой ветви — тоже до разморозки.
  - **Провал CAS = ответственность у watchdog'а следующего звена** (линия жива, у каждого звена
    своя копия до своего ack). Осознанный предел one-process: одновременная вечная заморозка
    двух соседних звеньев = потеря B при отсутствии владельцев-симуляторов (дюпа нет) —
    инцидент-класс.
  - Поздний install-ack при новей эпохе — игнор + уже выполненный Invalidate покрывает.
  - Ответ на Invalidate имеет таймаут (B остаётся замороженным) + алерт — доступность, не
    корректность.
  - Встречная гонка «RB флип-назад vs RC начинает свой хэндофф»: оба — CAS по {owner, epoch},
    проходит ровно один; проигравший узнаёт провал и гасит/забывает свою ветвь. Residual-окно
    (мс) до гашения: исходящие эффекты — «произвольный первый» при дубле эмиссии (не аддитивность),
    дедуп (fromID, seq) ловит дубли в пределах одной ветви, межветвевые — журнал transferID
    (предметы) и инцидент-алерт (остальное).
- **Компаунд = отношение владения для ЖИВОГО слуги:** живой пет/саммон всегда поездом хозяина
  (свои state/queue/inSeq/outbox/флип в одном блоке); один пет на носителя; отдельной миграции
  и гистерезиса пета нет. **Смерть слуги расстаёт компаунд:** труп — обычная сущность своего
  региона (хэндофф по геометрии, видимость через снапшоты, ресс — через директорию).
  **Ресс слуги переприсоединяет к поезду — правилом замыкания, а не одиночным хопом:**
  воскресший слуга до подключения — обычная геометрическая сущность; ресс инициирует хэндофф
  (та же CAS+Adopt машина) **телепорт-класса** — позиция слуги переносится к хозяину (прецедент
  L2: Return/Summon Friend), не только владение. На install прибывший слуга **перечитывает
  запись хозяина**: хозяин в другом регионе → ре-инициация хоп-погони (сходится к текущему
  региону хозяина, ритм ограничен cooldown); запись — tombstone (хозяин офлайн) → слуга остаётся
  геометрической сущностью своего региона. **Драйвер переприсоединения — reconcile
  «roster × директория», симметричный по сторонам отношения: триггер — любое событие владения
  любой из сторон** (ресс слуги; install прибывшего слуги; логин хозяина; ре-адопция хозяина
  или слуги — замороженная копия предшествует attach, отвязавшие возвращаются в погоню;
  гашение ветви хозяина или слуги (Invalidate)). Погоня — свойство состояния слуги
  («незакреплён, жив, хозяин известен»), а не одноразовый драйвер: reconcile восстанавливает
  её из этого состояния на любом триггере. Смерть хозяина при живых слугах и логаут-деспавн
  поезда — механически безопасны (поезд статичен / флип одного блока);
  фиксируются фразой здесь, чтобы не разбирать заново.
- **Per-entity handoff cooldown:** минимальный интервал между геометрическими хэндоффами
  сущности (гасит зигзаг-кайт); **cooldown < T_recover** (watchdog старше, не конкурирует со
  свежими отгрузками); recovery-флип-назад cooldown'у не подлежит (это не геометрический
  хэндофф); cooldown ≪ пробега региона за секунды (сотни мс).
- **Нагрузка:** контрольные сообщения — приоритетной полосой мимо drain-капа с собственным
  бюджетом; Adopt'ы тика коалесятся (батчинг); метрики application-delay-p99 и freeze-p99.

### 4. Домены

`domain` в директории — формат сейчас, **политика — фаза 6**. Whitelist advisory — именованный
enum (стартово: HP/MP/CP-статусы пати-окна; будущие кандидаты — level члена пати-окна —
записаны, добавление правкой ADR), default deny; правило «advisory не содержит координат,
таргетов, баффов, инвентаря».

### 5. Классы доставки (полный реестр — таксономия P0.10)

| Класс | Поведение при финальном дропе | Примеры |
|---|---|---|
| fire-and-forget | молча дроп | урон, бродкаст |
| reliable-until-delivered | NACK владельцу отправителя (идемпотентно) + алерт | аггро, KillCredit, XP-доля, контроль-эффекты (стан/рут/фир/силенс/слип) |
| transfer | дроп = чистый abort 2PC | Reserve/Commit трейда, spoil/sweep-забор |

Финальный дроп ≠ 0 для reliable/transfer — инцидент-алерт. Ретраев у отправителя в стационаре
нет; маршрутизационный-NACK → переслать тот же seq; финальный дроп → компенсация по классу.

### 6. Персистентность (требование в фазу 5)

Пишет текущий владелец; записи состояния несут epoch (устаревшие дискардятся). **Журнал
transferID — вне эпохальной дисциплины** (ключ transferID; TTL ≥ k×T_recover); ре-адопция
сверяется с журналом мёртвой ветви до разморозки. Консервативность предметов — и через рестарт.

### 7. Гарантии (честные)

- **At-most-once на конверт.**
- **Exactly-once эффекта** = at-most-once + seq-дедуп + журнал transferID (включая recovery).
- **Per-sender FIFO структурно на всех путях** (прямой, replay, holdback, tombstone-forward,
  маршрутизационный пересыл), включая хэндофф и отправителя, и получателя; «с точностью до
  пропуска, объявленного мёртвым» — каждый пропуск = финальный дроп с уведомлением по классу.
- **Единственный владелец — инвариант на всех путях, включая recovery:** все флипы CAS по
  {owner, epoch}; двойная симуляция исключена, residual-мс до гашения оговорён.
- Мейлбоксы без потерь; капы — на обработку.
- Порядок между отправителями не гарантируется (OQ-2).
- Граница: freeze-p99 / application-delay-p99 бюджеты; **ре-адопция — это откат позиции к точке
  заморозки (видимый телепорт-назад до ~T_recover)** — редкое авария-классное событие,
  инцидент-алерт; формулировка «маскируется интерполяцией и лагом», не «незаметна абсолютно».

### 10. Открытые вопросы (не блокируют акцепт)

1. **Корабли/пассажиры** — кандидат ADR-0005.
2. **Взаимоубийство у границы**: порядок двух смертей не детерминирован — геймплейная
   приемлемость, фаза 4.
3. **Групповые relocating-бёрсты** (Party Recall, Festival, Rift) — метрики фазы 6.
4. **Death-drop у границы** — сверить при реализации фазы 5.
5. **Гварды**: регион-принадлежные, не мигрируют, преследование до leash-радиуса; проверить,
   что leash не выводит расстыковку за пределы AoI 3×3; политика — P0.10.

### 11. Отвергнутые замечания и отвергнутые варианты фиксов (реестр)

1. (цикл 1) «Forward сохраняет порядок» — неверно; forward безопасен благодаря seq.
2. (цикл 2) «Разрыв потока отправителя — оговорка» — заменено фиксом (вечный fromID).
3. (цикл 3) Фикс «не длиннее одного неподтверждённого звена» (запрет цепочек до ack) — отвергнут:
   избыточен при CAS-флипах; CAS проваливается ровно тогда, когда линия жива, и запрещать
   легитимные цепочки не нужно.
4. (цикл 3) Связка «cooldown ≥ T_recover» — отвергнута: наоборот, cooldown < T_recover
   (watchdog старше свежих отгрузок); recovery-флип cooldown'у не подлежит.
5. (цикл 3) «Деспавн-и-возврат-в-ошейник» мёртвого пета — отвергнуто: расставание компаунда при
   смерти слуги проще и не теряет труп (видимость, ресс).
6. (цикл 2) Пул конвертов — вычеркнут (преждевременная оптимизация, источник багов транспорта).

## Отвергнутые альтернативы

- **v1** (NACK-bounce, флип у приёмника) — порядок/выгорание (цикл 1).
- **v2→v3 recovery без CAS** — цепочки владения в окне ack (цикл 3).
- **Полный seq-TCP**; **forward без seq**; **drain-before-flip**; **запрет трейда при
  мигрирующем контрагенте** (только как fast-fail в 2PC); **синхронный хэндофф** — см. §11 и
  историю циклов.

## Последствия

- Транспортный компонент в карте P0.9; таксономия P0.10: классы, relocating, домен-политика,

- r3 §3 сценарий 1 — superseded.

## Цена решения

Транспортный слой: конверт, per-target outbox (u64, ретеншен ≥ T_recover), inSeq-карта (GC по
смерти/idle), reorder-буфер (ассерт), tombstone + holdback + Invalidate(+ответ с финальным
inSeq) + watchdog, приоритетная полоса с бюджетом, батчинг Adopt. Recovery-механики — реализация
фаза 4 (скелет фазы 3: конверт/outbox/директория-стаб/шов). **Настраиваемых ручек три:**
T_recover (2–3 с), freeze-бюджет p99, handoff-cooldown (сотни мс, < T_recover). Метрики:
nack-rate, forward-rate, reorder-gap (ассерт), drop-by-class, re-adoptions (инцидент),
adopt-latency-p99, holdback-depth, freeze-p99, application-delay-p99, handoff-rate,
T_reorder-fire (инцидент). Эксплуатация: баги транспорта мульти-региональны — плата заложена
инжектируемым транспортом и оракулами.

## Проверка решения (фазы 3–5)

1. Инжектируемый транспорт с виртуальным временем и перебором шедулеров (фаза 3); таймеры
   recovery (T_recover, cooldown, holdback-GC) читают те же инжектируемые часы. Оракулы: ≤1
   применения на id; per-sender FIFO по трассировке seq (включая хэндофф отправителя и цепочки
   владения); liveness Reserve; **единственный владелец на всех путях, включая recovery
   (CAS-инвариант)**.
2. Отказ-инъекции: заморозка RC до ack (CAS-ре-адопция, отсутствие двойной симуляции), поздний
   ack, цепочка RB→RC→RD в окне неотозванного ack (CAS-провал флип-назад), паника в середине
   replay, паника между флипом и Adopt, переполнение reorder, скачок T_reorder.
3. Пытка ботами: трейд/кайт по границе; зигзаг; каскады (leash через 3 региона); петовод у
   стены (живой пет поездом, мёртвый — отдельно, **рессированный — переприсоединяется к поезду
   за ограниченное время при движущемся и логинящемся хозяине**; бот-паттерн «осцилляция
   хозяина на границе с ритмом cooldown»);
   массовое пересечение; контроль-цепочки (стан→нук) — оракул порядка; **оракул «каст переживает
   хэндофф без входящих прерываний»**; консервация адены через рестарт — фаза 5 (с персистом).
