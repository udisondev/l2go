# ADR-0003: Доставка и владение при хэндоффе — эпохи, seq, draft-модель

**Статус:** draft (v9.4 — редизайн по мета-ревью + правки циклов 1–4, см. §13–16; история
циклов v1–v8 — в git-истории, коммит 5398d72; правило завершения циклов: до отсутствия
замечаний; отвергнутые — §10).

## Контекст

Окно хэндоффа допускает потерю/дубль/инверсию сообщений к сущности (трейд-2PC на бегу через
границу — дюп; стан→нук — «рандомный резист у границы»). Требования: at-most-once на конверт;
exactly-once эффекта; per-sender FIFO через хэндоффы отправителя и получателя; единственный
владелец всегда; мейлбоксы без потерь; граница маскируется интерполяцией и лагом. Несущие
предположения: гистерезис границы (r0/r3); тик-модель ADR-0002 (блоки в тике актора, никто
никого не ждёт); один процесс, каналы надёжны и FIFO.

**Урок мета-ревью:** два кластера сложности v8 были костылями — рекламация владения (следствие
флипа директории до подтверждения установки) и компаунд-поезда (следствие first-class
маршрутизации слуг). v9 устраняет причины: владение переходит только после подтверждения
(draft-модель), слуги — sub-сущности хозяина.

## Решение

Два несущих механизма сохраняются из v8: **эпохи** (маршрутизация, at-most-once, метка ветви) и
**пер-сендерная seq** (порядок, дедуп). Оба — в общем транспортном компоненте (P0.9/P0.10),
одна реализация для регионов, сервисов, gateway. Инвариант AGENTS: каждый отправитель — только
через транспорт; сырой channel-send мимо конверта ломает гарантии.

### 1. Директория, конверт, слуги

- Директория (read-mostly): `id → {owner, epoch, domain}`. Эпоха растёт на каждой смене
  владельца: хэндофф, телепорт, вход/выход инстанса/олимпа, логаут/деспавн. Смерть — не смена.
  Записи не удаляются (tombstone `{owner=nil, epoch}`); **ID сущностей никогда не
  переиспользуются**. Флип директории — **CAS-ассерт**: инициирует только текущий владелец,
  конкурентов нет by construction (см. §3); провал CAS = баг, инцидент.
- Конверт: `{to, fromID, returnTo, epoch, seq, class, attrs}`. `to` — ID сущности **или
  composite `(ownerID, slot)`** для слуг. `fromID` — вечный ID источника (сущность / сервисная
  шарда / gateway; исходящие слуги — от хозяина: одна горутина сериализует, интерливинга
  счётчиков нет). `returnTo` — регион-якорь для возвратов. `attrs` — флаги, включая
  «интент привязан к позиции/моменту» (бывший relocating-класс; см. §6). Пула конвертов нет.
- **Слуги — sub-сущности хозяина (не first-class):** записи в директории нет никогда. Слот 0 —
  позиционный сервант (пет/саммон: позиция, HP, таргетность); слоты 1..3 — кубики
  (непозиционные, бафф-подобные). HP/позиция/команды мутирует регион-владелец **хозяина**;
  атака на слугу маршрутизируется по директории хозяина, валидируется и применяется у его
  владельца (паттерн «оффенс у отправителя, дефенс у владельца» r3 §3). Снапшот региона
  хозяина публикует `servants[]` под стабильным протокольным objectId (внутренняя модель
  владения ≠ сетевой протокол); AoI-дедупликация — по composite-ключу (требование в ADR-0004).
- **Слуга в норме — обычный mover, симулируемый владельцем хозяина:** follow / stand / attack —
  стейты; телепорт — **только аномалия** (прецедент L2: Return/застрял/телепорт хозяина).
  **Поводок:** дистанция > R_leash → телепорт к хозяину; инвариант: R_leash ≤ глубины читаемых
  владельцем снапшотов (~1 регион) и AoI наблюдателей возле слуги. Погоня за целью, вышедшей
  из AoI-окрестности хозяина (нет во читаемых снапшотах), → стоп + возврат к хозяину. Слуга
  может физически находиться в соседнем регионе — симулируется и валидируется владельцем
  хозяина по снапшоту соседа, как гварды (§9-5: немигрирующий преследователь с leash).
- Инвентарь слуги (beast soulshot, корм): предметы — состояние слота; движение предметов —
  transfer-класс (фаза 5). Дисконнект (не логаут) хозяина: слуга жив без команд до таймаута
  дисконнекта, далее — как логаут (деспавн; пет возвращается ошейником). Труп слуги публикуется
  в снапшоте региона хозяина — пока находится в его AoI (косметическое ограничение, осознанное;
  rесс-позиция «у трупа» фиксируется в момент смерти).
- Смерть слуги: слот → `{dead, позиция трупа, expire}` — данные, не сущность; труп виден в
  снапшоте региона хозяина. Ресс = флаг слота + позиция (труп или к хозяину) — **ноль
  протокола**. Логаут = деспавн слуг (пет возвращается предметом — канонический L2). Живой пет
  другому игроку не передаётся (трейдится ошейник) — не-проблема by construction.

### 2. Приём: последовательность = состояние сущности

- Владелец держит `inSeq: {fromID → lastApplied}` — состояние сущности, едет в Adopt.
- `seq == expected` → применить; `seq > expected` → гэп → reorder-буфер (per-source, ограничен;
  переполнение → форс-декларация старшего гэпа мёртвым + алерт); `seq < expected` → дубль →
  дроп. **T_reorder — ассерт:** незакрываемый гэп = баг транспорта, срабатывание = инцидент;
  пропуск объявляется мёртвым только с финальным дропом по классу (§6) и уведомлением.
- Обработчики reliable/transfer идемпотентны по `(fromID, seq)` на входе. Стационар: одно
  сравнение, ноль аллокаций. Resync после idle-GC: якорь на max пришедших.
- Outbox per (отправитель → цель): монотонный `seq` u64, счётчик вечен; запись о последней
  отсылке удерживается ≥ окна T_ack; outbox — состояние отправителя, едет в его Adopt.

### 3. Хэндофф: draft-модель (владение переходит по подтверждению)

Принцип: **директория никогда не указывает на неустановленного владельца.** До подтверждения
установки всё входящее идёт в текущего владельца и пересылается одним FIFO-каналом — гонки
владения непредставимы, откатывать нечего.

```
RB (тик, один блок; шаги идемпотентны, состояние попытки — часть состояния RB):
1. B.migrating = true; входящие → очередь B; открывается ЖУРНАЛ пересланных
   (журнал покрывает и очередь шага 1 — она пойдёт в payload И остаётся восстановимой при аборте)
2. payload = {state(B) со слугами-полями, очередь, inSeq, outbox, reorder-буфер,
   dirty-флаги персиста (какие поля требуют flush), transfer-журнал сущности
   {transferID, фаза, payload} — передаточные метаданные ЕСТЬ состояние сущности:
   едут в Adopt и в каждый снапшот владельца, переживая смену владельца и обрезку WAL}
3. send Adopt{id, attempt k, targetEpoch e+1} → RC; таймер T_ack
4. B заморожен и публикуется в снапшоте RB (видимость не рвётся)
   ДИРЕКТОРИЯ НЕ МЕНЯЕТСЯ: все отправители по-прежнему едут в RB

Окно (стационар): входящие для B → в журнал → forward в RC (канал RB→RC;
Adopt строго первый по FIFO канала)

RC:
- Adopt → install ЧЕРНОВИКА (идемпотентен по {id, attempt k}): replay очереди,
  применение дальнейших входящих — к состоянию черновика по порядку прибытия;
  ЧЕРНОВИК НЕ ЭМИТИТ эффектов, НЕ ПИШЕТ персист, НЕ ПУБЛИКУЕТСЯ в снапшот;
  transfer-Commit буферизуется НЕПРИМЕНЁННЫМ (WAL-гейт, см. §7) — черновик не создаёт
  WAL-записей, значит Commit нельзя применить до того, как его можно журналировать
- send install-ack{attempt k} → RB

RB по ack:
5. ФЛИП директории {RB@e} → {RC@e+1} (CAS-ассерт)
6. send flip-confirm{attempt k} → RC; redirect-стаб {B → RC@e+1}; журнал закрывается
7. по confirm-ack от RC (отправляется после подшага 5): копия и журнал забываются; **B
   удерживается в write-behind персисте RB УСЛОВНО — до подтверждённого на диске снапшота
   B@epoch e+1 у RC** (2 интервала снапшотинга — нижняя граница ожидания; T2/T3-пути не
   вытесняют B из снапшота RB раньше этого условия; интервалы тикают симуляционным временем —
   T2-фриз их останавливает). Дубль в персисте безвреден — рестарт режет по max-epoch;
   eager-flush перенесённых сущностей в подшаге 4 — опция фазы 5 при I/O-бюджете. Нет
   confirm-ack за T_forget → redirect-стаб удерживается — страгглеры после T_forget
   ре-раутятся по директории, не дропаются; копия GC с алертом: liveness-only путь, течь
   ограничена, корректность не страдает.

RC по confirm: черновик → АВТОРИТЕТ: (1) WAL group-commit fsync по отложенным
transfer-Commit; (2) применение отложенных; (3) flush буфера отложенных эффектов;
(4) персист маркера владения {id, owner, epoch}; (5) симуляция, публикация в снапшоте.
Пост-флипные прямые доставки применяются к (уже) авторитету; страгглеры до-флипных
чтений — redirect-стаб forward (epoch перештамповывается, seq сохраняется).
```

- **attempt k — собственный монотонный счётчик сущности**, не эпоха: аборт не двигает эпоху,
  повторная попытка получает k+1; черновик RC идентифицируется {id, attempt} — коллизий с
  абортнутыми попытками нет.
- **Аварии:**
  - Нет ack за T_ack → retransmit Adopt (≤2; install идемпотентен) → **abort**: B
    размораживается у RB, очередь восстанавливается из журнала, симуляция продолжается у RB
    (владение никуда не двигалось). Поздний ack/confirm абортнутой попытки — игнор по attempt.
    Черновик RC: retire-сообщение + TTL-GC по attempt. **Отката позиции нет** — B продолжил с
    точки заморозки. **Бюджет abort-стойки = T_ack × (1 + N_retransmit) ≈ 1.5–3 с** (единая
    формула; стойка коррелирует с лагом региона-приёмника — метрика abort-latency-p99).
    **TTL-GC черновика — только по доказанной смерти попытки** (retire от RB / attempt
    абортнут); TTL ≥ T_forget + запас; confirm-промах к собранному-GC черновику → RB
    пере-Adopt, пока держит копию (идемпотентность install по {id, attempt}). Голый TTL без
    доказательства смерти запрещён: гонка «GC vs поздний confirm» в окне flip→confirm
    оставляла бы сущность без владельца и без состояния.
  - RC завис **до install-ack**: B жив у RB (abort); после флипа — T_forget-путь + лестница.
    Регион RC — предмет лестницы надзора (§5).
  - RB завис с замороженным B: регион завис → лестница → рестарт; восстановление — фаза 5 (§7).
  - Паника в блоке RB: шаги идемпотентны (состояние попытки живёт в **памяти** региона —
    в персист не пишется и с рестартом умирает вместе с черновиком); повтор блока доводит
    до конца.
- **Freeze-бюджет:** норма ≈ install + ack + flip + confirm (4 контрольных хопа, при обработке
  на тиках акторов — до ~0.5 с хвостом; метрика freeze-p99); маскируется интерполяцией.
  Abort = стойка ≤ T_ack×3 без телепорт-назад.
- **Per-entity handoff cooldown** (сотни мс, гистерезис поверх) — против зигзага; с окном
  draft-модели совместим напрямую (окно теперь владельчески безопасно, cooldown — чисто
  нагрузочная гигиена).
- **Нагрузка:** контрольные сообщения (Adopt/ack/confirm/retire/redirect-forward/
  snapshot-persist-ack — уведомление RB о подтверждённом на диске снапшоте, замыкает
  условное удержание шага 7; без него удержание вырождается в liveness-only) —
  приоритетной полосой мимо drain-капа с собственным бюджетом; **при исчерпании бюджета полосы
  контрольные падают в обычный drain (не дропаются)**; Adopt'ы тика коалесятся (батчинг); в окне
  100% входящих пересылается RB (десятки сообщений на хэндофф — копейки); метрики
  application-delay-p99, freeze-p99, forward-rate, adopt-latency-p99, abort-latency-p99.

### 4. Домены

`domain` в директории — формат сейчас, **политика — фаза 6** (доменов нет). Whitelist
advisory-классов — именованный enum (стартово: HP/MP/CP-статусы пати-окна), default deny;
«advisory не содержит координат, таргетов, баффов, инвентаря»; расширение — правкой ADR.

### 5. Надзор и восстановление (лестница; let-it-crash на уровне владения)

Владение в процессе **не отбирается никогда** (нет флип-назад, нет Invalidate, нет рекламации).
Recovery-домен зависшего актора — процесс:

- **T1 ≈ 2 с** — лаг региона: лог + pprof-дамп (ADR-0002, без изменений).
- **T2 ≈ 5–10 с** — регион всё ещё лагает: **фриз мира** (метроном стопает рассылку тиков,
  регионы дренируются), дамп кучи, пейдж; оператор может разморозить или поставить hold.
- **T3 ≈ 60 с** — graceful shutdown: стоп метронома и логинов, flush снапшотов + WAL fsync
  (черновики НЕ флашатся — «черновик не персистит» выполняется и в shutdown-пути),
  exit (бюджет 30 с, не уложились — exit всё равно).
- Разморозка после T2: первый тик получает dt = длительности фриза — dt капится
  (баффы/реген/откаты не «дотикивают» разом; виртуальные часы в тестах читают то же).
- **Backstop вне процесса:** systemd `sd_notify(WATCHDOG)` из горутины-хартбита,
  `Restart=on-failure`, `StartLimitBurst=3/10 мин`. kill -9 корректен всегда (WAL).
- Загрузка после рестарта: реплей WAL (§7), очередь логинов ступенчатым адмитом (~200/с).
  Crash-loop детерминированного бага → старт-лимит + пейдж; карантин региона по контексту
  крэша — открытый вопрос (§9).

### 6. Классы доставки (полный реестр — таксономия P0.10)

| Класс | Поведение при финальном дропе | Примеры |
|---|---|---|
| fire-and-forget | молча дроп | урон, бродкаст |
| reliable-until-delivered | NACK владельцу отправителя + алерт | аггро, KillCredit, XP-доля, контроль-эффекты |
| transfer | дроп = чистый abort 2PC | Reserve/Commit трейда, spoil/sweep |

Финальный дроп ≠ 0 для reliable/transfer — инцидент. Ретраев отправителя в стационаре нет.
«Интент привязан к позиции/моменту» — **атрибут конверта**: резолв происходит применяющей
стороной по её текущему состоянию (в окне — черновиком, по его продвигающемуся состоянию);
после флипа страгглер отсекается универсальной валидацией-на-применении.

### 7. Персистентность (фаза 5 — первичный путь восстановления)

- Пишет только АВТОРИТЕТ (черновик не персистит никогда); записи состояния несут epoch.
- **WAL transferID, journal-before-apply:** Reserve/Commit/Abort с group-commit fsync до
  применения Commit; transferID = {bootID, монотонный}; реплей: Committed → применить,
  Reserved → Abort + компенсация. Кросс-владельческие предметные эффекты — только через
  transfer-класс (подбор лута — тоже), иначе рестарт между персистами = дюп. **WAL-гейт
  черновика:** transfer-Commit буферизуется неприменённым; авторитет при confirm сперва
  WAL-пишет, потом применяет — «Trade successful» не показывается раньше WAL-записи.
- Снапшоты write-behind per-owner (30–60 с), атомарная замена, чексуммы (torn write после
  kill -9). Потеря при kill -9: ≤60 с волатильной статики (паритет с v8).
- **Не переживают рестарт (осознанно):** конверты, эпохи, seq, inSeq, outbox, attempt-счётчики
  (inSeq/outbox/attempt ВЫРЕЗАЮТСЯ из снапшотов — устаревший персистённый inSeq съедал бы
  свежие сообщения как «дубли»; конверты в полёте умирают вместе с каналами).
- **Восстановление директории:** из снапшотов всех владельцев, коллизии одной сущности
  разрешаются по max-epoch; при confirm авторитет персистит маркер владения {id, owner, epoch}
  сразу после WAL-синка отложенных Commit (подшаг 4 confirm-списка §3), той же атомарной
  заменой с чексуммой, что снапшоты. **Состояние сущности при рестарте восстанавливается из
  свежайшего доступного персиста** (снапшот предыдущего владельца + WAL-реплей) **и
  устанавливается у владельца по маркеру/max-epoch** — «маркер есть, снапшота нового владельца
  ещё нет» не теряет сущность. Записи WAL несут entity-ID; реплей адресуется через
  восстановленную директорию (запись применяется текущим владельцем сущности).
- **Правила реплея WAL:** резолв transferID **глобален** — есть хоть одно Committed-
  доказательство transferID → коммитится у обеих сторон (перенос достраивается), Reserved
  без Committed → Abort + компенсация (локальный «Reserved → Abort» запрещён: kill -9 между
  Commit-записями двух сторон не должен абортировать против закоммиченной половины).
  **Committed-доказательство = WAL-запись ∪ transfer-журнал сущности** ({transferID, фаза,
  payload} — состояние сущности, едет в Adopt и в снапшот владельца: переживает смену
  владельца и обрезку WAL). **Обрезка WAL-записи переноса — только после резолва всех
  сторон** (метаданные мостят доказательство и фазу; payload последней копии жив до резолва);
  субъект резолва — инициатор переноса (финальные ack обеих сторон; персист-обязанность
  сервисных шард — фаза 5); GC записей transfer-журнала сущности — по возрасту после
  резолва. Удержание каскадно: выполнимость условия для RB опирается на то, что RC сам
  держит B@e+1 в своих снапшотах до подтверждения следующего звена. WAL-гейт удлиняет окно
  Reserve→Commit в draft-окне — требования к резервным блокировкам предметов фиксируются
  в фазе 5.

### 8. Гарантии (честные)

- **At-most-once на конверт** (надёжные каналы; финальный дроп = доказательство неприменения).
- **Exactly-once эффекта** = at-most-once + seq-дедуп + WAL (включая рестарт — специфицировано,
  в отличие от v8).
- **Per-sender FIFO структурно на всех путях**: в окне — единый FIFO-канал RB→RC (Adopt строго
  первый); после флипа — seq. «С точностью до пропуска, объявленного мёртвым» (только
  транспортный ассерт).
- **Единственный владелец — строже v8:** директория никогда не указывает на
  **неустановленного** владельца (в окне flip→confirm указывает на черновик — единственного
  применяющего входящие к единой линии состояния; формулировка принципа — §3); второй
  владелец непредставим (нет флип-назад); нет residual-окна двойной эмиссии; нет «двух
  замёрзших звеньев = потеря B».
- Мейлбоксы без потерь; капы — на обработку. Порядок между отправителями не гарантируется
  (OQ-2).
- Граница: freeze-p99 с бюджетом (хвост до ~0.5 с worst-case); abort = стойка ≤ T_ack×3
  **без телепорт-назад** (коррелирует с лагом приёмника); авария процесса = фриз/рестарт по
  лестнице (единственный класс «долго», инцидент-класс с алертом).

## 9. Открытые вопросы (не блокируют акцепт)

1. **Корабли/пассажиры** — кандидат ADR-0005 (пассажиры — не слуги; массовые компаунд-переезды
   платформой).
2. **Взаимоубийство у границы**: порядок двух смертей не детерминирован — геймплейная
   приемлемость, фаза 4.
3. **Групповые телепорт-бёрсты** (Party Recall, Festival, Rift): механика покрывает (много
   сообщений в окне у владельца), паттерн нагрузки — метрики фазы 6.
4. **Death-drop у границы** — сверить при реализации фазы 5.
5. **Гварды**: регион-принадлежные NPC, не мигрируют, преследуют до leash — тот же паттерн,
   что слуги-субсущности (немигрирующий преследователь); политика — P0.10; проверить, что
   leash не выводит преследование за AoI 3×3.
6. **Карантин региона по контексту крэша** (превращение crash-loop в региональное потемнение) —
   механика-кандидат, фаза 4+.

## 10. Отвергнутые замечания и альтернативы (реестр; не поднимаются без новых доказательств)

История v1–v8: см. git (5398d72). Ключевые отвержения, актуальные для v9:

1. (цикл 1) «Forward сохраняет порядок» — неверно; безопасен благодаря seq.
2. (цикл 2) «Разрыв потока отправителя — оговорка» — заменено вечным fromID.
3. **Флип у источника до подтверждения + рекламация владения (v2–v8)** — superseded draft-
   моделью: директория не лжёт, откатывать нечего; весь блок recovery (CAS-флип-назад,
   Invalidate с финальными счётчиками, мёртвые диапазоны, подтяжка outbox, сверка ветви)
   удалён как класс. Отвергнуто по итогам мета-ревью, не по формальному замечанию.
4. **Компаунд-поезда слуг + reconcile «roster × директория» (v4–v8)** — superseded
   субсущностями: слуга не может рассинхронизироваться с хозяином, потому что не является
   маршрутизируемой единицей. Шесть правок ревью о переприсоединении аннулированы как класс.
5. **Координатор владения (единственный писатель директории)** — отвергнут: под draft-моделью
   гонки отсутствуют структурно («инициирует только текущий владелец, отнимать не у кого»);
   остаётся чистым control-plane-оверхедом (~6 типов сообщений, rebuild-протокол). Может
   вернуться как телеметрия/наблюдаемость смен владельства, не как писатель.
6. **Пер-ветвевой микрорекавери вообще** — отвергнут (мета-ревью): страховал ~0.5 сущности на
   инцидент при регионе-заложнике; энд-стейт любой — рестарт; ложные срабатывания на транзитном
   лаге порождали пинг-понг откатов. Замена — abort + лестница надзора + WAL.
7. Пул конвертов; полный seq-TCP; синхронный хэндофф; запрет трейда при мигрирующем
   контрагенте (только fast-fail в 2PC) — отвергнуты ранее (история в git).

## 11. Цена решения

Транспортный слой (конверт, outbox u64, inSeq, reorder-ассерт, redirect-forward); draft-модель
(черновик + TTL-GC + журнал пересланных ≈ замороженная копия, что и так держалась); лестница
надзора (T2/T3/systemd ~200–500 строк) + sd_notify-юнит; фаза 5 дорожает на ~30–50% (WAL
group-commit, реплей, чексуммы, chaos-CI по точкам kill) — в обмен на эквивалентную экономию в
фазе 4 (нет recovery-хореографии и её интерливинг-оракуров). **Ручек хэндоффа три:** T_ack
(~0.5–1 с, 2 ретрансмита до аборта), freeze-бюджет p99, handoff-cooldown; инфраструктурные
константы (пороги T2/T3, draft-TTL, T_forget, кап reorder) — фиксированные, не тюнинг.
Метрики: forward-rate, adopt-latency-p99, abort-rate, abort-latency-p99, draft-GC-rate,
T_reorder-fire (инцидент), drop-by-class, freeze-p99, application-delay-p99, handoff-rate,
restart-count/MTTR, wal-lag.

## 12. Проверка решения (фазы 3–5)

1. Инжектируемый транспорт с виртуальным временем и перебором шедулеров (фаза 3); recovery-
   таймеры читают те же инжектируемые часы. Оракулы: ≤1 применения на id; per-sender FIFO
   (включая хэндофф отправителя и окно draft); **директория никогда не указывает на
   неустановленного владельца** (инвариант-оракул на каждом шаге трассировки); консервация
   адены — фаза 5 (с персистом, включая рестарт); liveness Reserve.
2. Отказ-инъекции: потеря/задержка Adopt (retransmit→abort), поздний ack/confirm абортнутой
   попытки, гонка draft-TTL vs поздний confirm, паника в блоке RB на каждом шаге, переполнение
   reorder, kill -9 по каждой точке WAL (реплей), **kill -9 в окне confirm-ack → первый
   снапшот RC** (проверка условного write-behind-удержания), kill -9 с незарезолвленным
   переносом после обрезки WAL (проверка transfer-журнала сущности).
3. Пытка ботами: трейд/кайт по границе; зигзаг; каскады (leash моба через 3 региона);
   петовод у стены (поводок-телепорт, ресс слуги — флаг); массовое пересечение;
   контроль-цепочки (стан→нук); оракул «каст переживает хэндофф»; лестница (дробы T2/T3 в
   dev-режиме).

## Последствия

- Транспортный компонент в карте P0.9; таксономия P0.10 несёт классы, composite-адресацию
  слуг, атрибуты конверта, домен-политику, политику гвардов; шов инжектируемого транспорта —
  требование с фазы 3.
- **Требование в P0.7/ADR-0004 (knownlist):** AoI-дедупликация по entity-ID **и composite-ключу
  слуг**; выбор источника при двойной публикации (замороженный у RB vs живой у RC в окне) — по
  max-epoch.
- Формат Adopt фиксирован: {state (+слуги-слоты), очередь, inSeq, outbox, reorder-буфер,
  dirty-флаги, transfer-журнал сущности {transferID, фаза, payload}} + буфер отложенных
  эффектов в install-контексте черновика.
- **При акцепте — синхронизировать AGENTS.md:** инвариант 4 переформулировать под draft-модель
  (флип после подтверждения; redirect-стаб; владение не отбирается); добавить инвариант
  «каждый отправитель — только через транспорт».
- r3 §3 сценарий 1 — superseded (пометка в r3 на месте).
