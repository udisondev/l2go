# ADR-0006: Ревью-конвейер задачи: стадии, роли, верификация находок

**Статус:** draft (создан 2026-09-09, ждёт акцепта владельца).

## Контекст

Проект исполняется агентными сессиями, каждая следующая ничего не помнит о предыдущей — вся
координация через файлы. Практика фазы 0 дала рабочий паттерн: ревью несколькими агентами,
верификация находок координатором, циклы до нуля замечаний; формализация правил ревью сокращала
сходимость с 8 циклов до 3. У паттерна два системных риска. Первый — ложная сходимость: после
многих раундов правок ревьюеры утверждают «мешанину», потому что вложились в неё. Второй —
вечные циклы: переоткрытие уже отвергнутых находок и гипотетические «можно лучше» без критерия
превосходства. Кроме того, владельцу нужны явные, а не сквозные точки контроля. Нужен конвейер с
верифицируемыми находками, общей файловой памятью решений и гарантией завершения.

## Решение

1. **Единица — одна задача плана фазы.** Состояние конвейера — файлы: статус задачи в плане и
   реестр находок задачи; любая новая сессия резюмирует конвейер с места остановки по ним, без
   памяти в чате.

2. **Стадии:**

| Стадия | Содержание | Исполнитель |
|---|---|---|
| S0 | проработка плана задачи | владелец + ведущая сессия |
| S1 | самопроверка плана (инварианты, карта пакетов, план тестов, критерии приёмки) | ведущая сессия |
| S2 | ревью плана панелью ролей, независимо, параллельно | сабагенты-роли |
| S3 | верификация каждой находки воспроизведением свидетельства | ведущая сессия; споры — владелец |
| S4 | исправление плана: правка + аргументация (какие альтернативы рассмотрены и почему хуже) | ведущая сессия |
| S5 | замыкание: авторы находок проверяют адресацию своих пунктов по дельте | затронутые роли |
| S6 | свежий взгляд: агенты без истории итераций ищут конкретно лучшее решение | сабагенты |
| S7 | реализация по утверждённому плану (TDD, ворота) | ведущая сессия |
| S8 | ревью реализации: роли + тестировщик + трассировка план↔код | сабагенты |
| S9 | приёмка: выжимка, статусы, журнал | владелец |

3. **Находка действительна только со свидетельством** одного из пяти видов: место + нарушенное
   правило; сценарий отказа (вход → неверный исход); трасса интерливинга (шаги по регионам и
   тикам → нарушение конкурентного инварианта); числа бенчмарка против бюджета или baseline;
   воспроизводимый злой вход (байты или действия → паника/дюп/выход за границы). Мнение без
   свидетельства — не находка. Серьёзность: блокер / мажор / минор; циклы перезапускают только
   блокеры и мажоры, миноры собираются пачкой. Выход из ревью-цикла = ноль подтверждённых
   блокеров и мажоров (миноры могут остаться записанными).

4. **Реестр находок один на задачу** и живёт во всех стадиях. Запись находки: идентификатор,
   стадия, роль, утверждение, свидетельство, серьёзность, статус (подтверждена / отклонена /
   владельцу / закрыта правкой), решение. Исправление: находка → правка → аргументация → чем
   проверяется закрытие. Отклонённые хранятся с причинами; переоткрытие — только новым
   свидетельством, с новым идентификатором и ссылкой на старый.

5. **Роли.** Ревьюеры — независимые сабагенты: до слияния находок друг друга не видят, слияние и
   дедупликация — ведущая сессия, конфликт мнений решается свидетельством или уходит владельцу.

| Роль | Мандат |
|---|---|
| инвариантщик | соответствие инвариантам проекта и принятым решениям — буква правил |
| конкурентщик | конкурентная корректность за пределами детектора гонок: интерливинги, окна передачи владения, порядок сообщений, побег указателей, горутины |
| перформансер | производительность как бюджет: горячие пути, наличие и честность бенчмарков, аллокации, baseline до оптимизации; и обратное — сложность без измерения |
| безопасник | недоверенный вход: границы доверия, валидация на применении, анти-дюп, устойчивость к малформенным пакетам; лицензионная гигиена портов |
| доменщик | семантика мира и протокола, корректность портов из GPL-референсов, поведение |
| прагматик | простота, YAGNI, скоуп, именование, читаемость |
| тестировщик (S8) | покрытие, фальсифицируемость критериев, race-стресс, golden-тесты |

   Свежий взгляд (S6) — три агента без истории итераций: исходная проблема + финальный план,
   вопрос «решение состоятельно? предложи конкретно лучше с трейдоффами». Рестарт цикла —
   только если альтернатива конкретна и превосходство подтверждено той же верификацией по
   свидетельствам; «гипотетически лучше» рестарта не даёт.

6. **Ревью-профиль** — строка в спецификации задачи, задаёт состав панелей; без строки —
   дефолт по типу задачи:

| Тип задачи | Панель S2 | Панель S8 |
|---|---|---|
| код мира / транспорт / тик | инвариантщик + конкурентщик + прагматик | + тестировщик |
| семантика мира (порты формул, AI) | + доменщик | + доменщик |
| задет горячий путь | + перформансер | + перформансер |
| протокол / шлюз входа | + безопасник | + безопасник |
| доки / скрипты | облегчённый режим | облегчённый режим |

   Облегчённый режим: самопроверка + ворота + один ревьюер + владелец.

7. **Бюджеты и завершение.** Ревью плана ≤2 раундов; рестарты свежего взгляда ≤2; ревью
   реализации ≤3 раундов. Превышение бюджета — остановка и вопрос владельцу. Числа — стартовые
   калибровки: их правка фиксируется записью в журнал и не является сменой решения.

8. **Соответствие реализации плану** проверяется к финальному утверждённому плану (включая
   правки), не к первому черновику. Трассировка двусторонняя: каждый пункт плана → артефакт
   (файл / тест / коммит); каждый значимый кусок диффа → пункт плана или запись-отклонение в
   реестре с аргументацией. Отклонение без записи — нарушение.

9. **Исполнение.** Ведущая сессия ведёт конвейер автономно: одна команда на задачу («проведи
   задачу через харнес»), остановки только в точках владельца: спор в S3, исчерпание бюджета,
   финальная приёмка S9. Реализация (S7) — обычная работа сессии, не контрольная стадия; ручной
   вход `/review` прогоняет только контроль, положенный задаче сейчас. Машина раньше мнения:
   что проверяется воротами, тестами, бенчмарками — исполняется, а не ревьюится. Статус ✅
   ставит только владелец. Исполняемый протокол закреплён workspace-навыком `review`.

## Альтернативы (отвергнуты)

- Один ревьюер без верификации находок — дешевле, но нет защиты ни от ложных находок, ни от
  ложной сходимости.
- Весь протокол в правилах для агентных сессий — грузится в каждую сессию, включая тривиальные;
  раздувает контекст всех работ.
- Внешний CLI-оркестратор — суждения всё равно агентные, слой даёт только спавн и слияние;
  зависимость наружу на старте фазы 1 не обоснована.
- Замыкание и свежий взгляд одной панелью — итерировавшие ревьюеры закоммичены в решение
  (якорение и вложенность); панель свежего взгляда обязана быть без истории.
- Полное соответствие «первому черновику плана» — превращает каждую правку ревью-цикла в
  «отклонение»; соответствие меряется к финальному утверждённому плану.

## Последствия

- Задачи проходят дольше и дороже: на контрольных стадиях панель из 3–7 агентов. Взамен —
  верифицируемость каждого замечания, файловая память решений и гарантия завершения.
- Владелец контролирует точки решений, а не весь поток; ✅ остаётся за владельцем.
- Спецификация задачи плана дополняется строкой «Ревью-профиль».
- Решение не влияет на инварианты мира, карту пакетов и ворота: конвейер их потребляет.

## Цена решения

- Платим временем и агент-тактами на каждый контрольный цикл, потому что целостность
  конкурентной модели и экономики дороже скорости прохождения задач.
- Дисциплина формата реестра требует поддержки; валидация реестра — отдельный маленький скрипт
  в воротах, когда формат устоится (сознательно не сейчас).
- Риск бюрократизации; лечение — профили ролей по типу задачи и облегчённый режим для не-кода.

## Проверка решения

- Первые 2–3 задачи фазы 1 прогнать полным конвейером; в журнал: число раундов до сходимости,
  доля отклонённых находок, число остановок владельца. По этим числам калибровать бюджеты и
  составы панелей; сигнал к пересмотру — устойчивый выход за бюджеты или рост доли споров.
