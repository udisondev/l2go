# ADR-0002: Модель тика основного мира — общий метроном без барьера

**Статус:** accepted (защищено в дизайн-сессии 2026-09-08; см. [r3.md §1](../../research/r3.md)).
**Примечание:** ADR-инфраструктура (шаблон, процесс) вводится задачей P0.3; эта запись сделана
досрочно, потому что решение уже прошло защиту. Номер 0001 зарезервирован за лицензионной
позицией (P0.8).

## Контекст

В r0 модель тики зафиксирована противоречиво: секция про изоляцию осады предлагает «общий
тик-луп с воркер-пулом и барьером на кадр», секция про стоимость акторов называет целевым
goroutine-per-region. Блокирующий вопрос №1 из [r2 §Открытые вопросы](../../research/r2.md).

## Решение

1. **Исполнитель тика региона — его собственная горутина** (мейлбокс + тик в одном `select`).
   Прикладной воркер-пул для состояния мира запрещён: single-writer должен быть халявным.
2. **Барьера на кадр нет.** Никто не ждёт опоздавших: отставший регион пропускает такт.
3. **Доставка — центральный диспетчер-метроном:** одна горутина, тикер 10 Гц, активный сет;
   на каждый такт N — non-blocking send номера тика в cap-1 канал каждого активного региона.
   Провалившийся send = дропнутый тик (коалесинг: очередь тиков не копится) + счётчик-метрика
   перегрузки per-region.
4. **Наблюдаемость вместо ожидания:** регион после шага атомарно пишет `doneTick`; вотчдог
   считает лаг (`текущийТик − doneTick > k` → лог/pprof/алерт), никто не блокируется.
   Debug-барьер («ждать все ack'и N») — режим за флагом для dev-проверок инвариантов на
   согласованном кате.
5. **Дисциплина шага:** drain-mailbox → фаза A (dt) → фаза B (capped) → публикация снапшота →
   ack. dt — реальное время между тиками по монотонным часам (дропнутый тик даёт 200 мс);
   хардкод dt = 100 мс запрещён.
6. **Осада/инстансы/олимп** — те же компоненты, но отдельный диспетчер со своим rate и бюджетом
   (унаследовано из r0, не пересматривается). Пустые регионы не в активном сете; пробуждение —
   сообщением в мейлбокс.

## Отвергнутые альтернативы

- **Воркер-пул + барьер:** теряет халявный single-writer (пиннинг региона к воркеру = своя
  горутина с лишним слоем); кадр = max по сотням регионов с тяжёлохвостым шагом — глобальная
  точка синхронизации; продукт барьера (консистентный кат на тике N) не нужен ни одному
  потребителю (knownlist, прицельные проверки, AoE, LOS, пати, экономика, расписания, персист —
  все advisory/eventual/владельческие), а клиент его не наблюдает вовсе (сетевой разброс
  доставки больше эпохи кадра).
- **Персональные тикеры на регион:** нет глобального номера тика; перегрузка утаивается
  (размазанный самоколлапс без точки наблюдения); нет ручки глобального троттлинга. Запасной
  вариант при фальсификаторе №1.
- **Когорты/иерархии барьеров:** сложность без потребителя.

## Последствия

- Изоляция деградации: отстаёт только регион, не мир; ручка осознанного глобального троттлинга
  (5 Гц всем) у диспетчера.
- Решение обратимо в сторону барьера (ack'и уже собираются; debug-режим ≈ 20 строк), необратимо
  в обратную — выбрана сторона с дешёвой ошибкой.
- Цена: нет глобального «тик N» для отладки/реплея (per-owner трейсы с корреляцией по id
  сообщений); backpressure не автоматический — дисциплина капов (фаза B, drain-mailbox) +
  вотчдог вместо него; плумбинг диспетчера.

## Проверка решения (фаза 4, боты)

1. Спайки шедулер-латентности на границе кадра → бакетный стаггер или персональные тикеры.
2. Потребность в консистентном кате → off-loop контент или debug-барьер.
3. Систематически горячая дроп-метрика при зелёных бенчмарках → пересмотр бюджета шага.
