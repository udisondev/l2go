# testing.md — правила тестов la2

Обязателен при написании или правке тестов, тест-харнесов и бенчмарков; перечитывается
вместе с codestyle.md. Выжимка официальных гайдов Go и практик проекта; любые
конкретные пороги подтверждаются своим прогоном. Инварианты проекта выше этого гайда.

## 0. Дисциплина

- TDD: тест раньше кода, красный обязателен (ошибка компиляции — тоже красный).
- Оракул обязателен: до написания теста сформулировано, что именно фальсифицируется —
  какой наблюдаемый результат (значение, канал, метрика, ящик, трафик-лог, дамп) и какой
  дефект этот тест поймает. Тест без оракула — отсыпка покрытия.
- Трассировка: каждый критерий приёмки задачи покрыт ≥1 тестом; тест-сирота без пункта
  плана — находка ревью в обе стороны.
- Флако-чувствительные тесты прогоняются дважды (`-count=2`) до коммита.

## 1. Флаки-контроль (главное)

- **`time.Sleep` для синхронизации запрещён.** Сон не доказывает наступление условия —
  он делает тест медленным и ломается на медленном железе/под `-race` (замедление
  5–20×). Допустимый сон — только как нагрузка или проверка тайминг-инварианта
  («молчун жив дольше дедлайна»), с комментарием, почему это не синхронизация.
- Синхронизация — детерминированная:
  - канал-оракул: `select` с `time.After` на ожидание события от тестируемого кода;
  - поллинг с дедлайном (waitFor): условие + шаг 5–10 мс + бюджет 2–5 с; бюджет меньше
    CI-таймаута, имя условия в ошибке;
  - `sync.WaitGroup` (горутины — `wg.Go`), барьеры;
  - швы времени: инъекция часов/тикера для дедлайнов и TTL — детерминизм без ожиданий.
- `testing/synctest` — только для чистого виртуального времени без реальных ресурсов:
  сокеты и файлы вне пузыря запрещены runtime'ом; сетевые сценарии — на реальных
  ephemeral-соединениях (`127.0.0.1:0`), фиксированные порты запрещены.
- Порядок горутин — не контракт: тест не полагается на шедулер; там, где порядок
  недетерминирован по построению, ассерт проверяет инвариант множества (multiset,
  счётчики, сортировка результата), а не последовательность.
- Время в тесте — из швов: никакого «сейчас + 5 с» в тестируемом коде без инъекции;
  тайминг-тесты ускоряются конфигом (миллисекунды вместо минут), а не сном.

## 2. stdlib-практики

- `t.Context()` (Go 1.24+) вместо `context.Background()` + ручная отмена: отмена
  привязана к жизненному циклу теста; `context.WithTimeout(t.Context(), …)` — по делу.
- `t.Parallel()` — на чистых юнит-тестах (нет общих ресурсов, нет таймингов, нет сети);
  timing-зависимые и сокетные — последовательно (правило: timing-dependent → not
  parallel). Параллельный тест не берёт `t.Setenv` и не мутирует глобальное состояние.
- Table-driven: таблица кейсов с полями-именами, `t.Run` на строку; общий код —
  хелперы с `t.Helper()` (чтобы ошибки указывали на строку вызова).
- Ресурсы: `t.TempDir()` (не tmp-имена руками), `t.Setenv`, `t.Cleanup` в хелперах
  (defer — только внутри самой тест-функции).
- Ошибки: вход, got, want — `t.Errorf("Foo(%q) = %d; want %d", …)`; в горутинах —
  `t.Error` безопасен, но фаталить можно только из основной горутины теста.
- Имена: `TestXxx` — по поведению; подтесты — по сценарию входа; бенчмарки — с
  измеряемым размером в имени.
- Запрещены: пустые тесты-заглушки, `t.Skip` без причины в комментарии, проверка
  `err != nil` без сообщения, игнор ошибки через `_`.
- Пакет-внутренние тесты (`package foo`) — для белого ящика; чёрный ящик
  (`package foo_test`) — по умолчанию для публичного API.

## 3. Уровни (пирамида; вниз — больше и быстрее)

- **Юнит**: чистые функции без I/O; злые входы таблицами; аллок-бюджеты машинно
  (`testing.AllocsPerRun`).
- **Компонентные**: пакет + реальные коллабораторы на швах; двойники — только по
  существующим интерфейсам-швам; интерфейс «для моков» — запрещён (codestyle §2).
- **Интеграционные**: живой контур в одном процессе (сервер + клиент + транспорт),
  ephemeral-порты, фикстуры ручные или golden; ассерты по трафик-логу и ящикам.
- **E2E**: живой внешний контур (реальный клиент/второй процесс); в CI — только
  воспроизводимое; живой клиент владельца — контрольные точки, не CI.
- **Внешние сервисные зависимости** (БД, брокер — когда появятся): testcontainers с
  health-check/strategией ожидания, а не мок: мок не ловит диалект/сериализацию/обрывы;
  тесты с контейнерами — за build-тегом, отдельной целью make; контейнер переиспользуется
  в рамках пакета. Для внешних HTTP-зависимостей, которые нельзя поднять контейнером
  (платные API), — локальный заглушечный сервер на ephemeral-порту, не мок-объект.
- Моки не подменяют уровень: если кейс называется «интеграционный», зависимости
  настоящие или контейнерные, а не приглушённые.

## 4. Конкурентность и race

- Все сценарии с заявленной параллельностью гоняются под `-race` (`scripts/race.sh`
  локально без системного gcc; CI — штатно). Стресс под `-race`: настоящий параллелизм
  (горутины-отправители + конкурентные операции), не последовательная имитация.
- Детектор — часть оракула: гонка в тестовом харнессе (чтение внутренних структур
  тестируемого актора из тест-горутины) — та же находка, что и гонка в прод-коде;
  харнесс ждёт по атомикам/каналам актора, к внутренним картам актора лезет только
  после quiesce (happens-before через атомик завершения).
- Тесты, фальсифицирующие тайминговые дропы/капы «на скорости», под детектором могут
  терять фальсификацию (дрен успевает за волной): инварианты счётчиков остаются,
  фальсификация — за `//go:build race`-исключением с комментарием.

## 5. Бенчмарки и бюджеты

- `b.Loop()` (Go 1.24+), `b.ReportAllocs()`, `b.ResetTimer` после подготовки;
  machine-пыль (клоны/спавн горутин харнесса) — вне измеряемого пути или оговорена
  в шапке baseline.
- Аллок-бюджеты горячих путей — машинные тесты (`AllocsPerRun`), не глаза;
  недостижимость бюджета — записью в реестр задачи с причиной.
- Baseline: `-count=10`, benchstat-совместимо; benchtime короткий фиксирующий
  (100 мс) — CV строк проверяется, автоповтор при высоком.

## 6. Фикстуры и логи

- Golden-фикстуры — в testdata; производные байты живого клиента — с атрибуцией
  происхождения; учётные данные (ключи, пароли, токены) — в фикстуры и логи не
  пишутся ни в каком виде, включая hex-дампы «для отладки».
- Трафик-лог — оракул протокольных тестов: имена пакетов и поля, которых хватает
  ассертам без ручного разбора байтов в тесте.
