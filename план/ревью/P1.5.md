## План задачи (S0, рев. 2 — после S2/S3/S4)

**Цель.** `internal/l2client` — headless-клиент (главный актив проекта по r2): TCP-подключение,
разрез потока на кадры, криптодвижки P1.1, стейт-машина login → выбор сервера → game-хендшейк →
минимальный вход (CharSelected), диспетчер по опкодам с читаемым детерминированным логом
трафика; `cmd/l2client` — тонкая обёртка. Интеграционный тест на in-process сценарий-сервере,
отвечающем golden-байтами P1.4; таблица злых входов; бенчмарк разреза потока.

**Решения (с аргументами).**

1. **Фрейминг — в `internal/protocol` (frames.go); правка ADR-0005 — только строка реестра
   горячих путей** (вопрос, прямо делегированный задаче p1.md): «Разрез входящего потока на
   кадры | protocol» — бенчмарк пути вводится вместе с кодом (правило реестра). Рёбра матрицы
   не меняются: protocol ни на что новое не ссылается, conn→protocol уже есть — переиспользование
   будущими проводами сервера без новых рёбер. Разрез — чистая функция над буфером вызывающего:
   запись провода [uint16 LE длина всей записи][тело = длина−2]. API:
   `func NextFrame(b []byte) (body []byte, err error)`: тело — срез в b (нулевая копия, буфер
   у вызывающего); потреблено всегда = len(body)+2 (выводимо, отдельного возврата нет);
   err — `ErrFrameIncomplete` (сентинел: полного кадра нет, дочитать и звать снова — прецедент
   io.ErrUnexpectedEOF) либо `ErrFrameLength` (объявленная длина < 2 — протокольное нарушение,
   детерминированный отказ, не ожидание; различение двух ситуаций — причина error-семантики
   вместо ok, in-band-признак запрещён codestyle §5). Не путать с crypto-кадром: там шифроблок
   над payload (паддинг/чексумма), здесь — длина-префиксная запись провода. Бенчмарк разреза —
   BenchmarkNextFrame рядом с функцией (критерий p1.md).
2. **Раскладка.** `internal/l2client`: login.go (LoginClient), game.go (GameClient),
   traffic.go (детерминированный форматтер трафик-лога), scenario.go (сценарий-сервер),
   doc.go; тесты integration_test.go и пофайловые. `cmd/l2client/main.go` — wire-up
   (checkdeps каталогизирует только internal/pkg; правило «cmd — только wire-up» держится
   ревью по ADR-0005).
3. **LoginClient — последовательный request-response.** Стадии-методы (ошибки — %w с
   идентификаторами стадии и опкода): Dial (TCP, TCP_NODELAY, дедлайн на соединение);
   ReadInit (первый кадр — статический BF + обратный XOR через LoginCrypt.DecryptInit,
   разбор InitView: sessionID, modulus, BF-ключ; SetKey; RSA-публичный ключ =
   crypto.RSAUnscrambleModulus + e=65537); GameGuard (WriteAuthGameGuard → GGAuthView,
   сверка sessionID); Login(user, pass) (WriteRequestAuthLoginPlain → RSAEncryptNoPadding →
   WriteRequestAuthLogin; ответ LoginOkView → ключи сессии | LoginFailView → ошибка с
   reason | прочее → ошибка протокола); ServerList (WriteRequestServerList → ServerListView);
   SelectServer (WriteRequestServerLogin → PlayOkView → ключи | PlayFailView → ошибка).
   Порядок флоу — канон Mobius: Init → AuthGameGuard → GGAuth → RequestAuthLogin → LoginOk →
   RequestServerList → ServerList → RequestServerLogin → PlayOk (подтверждён доменщиком P1.4:
   REQUEST_AUTH_LOGIN допустим только из состояния AUTHED_GG); источник порядка — Mobius
   master CT_0_Interlude (43ac8878), атрибуция — в doc-комментариях login.go/game.go.
   Каждая типизированная стадия обязана звать конструктор представления (NewInitView и т.д.) —
   доступ к геттерам только после ok; ok=false → детерминированная ошибка стадии («обрезанное
   тело»), не паника. Дедлайны: таймаут на стадию из опций (Timeout, дефолт 10с), раздельные
   SetReadDeadline/SetWriteDeadline (общий SetDeadline запрещён: затирает дедлайн соседней
   операции). Close — в API (соединение логина не бросается: FD утекает, боты фазы 4 умножат).
4. **GameClient: синхронный хендшейк → асинхронная стационарная фаза.** Порядок хендшейка —
   канон: клиент говорит первый (ProtocolVersion открытым текстом, ProtocolVersionInterlude)
   → KeyPacket открытым текстом → проверка Result()==0 (отклонение версии — ошибка стадии,
   сервер закрывает соединение) → NewGameCrypt(KeyPacketView.Key()) + Enable → AuthLogin
   зашифрованно → CharSelectionInfo | GSLoginFail → CharacterSelect → CharSelected.
   **Расхождение референса зафиксировано:** interlude-клиент читает KeyPacket ДО отправки
   ProtocolVersion (его сервер говорит первым — кастом); канон Mobius — клиент первый;
   принимается канон (правило P1.3/P1.4), расхождение — в сверку. **Механизм исполнения
   двухфазен:** хендшейк — синхронные стадии вызывающей горутины (строгий request-response,
   прямые io.ReadFull-чтения кадра из conn — как LoginClient; по канону до CharSelected
   сервер ничего не толкает, «чужой» кадр на стадии — ошибка); после CharSelected —
   стационарная фаза с горутиной чтения и командами каналом (буква p1.md «горутина чтения +
   команды каналом; общей мутации нет»): **ReadPump читает СЫРЫЕ кадры** (NextFrame;
   собственный буфер на кадр — аллокация при чтении, владение передаётся через канал) и
   шлёт их в канал кадров; **расшифровка, диспетчеризация, форматирование и TrafficLog —
   только в цикле Run** (единственный владелец криптодвижка и писатель лога: happens-before
   даёт канал кадров, Enable и Decrypt — в одной горутине; два писателя в io.Writer
   исключены). Отправка стационарной фазы — только из Run по **небуферизованному** командному
   каналу (единственный писатель conn; небуферизованность — условие контракта «команда
   после выхода Run — детерминированная ошибка»: select send/done, буферизованный канал
   молча терял бы). Завершение: Run выходит → закрывает done и conn → ReadPump выходит из
   Read и **закрывает канал кадров**; Run дренажирует канал до закрытия — кадры в полёте не
   теряются и не блокируют ReadPump (select send/done). Close идемпотентен (sync.Once);
   done закрывают и выход Run, и Close — команда после Close/выхода — ошибка, не блокировка
   (проверяется тестом). Дедлайны: SetReadDeadline на каждый Read обеих фаз (стадийный
   таймаут из общих опций; раздельные SetReadDeadline/SetWriteDeadline, общий SetDeadline
   запрещён — затирает соседний); «молчащий сервер» — злой вход.
5. **Диспетчер по опкодам + каталог-lookup (рождается здесь по решению 1+/P1.3).** В protocol
   (catalog.go): неэкспортированные мапы, построенные из таблиц на инициализации (иммутабельная
   статика — инвариант 3), + экспортированные функции только для S→C направлений (C→S клиент
   форматирует в момент отправки — lookup не нужен; встреченный C→S без форматтера —
   hex-фолбэк): `LoginServerPacketName(op byte)
   (string, bool)`, `GameServerPacketName(op byte) (string, bool)`, `GameServerExName(sub uint16)
   (string, bool)` (Ex-семейство: опкод 0xFE — именованная константа protocol, sub — uint16LE
   в байтах 1–2 тела; тип согласован с проводом и хранилищем opcodeDef.Value uint16).
   Диспетчер: **guard длины тела до любого доступа** — пустое тело (length=2) и Ex-кадр
   с телом < 3 Б → фолбэк без чтения опкода/sub (обрезанный заголовок не паникует);
   типизированный пакет — конструктор P1.4-представления; ok=false → фолбэк. Фолбэк один
   везде (определение, не отсылка): **имя из каталога (или «??») + hex-дамп первых 64 Б +
   «…N Б» при длиннее** — поток мусорных 0xFFFF-кадров не заливает лог (полный дамп — не
   лог), полный дамп нигде не печатается.
6. **Трафик-лог — детерминированный текст (golden-сравнимый).** Одна строка на кадр:
   направление («→» исходящий / «←» входящий), имя пакета, поля типизированного
   (ключ=значение, строки в кавычках; руны < 0x20 и 0x7F экранируются \xHH — терминальные
   инъекции и срыв «одной строки на кадр» исключены; грамматика фиксируется кодом форматтера
   и пинится golden-тестом) или hex-фолбэк решения 5. Никаких меток времени/адресов.
   **Учётные данные не печатаются никогда**: RequestAuthLogin логируется hex шифротекста
   (знание пассивного слушателя), plain-блок и пароль — ни в трафик-логе, ни в slog.
   ServerList: поля записей без ip/port (детерминизм golden при эфемерном порте GS-ноги
   сценария; адрес — slog Debug стадии). Форматтеры полей — только пакеты сценария флоу
   (~11 S→C); встречен типизированный без форматтера → hex-фолбэк. API — пакетные функции
   с io.Writer (состояния нет — тип-обёртка не вводится). Служебные события (стадии, ошибки,
   решения диспетчера) — slog Debug, в golden не входят; единственный писатель — Run.
7. **Сценарий-сервер.** In-process, **две ноги** в scenario.go: LS-слушатель и
   GS-слушатель (оба 127.0.0.1:0, порт GS возвращается тесту). Сценарий — **только Go-тип**
   (шаги «ожидай опкод X (проверка декодом при возможности) → ответь кадром Y»; JSON-форма
   не вводится — cmd остаётся тонкой обёрткой по букве p1.md, потребителей JSON нет: P1.6 и
   боты используют сценарий-сервер как Go-библиотеку). Ответы — golden-байты фикстур P1.4
   (fixture.Load) для пакетов с фиксированными полями (GGAuth, LoginOk, PlayOk, KeyPacket,
   CharSelectionInfo, GSLoginFail, CharSelected); **ServerList собирается WriteServerList с
   фактическим адресом GS-ноги** (fixed-порт из фикстуры не годится: конфликты в CI;
   писатель P1.4 существует, золотой байт-образ закреплён); крипто-зависимые — Init и
   RequestAuthLogin: Init собирается сценарием из фиксированных ключей (BF-ключ сценария,
   скрэмбл фиксированного RSA-модуля тестовой пары); RequestAuthLogin расшифровывается
   приватной операцией (stdlib: x509-парсинг ключа + math/big-экспонента — сырой
   NoPadding-расшифровки в crypto/rsa нет; новых зависимостей нет)
   и проверяется (user/pass сценария); **мусорный/не-той-системы блоб → ошибка шага
   сценария, не паника** (расшифрованный мусор разбирается только через AuthLoginPlainView
   с конструктором). Тестовая RSA-пара генерируется один раз, DER-байты —
   testdata/scenario_test_key.der + комментарий генерации (тестовый ключ, не секрет;
   собственные данные, не NCsoft-derived). XOR-ключ EncryptInit — константа сценария.
   Детерминизм: фиксированные ключи → фиксированные шифротексты → фиксированный лог.
8. **Таблица злых входов (клиент не паникует, завершается ошибкой).** Мусор вместо Init
   (не кратно 8 → ошибка crypto-гварда); Init с вырожденным модулусом (нулевым/малым →
   ErrBadPublicKey/ErrBadLength crypto); **валидный шифрокадр с известным опкодом и
   обрезанным телом** (Init 16 Б, LoginOk 3 Б, KeyPacket 4 Б, Ex-кадр < 3 Б …) → ok=false
   конструктора → ошибка стадии/hex-фолбэк — не паника; GGAuth с чужим Response →
   детерминированная ошибка стадии; KeyPacket с Result()==0 (версия отклонена —
   ошибка стадии, канон закрывает соединение); пустое тело кадра (length=2) и
   Ex-кадр < 3 Б → фолбэк диспетчера (guard решения 5); корректный кадр с битой чексуммой (после SetKey);
   мусорный опкод (→ диспетчер hex — не ошибка, лог); **молчащий сервер** (принял и не
   отвечает; читающий горутине — стадийный read-дедлайн → таймаут-ошибка); обрыв посреди
   кадра (EOF → ошибка); обрыв сразу после подключения; длина записи < 2 (ErrFrameLength);
   максимальная длина 0xFFFF (чтение 65533 Б тела — верх uint16; лог — усечённый дамп
   решения 5); LoginFail/PlayFail/GSLoginFail — ошибки с reason; мусорный auth-блоб на
   сценарий-сервере (решение 7). Recover-пачка на злых сценариях (мутации байтов
   golden-потока и длин).
9. **Бенчи.** BenchmarkNextFrame (protocol): разрез потока golden-байтов; 0 аллокаций на
   кадр — цель (тело = срез); ReportAllocs/SetBytes.
10. **cmd/l2client.** Флаги: -addr (адрес LoginServer), -account, -server (ID), -char (слот),
    -v (slog); пароль — env L2CLIENT_PASSWORD (не argv: ps/история шелла). Трафик-лог —
    stdout, slog — stderr (смешение делало бы golden недетерминированным).
    Критерий «прогон против записанного сценария воспроизводит лог»: TestCmdScenario — тест
    поднимает Go-сценарий (две ноги) в своём процессе и передаёт бинарнику адрес LS-ноги
    флагом -addr; stdout бинарника == golden («записанный сценарий» — Go-тип в тесте;
    JSON-форма не вводится, решение 7).
11. **Тест-план (TDD, красная фаза отдельным коммитом, красные против оракула — ожидания
    фиксируются по форматам канона/фикстур до реализации).** Unit: NextFrame (полный кадр/
    частичный/два склеенных/пустой буфер/length<2/length=2/0xFFFF); lookup-функции (выборочные
    имена + отсутствие); форматтер трафика (типизированный/неизвестный/Ex/hex/строки).
    Интеграционные: полный флоу сценарий-сервером → лог == golden; ветки отказов (LoginFail —
    reason в ошибке; PlayFail; GSLoginFail). Злые входы — решение 8 + recover-пачка.
    Конкурентный стресс: ReadPump + команды + Close/двойной Close/команда-после-выхода/
    кадр-в-окне-выхода под -race (CI). cmd: exec-сценарий == golden. Пример (Example) —
    пайплайн форматтера.
12. **Скоуп-границы.** Не входит: боты и нагрузочные сценарии (фаза 4), pcap-analyzer (P1.6),
    fuzz-цели клиента (P1.7), живой референс-сервер (контрольная точка 3 — ручная, вопрос
    владельцу на S9), реконнекты/повторные сессии, пакеты мира (hex по задумке p1.md).
