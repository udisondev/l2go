# Реестр находок P3.8

- Задача: P3.8 «Видимость: AoI/knownlist скелета» — internal/replica (+ world join-стадия)
- Ревью-профиль: S2 — инвариантщик, конкурентщик, перформансер, прагматик; S8 — + тестировщик, доменщик
- Бюджеты: план 0/2 · рестарты 0/2 · ревью реализации 0/3

## План задачи (рев. 4, S4+S5+S6 — закрытие F1–F24)

Исполнение оси 6 ADR-0004: вырожденная конфигурация (один регион ≈ одна ячейка), механика —
настоящая и не throwaway. Входы по факту кода: replica — скелет типов P0.9; world — актор/
свёртка P3.2–P3.7 (publish-шов `snapPtr` — прод-читателей нет, единственный читатель тест
region_test.go, правится вместе со швом; compose-путь `pushFrame`→`Pushes`→
`pendingPushes`→фаза B, эффекты населения применяет актор после fold); protocol — писатели
  CharInfo/NpcInfo/DeleteObject/UserInfo; матрица: world→replica есть, новых рёбер нет.

### 1. internal/replica — блоб, view, join, advisory

**Файлы:** `blob.go` (Blob+Record+Builder), `join.go` (View+Join); Advisory impl — в
`replica.go` рядом с интерфейсом. Отдельные publisher/advisory-файлы не заводятся.

- **Record-поля блоба — по потребителю CharInfo/NpcInfo/UserInfo** (полные пейлоады, ось 3):
  `{EntityID (вечный), X/Y/Z int32, Heading int32, Moving bool, Type (player|npc), Name string,
  ClassID int32, Race int32, Female bool, HairStyle/HairColor/Face int32, TemplateID int32 (npc),
  Flags uint32 (входы предиката видимости — инвиз/GM; фаза 3 не ставится, но поле — шов
  переоценки предиката, тестируется синтетическим флагом), Epoch uint64 (эпоха записи —
  источник инкремента появляется с хэндоффами фазы 4; фаза 3 пишет 0; потребитель — Snapshot
  advisory и max-epoch-дедуп фазы 4)}`. Строки — параллельный массив. Per-template константы
  (MAtkSpd/PAtkSpd/SwimSpd/мультипликаторы/коллизии/Title/Running) в блоб не входят —
  источник при compose: **persist.Template расширяется портом той же задачи (F22)**:
  basePAtkSpd=300, swim 50/50, collision male 9/23 (файл HumanFighter — тот же, что у
  порта P3.3); мультипликаторы — плейсхолдеры по прецеденту userInfoOf (производные
  статы — до формул фазы 4), Title="", Standing=true, Running=false (канон:
  Creature._isRunning=false на спавне). Чекпоинт F24: ObjID кадров — маппинг
  ObjectIDBase+EntityID по прецеденту encode/enterworld.go (иначе таргетирование
  разъедется).
- **Blob** — иммутабелен после сборки; **arena-укладка**: 1–2 бэкинг-слайса (числовой + строковый),
  нарезаемых на подслайсы колонок — ≤3–4 аллокации на поколение (ADR-0004 ось 3 «1–2» —
  считаем бэкинги+структуру, число фиксируется в машинном тесте). Поля: SoA-колонки,
  `Gen uint64` (+1 на публикацию), `Members` и `Dirty` — битмапы слотов. Слоты стабильны, пока
  житель жив; реюз слота детектируется читателем по вечному id. Отсортированный id-индекс в
  блобе отсутствует (F12): join-путь по id не ищет, advisory — линейный скан по SoA-id с
  комментарием профиля (осознанное отклонение от «O(1)» реестра ADR-0005 — актуализация
  структуры с потребителем фазы 4; записано в реестре задачи).
- **Builder** (издательская сторона, собственность горутины региона): `Update(id, Record)`
  (upsert полей жителя) / `Remove(id)` / `Build(vs *Blob) *Blob` — плотные стабильные слоты
  (первый свободный индекс; назначение слота живёт в бухгалтерии Builder — инкрементально-
  отсортированный слайс (id, slot) по прецеденту residents, binary search вставка/удаление);
  **Build всегда копирует** (алиасинг с хранилищем Builder запрещён — тест-читатель держит
  блоб N, регион исполняет полный шаг N+1, F6). **Дифф вычисляется в Build против `vs` —
  последнего опубликованного блоба, не против состояния Builder** (R1): Members-дифф и Dirty —
  сравнением слотов с `vs` (O(#слотов) слов — тот же класс, что копирование); инкрементальных
  dirty-битов в Builder нет. Неопубликованное поколение не существует для диффа: паника до
  publish → следующий Build вычисляет тот же дифф заново — события не теряются.
- **View** (наблюдательская сторона, собственность горутины региона): `knownSlots` битмап слотов
  + `knownIDs []EntityID` (слот-индексированный снимок) — pair-тест O(1) array-indexed без
  хеша. Представление вырождено (один издатель на ячейку; F9): подъём сетки фазы 4 меняет ключ
  на (издатель, слот) либо отсортированное множество ID — механика (гистерезис, два случая
  ухода, предикат) не меняется. В модель сущности/чемодан/Dump не входит; поля неэкспортированы.
- **Join — чистая функция событий, идемпотентная по view**: `(blob, diff, view, obsDirty,
  obsX/obsY/obsZ, enter, exit, предикат) → события {вводы, удаления}` в терминах слотов;
  повторный вызов с тем же view событий не порождает (ввод только для неизвестного id — это и есть
  защита от дублей при доигрывании паник-шага). Diff — явный параметр (битмапы Members-диффа
  и Dirty от Build); obsDirty — собственное движение/флаги наблюдателя → пересчёт его пар по
  слотам Members; полный проход по населению — только при пустом view (рождение наблюдателя).
  Гистерезис: ввод при d ≤ enter, удаление при d > exit (**d — 3D dx²+dy²+dz², F21**:
  aCis checkIfInShortRadius вызывается с includeZAxis=true — Z входит, многослойность
  мира r1 иначе даёт фантомы сквозь перекрытия с P3.9). **Условие вызова (F5):**
  Join для наблюдателя исполняется только при непустом diff (скан битмапов O(n/64 слов),
  без чтения пейлоадов) или obsDirty; idle-тик — ноль join-пар. **Удаления абсолютны по
  вечному id (F19):** слот Build, занятый другим id, чем в knownIDs наблюдателя, — это
  удаление старого + кандидат-ввод нового (не «известен»); swap-семантика покрывает
  реюз слота в один шаг. **Reconcile после паник-шага (F19):** флаг «join был, публикации
  не было» (**ставится на входе join-стадии**, до первой мутации view — инвариант
  «флаг снят ⇒ reconcile прогнан» тривиален; снимается в publish): шаг с выставленным
  флагом прогоняет абсолютную свёртку всех view против Build (view \ Build → удаления
  по id, Build \ view → вводы по дистанции/предикату, пересечение — не трогается:
  гистерезис reconcile'ом не нарушается) — **раньше и вне F5-условия** (reconcile не
  зависит от диффа). Закрывает изменения,
  сократившиеся между Build и публикацией (трасса: спавн A → паника phaseLog → логаут A
  в N+1: дифф против опубликованного пуст, а CharInfo(A) едет хвостом → без reconcile
  вечный фантом). Само событие паники — recover механизма P3.2, reconcile — доигрывание.
  Grace-наблюдатель (LinkDead, сокет мёртв): join продолжает вести его view — кадры в
  мёртвый коннект идемпотентны (encode no-op), стоимость ограничена grace-окном.
  Два случая ухода: исчезновение слота без маркера → немедленный DeleteObject; маркеры
  переезда в фазе 3 не порождаются (юнит-тест на пустоту). Self-пара исключается
  вызывающим (world-стадия; тест — компонентный).
- **Числа (OQ-3, атрибуция в коде)**: enter=1800, exit=2700 — aCis PcKnownList (GPLv3):
  watch=max(1800, 3600−20×|known|) — берём пол (динамика — фаза 4+); forget=round(1.5×watch).
  Утверждает владелец на ✅.
- **Предикат видимости** — одна функция пары `Visible(obsFlags, tgtFlags) bool` для репликации
  и advisory; фаза 3: Flags==0 → true; изменение Flags записи = dirty → переоценка всех пар
  (не только новичков). Гео-LOS отсутствует — документированное исключение оси 4 (выжимка
  OQ-8 — конец реестра). **Судьба скелетного MembershipHeader (F23):** дубль
  Generation/Moving не заводится — Moving-поле типа остаётся под маркеры переезда фазы 4
  (не порождается, юнит-тест на пустоту), Generation живёт в Blob; при реализации тип
  воссоединяется с Blob-заголовком или остаётся скелетом P0.9 по прецеденту GroundItem —
  решение фиксируется кодом, не планом.
- **Advisory impl**: `Snapshot(cell, id) (Snapshot, bool)` — Load последнего опубликованного
  блоба, линейный скан по id; **Snapshot — чистое значение** {Entity, X/Y/Z, Epoch} (R2:
  факт успеха — в ok-параметре сигнатуры; дубль полем не кодируется) — потребитель фазы 4
  (range-чек) обязан получить значение, а не только адрес.

### 2. internal/world — join-стадия актора, публикация, advisory-логирование

- **Стадия `phaseJoin` между phaseEffects и phaseLog** (население шага готово, лог порций
  join не касается; маркер паники phaseJoin + фазовый счётчик, F11):
  - `Build` блоба из residents (спавн/деспавн шага уже применены эффектами; дифф — против
    последнего опубликованного блоба, см. §1 Builder/R1);
  - для каждого жителя-игрока — условие вызова (§1) → `replica.Join` → события → **apply view
    и генерация кадров немедленно в join-стадии** (R1): кадры в `pendingPushes` той же
    стадией — механика доставки едина со слитком входа P3.7; выжидание «после успешной
    выкладки» из рев. 2 снято (окно потери join-событий при панике между стадиями —
    трасса R1). **Внутри события порядок „кадр → apply"** (Ост-4 замыкания): кадр кладётся
    в pendingPushes раньше мутации view — паника в межоперационном окне сводится к
    идемпотентному повтору ввода, окно вечной потери исчезает конструктивно;
  - вводы: WriteCharInfo (player) / WriteNpcInfo (npc — каркас, наполняется P3.10, тестируется
    синтетической записью); удаления: WriteDeleteObject; несколько вводов — по слотам блоба
    (детерминизм). Позиционные апдейты K∩M (CharMoveToLocation/StopMove) — каркас: место в
    join-цикле, наполнение P3.9 (в фазе 3 сущности неподвижны, события не порождаются).
  - self-поток — из приватного состояния владельцем (UserInfo — P3.7); join пару (self,self)
    исключает.
- **Доставка кадров переживает панику (F2/R1):** `pendingPushes` убираются из resetDrain;
  обнуление — в конце успешной фазы B после выталкивания; при панике любых фаз после
  join-стадии хвост доотправляется следующим шагом (кадры идемпотентны: повторный спавн =
  обновление — OQ-5 не предпосылка корректности; Join идемпотентен по view, дифф строится
  против последней публикации — паник-шаг доигрывается без дублей и потерь). Существующее
  окно для слитка входа P3.7 закрывается той же правкой. Порядок фазы B: выталкивание
  pendingPushes (хвост + свежие join-кадры) → обнуление вытолкнутого → outbox-письма.
- **Публикация:** блоб занимает шов P3.2 — `snapPtr atomic.Pointer[replica.Blob]`, Store в
  фазе publish (только горутина региона); `snapshot{tick}` и тип удаляются (читателей нет,
  F8). Advisory Load — тот же указатель.
- **AdvisoryRead(cell, id)** — world-обёртка: чтение через advisory impl + **логирование
  значения** в порцию: AdvisoryIn расширяется {X,Y,Z int32, Epoch uint64, Found bool}
  (Found — из ok-параметра чтения, R2; **при Found=false значения пишутся нулями** —
  запись детерминирована для D6-реплея); версия формата лога порций +1 (рутинная правка
  portionlog + ридер). Потребитель-геймплей — фаза 4 (аггро); шов процедуры и представления
  готов.
- **Бёрст новичка vs byteCap encode.Stage (F10):** риск записан; wire-up byteCap берётся с
  запасом на бёрст NpcInfo среза зоны (числа — после P3.10, в журнал); порционность вводов —
  не в фазе 3; метрика capDrops на входе наблюдается.
- Никаких новых Kind/писем; матрица ADR-0005 без правок.

### 3. Тесты

- property: join = set-equality «население ∩ радиус» (синтетические позиции, граница ±1);
  гистерезис: дуга по краю — нулевой churn, ровно один ввод/один DeleteObject;
- **idle-тик — 0 join-пар** (машинный счётчик шва Join, F5); дифф битмапов — без чтения
  пейлоадов (счётчик чтений колонок);
- слоты: деспавн+рождение в ячейке — молодой id в старом слоте не читается как старая запись;
- публикация: только владелец, Store в фазе publish, **иммутабельность через полный следующий
  шаг** (читатель держит блоб N, регион строит N+1 и мутирует Builder — под `-race`, F6);
- view set недоступен игровой логике (пакетный тест компилируемости);
- предикат: синтетический Flags → ввод/удаление; переоценка всех пар;
- advisory: N чтений → N записей **со значениями** в логе порций (F1); приватность типов;
- маркеры переезда не порождаются (пустота); два случая ухода;
- **паника phaseJoin/phaseLog/phaseB после join-событий → доотправка хвоста следующим шагом
  без потерь и дублей** (инъекция паники: спавн в шаге N + паника → старожил получает
  CharInfo ровно к шагу N+1; при панике до apply — повторный ввод идемпотентен; счётчик
  доставки, F2/R1);
- **reconcile-интерливинг (F19):** спавн A в N → паника phaseLog → логаут A в N+1 →
  наблюдатель получает CharInfo(A) хвостом И DeleteObject(A) reconcile-свёрткой того же
  шага N+1 — фантома нет (машинный ассерт последовательности кадров);
- **3D-дистанция (F21):** равная 2D-дистанция с разными Z — ввод/удаление по dx²+dy²+dz²
  (канон includeZAxis=true);
- **swap слота:** деспавн+рождение в один шаг в один слот — старожил получает
  DeleteObject(старый) и CharInfo(новый) парой (F19-семантика абсолютных удалений);
- компонентный: второй игрок входит → взаимные CharInfo тем же шагом; логаут → DeleteObject
  у оставшегося; e2e-хвост взаимной видимости двух headless-клиентов (база КТ-4);
- **аллокации блоба: ≤ именованной константы на поколение стабильного населения** (машинно,
  F3); **idle-бюджет шага переформулируется**: TestRegionStepIdleAllocBudget P3.2 (порог 2:
  rand.New + снапшот) после P3.8 — «минус удаляемый snapshot{tick}, плюс аллокации блоба
  ≤K» (точный порог — константой в тесте, F3-хвост замыкания).

### 4. Бенчи (baseline → benchmarks/, benchstat-совместимо: b.Loop, -count=10, шапка — F4/F14)

- **cold-join**: блоб 100/1000, наблюдатель в центре, всё население внутри enter, view пуст;
  метрика нс/пара, знаменатель — машинно посчитанные введённые пары; якорь ~7–11 нс/пара —
  порядок величины, в журнал не в ворота;
- **steady-dirty**: полный view, все слоты dirty (модель города P3.9+, данные для решения о
  сетке 3×3 — остаточный риск плана);
- **публикация**: Build+Store 100/1k/10k, ReportAllocs, аллок-подпас (датчик GC outbound-пути).

### 5. Анти-скоуп

LOD/бюджет/тировать (фаза 6), сетка 3×3/стенсилы (фаза 4), маркеры переезда/hold-last/
max-epoch (типы присутствуют, не порождаются), слуги/предметы, динамика радиуса aCis (фаза 4+),
NPC-спавны (P3.10), порционность вводов новичка (по числам P3.10), пул блобов (фаза 6).

## Выжимка OQ-8 (дистанционность известности — основание исключения LOS)

только `Util.checkIfInShortRadius(getDistanceToWatchObject(...), _activeObject, object, true)`

предиката репликации (ось 4) подтверждено источником.
