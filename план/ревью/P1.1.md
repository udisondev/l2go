## План задачи (S0, рев. 3 — после S2/S4, S5 и S6)

**Цель.** `internal/crypto` — криптодвижок протокола Interlude 746: Blowfish (LE-семантика
L2J), XOR-каскад game-канала, checksum, паддинг, XOR-pass Init, RSA-скрамбл логина.
Golden-векторы + property-раундтрипы + бенчмарки. Порт семантики из `udisondev/interlude`
(34fe4c86); `la2go` (1eed6cb5) — только BF-независимые вещи (скрамбл-константы, ориентиры
бенчей): его Blowfish — BE-ядро без свопов, байтовым оракулом не является. Живой трафик
появится позже (КТ-1) — конструкция обязана принять живые фикстуры без переделки.

**Решения (с аргументами).**

1. **Ядро Blowfish — `golang.org/x/crypto/blowfish`** (BSD-3, GPLv3-совместимо); своя
   реализация алгоритма не пишется. Аргумент: оба референса используют x/crypto; владеть
   криптопримитивом без измеримой потребности — против простоты. Первая внешняя зависимость
   проекта: критерий приёмки в план/p1.md правлен явно; прецедент в журнале; машино-проверка —
   allowlist require в checkdeps (F19). Откат (свой порт Blowfish) — записан, применится по
   несогласию владельца на приёмке.
2. **LE-семантика L2J поверх BE-ядра** байтовыми свопами вокруг блока (как interlude):
   Java `BlowfishEngine` читает полублоки little-endian (сверено по независимым Java/C++
   исходникам свежим взглядом S6). Инвариант закрыт golden-вектором, различающим LE/BE
   (генерируется запуском interlude@34fe4c86; перекрёстная проверка «interlude ≠ la2go на
   одном блоке» в генераторе векторов — машиноисполнимое напоминание о BE-дефекте la2go).
3. **Клиентская сторона — первичный потребитель фазы 1.** LoginCrypt двухфазен: NewStatic
   (статический BF) → расшифровка Init (`DecryptInit`: статический BF + DecXORPass, инплейс)
   → `SetKey(dynamic)` из полей Init → динамические Encrypt/Decrypt. GameCrypt —
   `NewGameCrypt(wire [8]byte)`: проводные байты KeyPacket как есть, без обфускации
   (pcap-analyzer кладёт data[2:10] в ключ напрямую); контракт среза (какие 8 байт передаёт
   P1.4 для флэворов KeyPacket 0x2E/0x00) — на стороне P1.4; статическая половина — константа
   пакета. Жизненный цикл: динамические операции до SetKey, повторный SetKey, DecryptInit
   после SetKey → детерминированные ошибки (таблица злых входов).
4. **Без внутренней синхронизации.** Движок на соединение; владелец — горутина соединения.
5. **Единый API над срезом кадра: без offset-параметров и без InPlace-дублей.** Все функции
   принимают точный срез; guard'ы на входе (пустой вход; кратность 8 для BF-семейства; 128
   байт для RSA); нарушение → ошибка `%w`, паник нет нигде. Кадрирование (P1.5) выдаёт
   точные срезы. Экспорт `MaxFrameOverhead = 24` (максимум роста кадра: static 8+8+8;
   документировать затирание байтов в [len(payload), конец кадра)).
6. **Ничего случайного в фазе 1.** XOR-ключ Init — параметр; генерирующие конструкторы и
   `RSADecryptNoPadding` (CRT, тайминг) — фаза 3.
7. **Паддинг login-кадров: приём толерантный, отправка — форма CT0/interlude (провизорно).**
   Свидетели расходятся: классический L2J (net.sf.l2j, зеркала) — безусловное добивание до
   кратности 8, без хвостового блока; текущий Mobius CT0 Interlude (`LoginEncryption.java`,
   GitLab, прочитан напрямую ведущей сессией 2026-09-09) — безусловное добивание + хвост +8
   в обеих ветках, побайтово совпадает с interlude Go; la2go — условное добивание (и BE-ядро);
   эмпирика pcap-analyzer («real servers omit the extra 8-byte tail») — без хвоста,
   направление трафика не указано. Решение: **Decrypt принимает любой кадр, кратный 8**
   (длина — из u16-префикса, который идёт плейнтекстом и вне области шифра, — подтверждено
   тремя источниками; checksum — последнее слово кадра), **Encrypt строит кадр формы
   CT0/interlude** (единственная форма с живым побайтовым Go-оракулом); формула размера
   изолирована в одну внутреннюю функцию; арбитр — живые дампы КТ-3 (первый пункт P1.6);
   флип одношовный.
8. **GameCrypt — стандартный L2J-режим:** 16-байтовый ключ (8 из провода + 8 статических),
   XOR-каскад `i&15` с prev=шифрбайт, раздельные in/out ключи, LE-u32 счётчик
   `key[8:12] += size(payload)` после пакета, Enable после ProtocolVersion (до Enable —
   прозрачный проход, тест обязателен). Кастомный режим живых серверов (`(i+1)&7`) — не
   переносится; дамп такого сервера — флаг владельцу КТ-3.
9. **Атрибуция** — заголовок каждого файла: источник-референс с коммитом; значимые функции —
   по месту.

**Состав пакета.** Экспорт: `LoginCrypt`, `GameCrypt`, `RSAScrambleModulus`,
`RSAUnscrambleModulus`, `RSAEncryptNoPadding`, `MaxFrameOverhead`. Внутренние: blowfish-обёртка
LE, append/verifyChecksum, enc/decXORPass, frameSize (изоляция канона).

| Файл | Содержимое |
|---|---|
| `login.go` | LoginCrypt: NewStatic, DecryptInit (стат.BF + DecXORPass, guards), SetKey, EncryptInit(payload, xorKey)→кадр, Encrypt(payload)→кадр (checksum + frameSize + динам.BF), Decrypt(кадр)→**расшифрованный кадр целиком** (динам.BF; битый checksum → ошибка; любой %8 кадр; длину payload криптослой не восстанавливает — парсер P1.4/P1.5 читает поля и игнорирует хвост) |
| `game.go` | константа статической половины; NewGameCrypt(wire [8]byte); Enable/IsEnabled; Encrypt/Decrypt(кадр) по направлениям; до Enable — no-op |
| `blowfish.go` | внутренняя обёртка x/crypto: LE-свопы, guards; статический 16-байтовый ключ Init |
| `checksum.go` | внутренние: appendChecksum, verifyChecksum, encXORPass, decXORPass |
| `rsa.go` | RSAScrambleModulus/RSAUnscrambleModulus (128 байт, иначе ошибка), RSAEncryptNoPadding (big.Int) |

**Тест-план (TDD: тесты раньше кода, в дифе виден порядок).**

- **Все BF-проходящие golden-векторы генерируются только запуском interlude@34fe4c86**
  (единственный LE-референс; la2go исключён — BE-ядро). RSA: собственный фиксированный
  RSA-1024-ключ пиннится фикстурой, векторы — запуском interlude на нём (в тестах la2go
  байтовых векторов нет). Генератор векторов: буфер зануляется (референсы оставляют мусор в
  паддинг-хвосте static-ветки), xorKey фиксирован. Перекрёстная проверка interlude ≠ la2go
  на одном блоке — в генераторе.
- Golden-покрытие: BF-блок LE (дискриминирует LE/BE); checksum; XOR-pass; кадр Init
  static-ветки и dynamic-кадр — форма CT0/interlude, на дискриминирующих размерах
  (static payload ≡ 0 mod 8 — различает безусловную/условную; dynamic payload ≡ 4 mod 8 —
  различает все три формы); GameCrypt — последовательность ≥2 пакетов (счётчик меняет
  поток); RSA-скрамбл и no-padding на пиннутом ключе.
- **Тест дешифр-толерантности:** один payload, зашифрованный тремя формами кадра
  (классическая-16 / CT0-24 / la2go-8 для выровненного случая), — Decrypt + verifyChecksum
  проходят все три. Фикстуры трёх форм строятся нашим шифратором через test-локальные
  варианты frameSize (запуск la2go исключён — BE-шифртекст, F11). Единственная по-настоящему
  фальсифицируемая защита «клиент неверен на реальном сервере» без живого трафика.
- Property: BF раундтрип (случайные ключи, 8–1024 кратно 8); LoginCrypt полный цикл
  EncryptInit→DecryptInit и Encrypt→Decrypt; GameCrypt встречный (оба направления, много
  пакетов); verifyChecksum: порча байта → false.
- Таблица злых входов (все → детерминированная ошибка, не паника): пустой кадр; кадр не
  кратен 8 (BF-семейство); size=0; гигантский заявленный размер против малого буфера; битый
  checksum → ошибка Decrypt; RSA-вход ≠ 128 байт; пустой/длинный ключ BF; **динамические
  операции до SetKey; повторный SetKey; DecryptInit после SetKey**. Отдельно: до Enable —
  прозрачный проход.
- Аллокации (`testing.AllocsPerRun` == 0 после инициализации): GameCrypt.Encrypt/Decrypt;
  LoginCrypt.Encrypt/Decrypt; appendChecksum/encXORPass через публичные пути. Буфер — кадр +
  MaxFrameOverhead, до цикла; контракт запаса документирован у обоих encrypt-методов
  одинаково.

**Бенчмарки.** `b.Loop()`, `b.ReportAllocs()`, `b.SetBytes(size)` — все. BenchmarkBlowfish{Encrypt,Decrypt}
и BenchmarkGameCrypt{Encrypt,Decrypt} — кадры 40/256/1456. BenchmarkLoginCrypt{Encrypt,Decrypt} —
payload 40/256/1440 → кадры 56/272/1456 (форма CT0: p+4 → безусловное добивание → +8; кадр 1456
совпадает с BF/GameCrypt-бенчами); буфер = кадр + 24, до цикла. Decrypt-бенчи: восстановление
входа — вне таймера (StopTimer/StartTimer) либо честный EncryptDecrypt-раундтрип; паттерн la2go
(Decrypt+Encrypt в замере, ns/op ×2) не переносится; GameCrypt-дешифр восстановления не
требует. Якорь la2go ~864 нс — BE-реализация без свопов, не like-for-like: только порядок
величины; дельта «обёртка−голый блок» — локальным бенчем голого блока, если/когда LE-свопы
возьмут в оптимизацию. Baseline: benchstat-совместимо (`-count≥10`), окружение (машина, go
version) — в журнал; единичный прогон — не baseline. Per-connection стоимости (создание
шифра, RSA) — фаза 3.

**Скоуп-границы (не входит).** Кадрирование потока — P1.5; генерация ключей,
RSADecryptNoPadding, CRT — фаза 3; статический ключ GS↔LS — фаза 3; кастомный XOR-режим —
нет (флаг КТ-3); плейнтекст-Init и флэвор KeyPacket 0x00 — фикстуры обоих флэворов в P1.4,
клиент обрабатывает по фактуре, флаг КТ-3; per-connection бенчи — фаза 3; интеграция с
conn/encode — фазы 3+.

## Отклонения реализации от плана (S8, F27)

1. **Сигнатуры `EncryptInit(dst, payload, xorKey) (int, error)` / `Encrypt(dst, payload) (int, error)`** вместо плановых «EncryptInit(payload, xorKey)→кадр». Мотив: критерий 0 аллокаций — буфер вызывающего (конвенция владения пакетом данных); dst-форма возвращает размер кадра без аллокации результата.
2. **`NewLoginCrypt`** вместо планового `NewStatic`. Мотив: симметрия с NewGameCrypt, godoc-самоочевидность (конструктор пакета, а не фазы); фаза выражена методами DecryptInit/SetKey.
3. **Шесть экспортированных сентинел-ошибок** (ErrBadKey, ErrKeyAlreadySet, ErrKeyNotSet, ErrStaticPhase, ErrBadChecksum, ErrBadLength) сверх экспорт-списка плана. Мотив: потребители P1.4/P1.5 ветвятся по errors.Is (lifecycle-обработка клиента); идентификация строками запрещена codestyle.
4. **LE/BE-перекрёстная проверка в тесте пакета**, а не в генераторе векторов. Мотив: генератор живёт вне репо; тест самодостаточен и падает при рефакторинге свопов.
5. **`mustBFCipher` паникует** на невалидной константе staticLoginKey. Недостижимо (константа 16 байт; каждый тест создаёт движок — служит инвариантом); паника построения, не входа API.
6. **TDD-порядок** закоммичен одним слайдом (красная фаза не наблюдаема в истории). Долг процесса: со следующей задачи — отдельный коммит красной фазы или SHA красного прогона в журнал.
