# Реестр находок P2.1

- Задача: P2.1 «Рамка датапака + категория "предметы"» — [план/p2.md](../p2.md)
- Ревью-профиль: S2 — инвариантщик, безопасник, перформансер, прагматик; S8 — + доменщик,
  тестировщик
- Бюджеты: план 1/2 · рестарты 0/2 · ревью реализации 0/3

## План задачи (S0/S1 + S2/S4, рев. 2)

**Цель.** `internal/data` — каркас загрузки статики (категории, контекст, отчёт валидации,
манифест входов) и первая категория «предметы» поверх него; `cmd/l2data check` — отчёт и код
выхода; синтетическая фикстура в testdata; машинная проверка «данные дистрибутива в репо не
попадают»; fuzz-цель малформленного XML в CI-смоуке.

**Контекст S0 (закрытые вопросы).**

- Канон дистрибутива — Mobius Interlude: GitLab-зеркало expcero/L2J_Mobius, master 43ac8878
  (тот же коммит, что в фазе 1), поддерево `L2J_Mobius_CT_0_Interlude` скачано в
  `C:\projects\_refs\mobius-interlude\`; корень данных = `dist\game\data` (81 МБ; предметы —
  `stats/items/`: 93 XML верхнего уровня по диапазонам ID + подкаталог `custom/` (4 XML,
  7 предметов) + `documentation.txt`). Решение владельца (КТ-1): Mobius Interlude, скачивание
  агентом в `_refs`, CI — только синтетика.
- Формат предмета — property-bag: `<item id type name>` + `<set name val/>` + `<stats><stat
  type>значение</stat></stats>`; кроме того встречаются `<skills>`, `<conditions>`,
  `<capsuled_items>` (значимая часть: 2352 stats-блока, 1660 skills, 500 conditions на наборе).
- Объём реального набора (замеры S2): 9208 предметов, 83 875 set-пар (~9.1/предмет), 9463
  stat-записи, 42 уникальных set-имени, 13 stat-типов; максимум файла 119 КБ; типы предметов —
  ровно {Weapon, Armor, EtcItem}; дубликаты ID между базой и custom: 733, 6593–6595 (custom
  несёт и новые предметы: 13531, 13534, 50000).

**Решения (с аргументами; правки рев. 2 помечены ◆).**

1. **Источник истины семантики — Java-ридеры канона, не наша интерпретация.** ◆ Цепочка
   оракула: `DocumentItem.java` (XML → StatSet-bag) → `DocumentBase` (`parseBeanSet`/
   `parseTable`/`getValue`: trim значений, фолбэк «val → текст тега», `#`-ссылки, тихий пропуск
   пустых) → `ItemTemplate.set(StatSet)` (словарь set-имён → поля). Атрибуция всех трёх:
   `// семантика: L2J_Mobius DocumentItem/DocumentBase/ItemTemplate`. Аргумент: xsd описывает
   структуру, но не значения set-имён и не семантику разбора значений (F16).
2. **Форма записи: типизированные поля + raw set-bag.** `Item`: типизированные поля минимального
   потребителя фазы 3 (инвентарь/дроп/подбор): ID, Name, Type, Weight, Price, Stackable,
   CrystalType, CrystalCount, Material, BodyPart — точный список фиксируется при реализации по
   ItemTemplate. Raw-bag хранит: set-ключи как есть; stat-записи с префиксом `stat.`
   (`stat.pAtk → "8"`) — статы фазы 4 не теряются (F3). Прочие дочерние элементы (`skills`,
   `conditions`, `capsuled_items`) — пропуск с счётчиком по имени элемента в отчёте; их
   типизация/свёртка (канон сворачивает skills в set-ключи) — P2.6 (F3). ◆ `Type string` +
   счётчик unknown-типов в отчёте — без enum-sentinel: «неизвестный тип» — широта данных
   (решение 7 фазы), не целостность; типизация в enum — при потребителе фазы 4 (F2, П-м2).
   ◆ Оценка памяти raw-bag (осознанная цена «ничего не теряется»): ~8–10 МБ на items (84k пар:
   map-инфраструктура + строки), фазовый состав ~35–45 МБ; интернирование ключей (42 уникальных
   на 84k вхождений) — разрешённая эволюция по измерению, не требование сейчас (П-Н1).
   ◆ Bag не экспортируется наружу map-ом: неэкспортируемое поле + доступ по ключу
   `Set(key string) (string, bool)` — map целиком наружу не отдаётся ни геттером, ни копией
   (И-Н4, И-нФ-S5).
3. **Декодер — token-стриминг `encoding/xml`.** Один ручной проход `Decoder.Token()` по файлу.
   Аргумент: внутренности item — разнородные элементы (set/stats/…), аннотированная структура
   их не покрывает; токен-режим даёт точное место ошибки и един механизм на все категории.
   ◆ Довод про аллокации снят: токены аллоцируют строки (значения атрибутов — копии);
   «меньше промежуточных структур, чем Unmarshal» — корректная формулировка, «0 аллокаций» —
   нет (П-Н3). Скорость некритична: build-time путь, вне реестра ADR-0005. ◆ Потолок входа:
   `io.LimitReader` на 16 МБ + 1 байт с явной проверкой превышения — различимый код «файл
   превышает потолок», а не загадочный «обрыв XML» (максимум датапака 119 КБ, запас ×130;
   константа с комментарием) — гигантский атрибут не валит процесс OOM (Б-3, Пф-нФ-S5).
   ◆ Место ошибки — `файл:строка`
   (трекинг `\n` при стриминге), офсет — внутреннее поле (П-м4; план фазы требовал
   человеко-адресуемость).
4. **Каркас категорий.** ◆ В P2.1 — один загрузчик `loadItems`; в `Load` — слайс функций-
   загрузчиков; интерфейс категории не заводится до ≥2 реализаций (P2.2), codestyle §2 (П-м3).
   ◆ Тип результата — `*data.Static` (не `*Data`: `data.Data` — повтор имени пакета,
   codestyle §4) (П-м1). ◆ Граница ошибок: ошибки данных — записи отчёта, Load читает всё до
   конца и возвращает `(*Static, *Report)` (Static == nil только при фатальных условиях FS —
   корень не читается); `error` из Load — только фатальные FS-условия; exit 1 = в отчёте есть
   записи-ошибки (П-м5). Отчёт: записи {категория, файл, строка, ID, код} и счётчики {файлов,
   записей, unknown-ключей (top-N), unknown-типов, пропущенных элементов по именам, пропущенных
   файлов, ошибок}. Политика: дубликат ID / битая структура / кривое число / отсутствующий
   обязательный атрибут = ошибка; id ≤ 0 — ошибка (ParseInt пропускает знак молча —
   Б-нФ-S5); неизвестный set-ключ / неизвестный тип / пустое значение =
   счётчик (решение 7 фазы; семантика канона: пустой set пропускается тихо — переносим с
   счётчиком) (F2, Б-8).
5. **Состав входов категории items.** ◆ Обход — только верхний уровень `stats/items/*.xml`
   (93 файла, как канон: нерекурсивный `listFiles`); подкаталог `custom/` не грузится: его
   override-семантика канона (custom заменяет базу) противоречит целостности «дубликат =
   ошибка», контент — события/маунты фаз 5+; пропуск виден: счётчик «custom: пропущено N файлов»
   в отчёте, манифест — по фактически потреблённым 93. Судьба custom (переопределение против
   отказа) — отложенное решение, фиксируется здесь; прогон и числа оперируют составом 93 (F1,
   4 роли).
6. **Граница fs.FS + манифест входов.** `fs.FS` — единственный вход (os.DirFS в cmd; тесты —
   os.DirFS над testdata). ◆ Манифест: SHA-256 (stdlib), детерминированный фрейминг — по
   отсортированному списку {путь, SHA-256 содержимого}: h.Write(le64(len(path)) ‖ path ‖
   contentHash) — однозначность склейки; не криптографическая граница (данные локальные), а
   ключ детерминизма и будущий ключ кэша P2.7 (Б-4). Возвращается при загрузке: идентичность
   данных для реплея (D1–D6). Расширение на весь корень — P2.7.
7. **`cmd/l2data check <root>`** — тонкий wire-up: флаги/вывод отчёта/exit 0|1; логика целиком
   в пакете. Печать: сводка счётчиков + перечень ошибок + top unknown.
8. **Синтетическая фикстура** — `internal/data/testdata/synth/`: 4–6 предметов (weapon с
   stats-блоком, armor, etcitem stackable, arrow и т.п.) по формату канона с собственными
   ID/именами/значениями; ◆ имена не совпадают с именами предметов канона (лицензионная
   гигиена). Коммитится. Злая синтетика рядом: обрезанный XML, дубликат ID, кривое число, ◆ id
   за границами int32, отсутствующий обязательный атрибут, неизвестный ключ/тип.
9. **Проверка «данные дистрибутива не в репо»** ◆ — единое правило по всему дереву репо
   (рекурсивный WalkDir, кроме .git): каждый `.xml` ∈ белый список путей (новый xml-файл
   в любом месте репо = правка теста, сознательный акт); файлы с паттерном имён диапазонов
   дистрибутива (`NNNNN-NNNNN.xml`) запрещены везде, даже в списке. Порог размера исключён:
   аргумент «размер различает» ложен (ctf_event.xml — 1961 Б) (F4, Б-1/2, П-м7/м8, И-Н5).
10. **Fuzz** — `FuzzLoadItems`: мутации байтов вокруг синтетики → Load не паникует, возвращает
    отчёт (любые данные) или фатальную FS-ошибку; seed — синтетика + злые файлы. Добавляется
    в CI-смоук (10 с). ◆ id — `type ItemID int32`, разбор `ParseInt(…, 10, 32)` (переполнение —
    ошибка, не молчаливый каст) (Б-8).

**План тестов.** Golden синтетика→поля (таблица по предметам); raw-bag: невиденные set-ключи и
`stat.*` сохраняются + счётчики; ◆ пропуск `skills/conditions` виден счётчиком; злые входы
таблицей (обрезанный файл, пустой файл, чужой корневой элемент, кривые int/bool, ◆ id за
границами int32, отсутствующий обязательный атрибут, дубликат ID — у каждой место `файл:строка`
и код); ◆ trim/пустые значения — семантика канона (trim; пустое — пропуск + счётчик); манифест
детерминирован и чувствителен; ◆ custom-пропуск отражается в отчёте и манифесте (93, не 97);
◆ канонический дамп загруженных записей (детерминированный порядок полей/записей) — golden-
сравнение и форма проверки эквивалентности для P2.7 (вход владельца: round-trip
«XML → структуры → X → структуры == структуры» — принят в этой форме; побайтовая идентичность
XML не цель: форматирование и сознательно пропущенные элементы); `check` exit-коды 0/1 на
чистой/грязной синтетике; ◆ xml-гвард по всему дереву (белый список +
запрет паттерна); fuzz; ◆ приёмочный прогон на реальном дистрибутиве (93 файла) с минимальным
набором чисел — **baseline для P2.7** (F6): wall-time `check`, аллокации/heap результата
(ручной bench-замер вне CI, perf.md §0), счётчики {предметов, set-пар, stat-записей, файлов,
байт} и unknown-топ; выписка в журнал.

**Критерии приёмки** — из план/p2.md P2.1 (синхронизированы с правками F2/F17): синтетика
грузится golden; злые входы — детерминированные ошибки с местом, не паники — таблица; неизвестные
значения — счётчик; fuzz-цель в CI; `check` exit 0/1 проверен тестом (злой вход — дубликат ID;
битые ссылки — P2.2); прогон реального items-набора без паник — числа и unknown-выписка в
журнал; ворота зелёные покомпонентно; `internal/data` без зависимостей и внешних require нет;
правка ADR-0005 не требуется.

**Скоуп P2.1 не включает:** остальные категории (P2.2+), перекрёстные ссылки (P2.2), каталог
`custom/` и override-семантику (отложено — см. решение 5), артефакт и манифест полного корня
(P2.7), свёртку/типизацию skills/conditions/capsuled (P2.6), горячие пути и их бенчи (загрузка —
build-time).

**Методные уточнения S6 (внесены, рев. 2.2).**

- ◆ Дефолты и единицы: переносим **дефолты канона** (material→STEEL, bodypart→none,
  crystal_type→NONE, duration/time→-1) в типизированные поля при отсутствии set-ключа —
  семантика полей обязана совпадать с каноном; единицы — как в каноне после его пересчётов
  (reuse-задержки канон умножает на 1000); zero-значение без переноса — ложная семантика
  (duration 0 ≠ -1). Источник дефолтов — ItemTemplate.set с атрибуцией.
- ◆ Дубликат set-ключа внутри предмета — перезапись (последний выигрывает, как канон) +
  счётчик; дубликат stat-типа в stats-блоке — та же политика (в данных нет — сверьт
  machines fresh-look; политика назначена, чтобы не решал реализатор молча).
- ◆ `<set>` без атрибута name — пропуск + счётчик (канон пропускает тихо); обязательные
  атрибуты (ошибка при отсутствии) — только id/type/name у `<item>`.
- ◆ Номер строки — `xml.Decoder.InputPos()` (Go 1.19+), без ручного трекинга `\n`.
- ◆ Контракт Load в doc-комментарии: Static валиден к использованию только при
  `Report.HasErrors == false` (и это же требование — в P2.7).
- ◆ Обход категории фильтрует `*.xml` (в каталоге лежит documentation.txt); при дубликате ID
  побеждает первая встреченная запись, дубликат — ошибка в отчёте (детерминизм канонического
  дампа и на грязных данных); регистр корневого элемента — строгий (list), «чужой корень» уже
  в злых входах.
