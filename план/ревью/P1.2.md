## План задачи (S0, рев. 2 — после S2/S4)

**Цель.** `pkg/bufpool` — бакетный пул байтовых буферов: порт семантики `BytePool` из
`udisondev/interlude@34fe4c8657d8b6bf338a5d2e788e197489a44f8f` (pkg/bufpool/bufpool.go).
Критерий жителя `pkg/` (ADR-0005): только stdlib, полезен вне проекта. Первый житель
`pkg/` — каталог рождается с кодом и тестом.

**Решения (с аргументами).**

1. **Контракт владения буфером — deliverable спеки, фиксируется doc-комментарием
   пакета** (самодостаточный текст): после Get буфер принадлежит вызывающему до Put;
   Put передаёт владение безусловно (в т.ч. при отбраковке чужой ёмкости буфер уходит
   в GC); после Put любое использование любого алиаса (копия заголовка, подслайс)
   запрещено; двойной Put одного буфера запрещён — пул молча выдаст массив двоим;
   передача в другую горутину — только с единственным владением. Конвенция: малые
   пакеты — стек, пул — для крупных, Put обязателен на горячих путях. Example
   демонстрирует дисциплину Get → использование → Put.
2. **Хранение в бакетах — pointer-shaped `*[N]byte`** (шесть типизированных веток по
   бакетам; Put: `(*[N]byte)(b[:N:N])`, Get: `a[:size]`). Аргумент: `sync.Pool.Put`
   над `[]byte` боксит заголовок слайса в `any` — 1 аллокация 24 Б на каждый Put,
   тест «0 аллокаций» невыполним; прототипные числа: параллельный цикл @4096 —
   10.1 нс с боксом против 4.4 нс pointer-shaped (~2.3×). Пул — эталонный
   аллокационно-чувствительный путь (codestyle §10). Цена: механические ветки;
   альтернатива «принять 1 аллокацию» — красный тест на ровном месте и мусор на
   каждую операцию.
3. **Zeroed-контракт — по всему cap**: Get возвращает полностью нулевой буфер (clear
   до ёмкости). Аргумент: clear только по len протекал хвостами прошлого владельца
   при кросс-размерных выдачах (репро: Get(128)/мусор/Put/Get(64) → 64 stale-байта);
   цена мала против make (цикл с clear ~54.7 нс @4096 против 388 нс make — ~7×).
   Тест — кросс-размерная фиксация.
4. **Статистика — три агрегата** `PoolStats{Gets, Puts, Overflows int64}`: per-bucket
   массив — спекулятивная детализация без потребителей (в референсе Stats никто не
   зовёт; спека требует три числа). Цена per-op атомиков на многоядерном hot path
   (~×2 пропускной способности на 16 ядрах, серийно — бесплатно) фиксируется в
   baseline и doc; вынос счётчиков из горячего пути — эволюция по потребителю
   (фаза 4, нагрузка).
5. **API: `Pool`, `Get(size) []byte`, `Put(b []byte)`, `Stats() PoolStats`.** Нулевое
   значение `var p bufpool.Pool` работоспособно (sync.Pool с nil New; Get выделяет
   свежий массив) — codestyle §11; конструктор не нужен. Имя `Pool` не повторяет имя
   пакета (§4); «BytePool» референса — записанное отклонение. `Get(size<1)` — паника
   с диагностикой «size должен быть ≥ 1» (программный контракт вызывающего,
   stdlib-прецедент strings.Repeat/slicing); **статус: владельцу — решение по
   рекомендации, ратификация на S9 вместе с калибровкой codestyle §5 (паника
   допустима при нарушении программного контракта; недоверенный вход — только
   ошибка); до ратификации гайд не правится; откат — guard в ошибку, одна ветка.**
   Обработчики «как overflow» сняты (прячет баг / паникует без диагностики).
   slog в Get референса убран: observability — Stats().
6. **Таблица бакетов — один источник правды** (массив bucketSizes), обе функции
   поиска индекса — над ним; switch-дубли референса не переносятся. >4096 — прямая
   аллокация (Overflows растёт).
7. **Тест-план (TDD, красная фаза — отдельным коммитом)**: таблица бакетов на всех
   границах (1, 128, 129, …, 4096, 4097); zeroed по cap (кросс-размерный); Put:
   nil — no-op, чужой cap — отброс (счётчики не растут); переиспользование —
   `AllocsPerRun == 0` на прогретых Get+Put; нулевое значение Pool без конструктора;
   паника-контракт Get(0)/Get(-1) (recover-проверка); **стресс: паттерн во владении
   f(goroutineID, iter) заполняется и сверяется перед Put, размеры покрывают все
   границы и overflow, полный GOMAXPROCS (не P=1), после join — покомпонентная
   сходимость локальных ожиданий со Stats()**; Example с дисциплиной владения.
8. **Бенч-план**: `BenchmarkGetPut` — стационарный цикл по ВСЕМ шести бакетам,
   серийно + параллельное семейство (RunParallel, полный GOMAXPROCS — путь реестра
   многопоточный, конфликт атомиков виден только параллельно);
   `BenchmarkColdGet` (крайние 128/4096; doc: измеряет свежую аллокацию, не пул);
   `BenchmarkAllocMake` — эталон прямой аллокации (те же размеры). Все — b.Loop,
   ReportAllocs, SetBytes(size); baseline `-count=10` с окружением; сверка семейств
   с планом (правило F25/P1.1); послабление против perf.md §0 — по прецеденту
   P1.1/F28, фиксируется в шапке baseline; без StopTimer/StartTimer-паттернов.
9. **Атрибуция**: заголовок — порт interlude@34fe4c86; отклонения перечислены (slog,
   pointer-shaped хранение, нулевое значение/имя, паника-контракт, агрегатная
   статистика).
10. **Скоуп-границы**: интеграции с encode/protocol нет (потребители — фазы 3+);
    статистика не расширяется; API не растёт «на всякий случай».

## Дополнения S6 (рев. 3 — текст плана, без рестарта)

- **Решение 1+**: Put принимает буфер, полученный из Get; проекция с урезанной ёмкостью
  (`b[:128:128]` от Get(4096)) — нарушение контракта (удержание массива GC + возможное
  перекрытие без детекта). Doc: подслайс, пережива́ющий буфер (в т.ч. асинхронный
  потребитель), — копировать. Закрепление при burst до GC (+victim-цикл) — риск в doc,
  датчик Stats, позиция GOMEMLIMIT; bounded-пул — фаза 6 (ADR-0004). Append за cap
  аннулирует членство — датчик дрейфа Gets−Puts. Верхняя граница size — валидация
  вызывающего (провод подаст кадр из недоверенного поля — фаза 3).
- **Решение 3+**: семантика выдачи фиксирована: len == size точно, cap == размер бакета,
  весь cap нулевой.
- **Решение 4+**: семантика Stats: Gets — все выдачи включая overflow; Overflows —
  подмножество; Puts — только принятые в бакеты; nil/чужой cap не растят; снимок
  некросс-консистентен (три Load не атомарны вместе) — doc.
- **Решение 5+**: паника-сообщение включает значение size; doc «не копировать после
  первого использования»; реализационно: двухзначный assert/nil-check при nil New.
- **Решение 7+**: перед заполнением в стрессе проверяется «Get вернул нули по всему cap»
  (непрерывная проверка инварианта zeroed под конкурентностью); ограничение паттерна по
  двойному Put — в комментарии теста; **добавлен стресс с хэндоффом владения через
  канал** (половина горутин Get+fill+send, половина receive+verify+Put, полный
  GOMAXPROCS) — заявленная контрактом кросс-горутинная форма исполняется до фазы 3;
  документирующий тест алиасинга двойного Put.
- **Решение 8+**: в шапке baseline — предсказание итоговой точки (@128 параллельно
  ≈10 нс: атомики доминируют, не читать как регрессию); sink против DCE.
- **Решение 9+**: в список отклонений добавлен clear по cap.

  S4: план рев. 2. Бюджет планов: 1/2.
