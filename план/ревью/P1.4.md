# Реестр находок P1.4

- Задача: P1.4 «Пакеты логин-флоу и хендшейка» — [план/p1.md](../p1.md)
- Ревью-профиль: S2 — инвариантщик, безопасник, доменщик, прагматик; S8 — + тестировщик
- Бюджеты: план 1/2 · рестарты 0/2 · ревью реализации 0/3

## План задачи (S0, рев. 2 — после S2/S3/S4)

**Цель.** `internal/protocol`: типизированные пакеты логин-флоу и game-хендшейка Interlude 746
по конвенции P1.3 (форма по роли потребителя: писатель — исходящий, представление — входящий,
в любом направлении). Состав — **20 пакетов** (18 по букве p1.md + два документированных
расширения): login-флоу полный + game-хендшейк и минимальный вход по фактуре Mobius Interlude.
На каждый пакет — golden encode (писатель → байты == фикстура) и golden decode (представление
над фикстурой → поля); отрицательная таблица; опкоды — константами из каталога P1.3.

**Решения (с аргументами).**

1. **Место и раскладка.** Всё в `internal/protocol`: правка ADR-0005 не нужна (строка и ребро
   protocol→fixture есть). Файлы: `login.go` (писатели LoginServer→C и C→LoginServer —
   wire-уровень), `login_view.go` (представления обеих сторон login-протокола),
   `handshake.go` (писатели game-хендшейка обеих сторон), `handshake_view.go`
   (представления game-хендшейка). Крипта не импортируется (и запрещена матрицей): RSA-блоб
   и скрэмблированный модуль — непрозрачные байты; шифрование — пакет crypto (P1.1),
   применение в флоу — P1.5.
2. **Обе формы на каждый пакет** — по букве критериев p1.md: golden encode требует писателя,
   golden decode — представления. Потребители: клиент P1.5 шлёт C→S писателями и читает S→C
   представлениями; login/game-сервер фазы 3 — зеркально (сценарий-сервер P1.5 сам по себе
   отвечает golden-байтами и писателями не пользуется — аргументация через него не ведётся).
3. **Состав (20).** LoginServer→C (8): Init, LoginOk, LoginFail, AccountKicked, ServerList,
   PlayOk, PlayFail, GGAuth. C→LoginServer (4): RequestAuthLogin (+plain-блок), RequestServerList,
   RequestServerLogin, AuthGameGuard. GameServer→C (4): KeyPacket, CharSelectionInfo,
   GSLoginFail, CharSelected. C→GameServer (4): ProtocolVersion, AuthLogin, Logout,
   CharacterSelect. GG-пробы включены: референс их шлёт (AuthGameGuard → GGAuth). **Расширения
   против буквы списка p1.md** (флоу не замыкается без них; оба — фактура Mobius и интерлюда):
   CharacterSelect (запрос, без которого CharSelected не приходит) и GSLoginFail 0x14
   (fail-ветка минимального входа; попутно упражняет правило коллизии F12/P1.3 — LOGIN_FAIL
   есть в обоих направлениях GS). Вне состава: PI_AGREEMENT/LOGIN_OPT_FAIL (не в флоу
   референса), CHAR_TEMPLATES/NEW_CHARACTER (экран создания персонажа — вне минимального
   входа), пакеты мира (анти-скоуп p1.md).
4. **RequestAuthLogin — слоистая типизация** (по референсу): wire-писатель
   `WriteRequestAuthLogin(dst, block []byte)` — опкод + 128-Б RSA-блоб (контракт: блок ровно
   128 Б — иначе паника с диагностикой, класс F6/P1.2: размер аргумента-буфера);
   wire-представление `RequestAuthLoginView` над [опкод||блоб] (конструктор min 129 =
   1+128; RSABlock — непрозрачный срез v[1:129], границы гарантированы конструктором);
   plain-писатель `WriteRequestAuthLoginPlain(dst, user, pass string) error` — 128-Б блок:
   user@0x5E (14 Б), pass@0x6C (16 Б), офсеты и длины — константами; **переполнение длины
   user/pass — ошибка** (буква p1.md «переполненные длины строк → детерминированная ошибка»;
   учётные данные — данные пользователя из конфига, не программная инварианта вызывающего —
   класс паники F6 здесь неприменим); паника остаётся только на коротком dst; plain-представление
   `AuthLoginPlainView` над расшифрованным блоком (конструктор min 124 = 0x6C+16; User/
   Password — обрезка ≤ U+0020 с обоих концов — семантика Java String.trim() канона; строки
   таблицы: ведущие пробел/таб обрезаются, пробел в середине пароля сохраняется). New-method
   (256 Б) не типизируется вовсе: ни RSABlock2, ни IsNewMethod — потребителя в фазе 1 нет
   (клиент классический; детекция new-method — задача login-сервера фазы 3), офсеты new-method
   — комментарием у констант. RSA-шифрование/расшифровка блока — crypto, не здесь.
5. **Переменно-структурные представления.** Конструктор проверяет только заголовок (мин.
   длину); навигационные геттеры ходят по буферу с ok=false на усечении — частичный разбор
   лучше отказа, диспетчер P1.5 падает в hex-дамп. ServerListView: `Count/LastServer` из
   заголовка, `Server(i) (ServerListEntry, bool)` — секция 1 (фиксированный шаг 21 Б:
   id, ip4, port D, age C, pvp C, cur H, max H, status C, type D, brackets C),
   `CharsCount() (byte, bool)` и `Chars(i) (ServerChars, bool)` — секция 2 после H(0)
   (serverID C, charCount C, deleteCount C, deleteCount×D; count2 канона независим от count1 —
   навигация самостоятельная). CharSelectionInfoView: `Count`, `Char(i) (CharSelectionEntry,
   bool)` — запись с двумя строками (name, loginName), скан до терминатора, ok=false на
   незакрытой строке. Возвращаемые структуры — значения со скалярами (строки/слайсы —
   материализация, допустимая на не-тиковом пути, конвенция F23/P1.3). Фиксированные-offsets
   представления (Init, LoginOk, PlayOk, GGAuth, KeyPacket, …) — геттеры по офсетам как
   AttackView. CharSelectedView/AuthLoginView: строки ведут переменный хвост — геттеры после
   строки считают её длину проходом (скан с ok-семантикой).
6. **Единый тип записи на пакет: аргумент писателя == результат навигационного геттера**
   (раундтрип-семантика одного wire-формата, бесплатный семантический тест):
   `ServerListEntry` (поля секции 1), `ServerChars` (serverID, charCount, deleteTimes),
   `CharSelectionEntry` (переименован из CharInfo — коллизия с будущим пакетом CHAR_INFO
   каталога), `CharSelectedData` (поля из канона — см. решение 8). Писатель ServerList
   принимает `servers []ServerListEntry, chars []ServerChars, lastServer byte` — канон
   строит секции из разных источников (список серверов и мапа счётчиков), сшивать их в один
   тип — искажение.
7. **Писатели — стек/пул, sizing-хелперы, полная таблица фиксированных размеров.** Принцип:
   каждому фиксированному писателю — экспортированная константа: InitSize=170, LoginOkSize=49,
   LoginFailSize=2, PlayFailSize=2, PlayOkSize=9, AccountKickedSize=5, GGAuthSize=21,
   KeyPacketSize=**23** (канон: result C + 8 Б ключа + encryption D + serverID D + C(1) +
   obfuscation D(0); расхождение с interlude-18 — в секции сверки), GSLoginFailSize=**5**
   (reason — int32 по канону GS-формы; шире LS-формы), RequestAuthLoginSize=129,
   AuthLoginPlainSize=128, RequestServerListSize=9, RequestServerLoginSize=10,
   AuthGameGuardSize=21, ProtocolVersionSize=5, LogoutSize=1, CharacterSelectSize=**19**
   (D слот + H + 3×D хвост — канон; интерлюд-порт знает только слот). Вариабельные —
   sizing-функции по образцу LenS (sizing и запись одним расчётом): ServerListSize,
   CharSelectionInfoSize, CharSelectedSize, AuthLoginSize (строки — через LenS). Писатели:
   паника с диагностикой на коротком dst — программный контракт (ратифицировано F6/P1.2,
   codestyle §5); 0 аллокаций — AllocsPerRun-тесты. Мультиполевые аргументы (≥6 полей) —
   структурами с именованными полями (codestyle §11).
8. **Канон и сверка.** Оракулы: порт-источник — interlude@34fe4c8; дополнительный —
   la2go@1eed6cb; канон — Mobius master CT_0_Interlude (зеркало gitlab.com/expcero/
   L2J_Mobius, пин 43ac8878f582ea792874eb74df16e2b0b64990e6; правило P1.3: при расхождении
   источник↔канон принимается значение канона, расхождение — строкой сюда). Известные
   расхождения источник↔канон (закрываются в S7 полной сверкой): KeyPacket — interlude 18 Б
   без хвоста C(1)+D(0), канон 23; CharacterSelect — интерлюд-вид знает только слот, канонное
   тело 18 Б с хвостом; CharSelected — интерлюд-порт короче канона на ~184 Б (нет блока
   6 статов INT/STR/CON/MEN/DEX/WIT, 30 нулевых D paperdoll, хвост 0/0/gameTime%1440/0/
   classId/12 нулей; exp в каноне — writeLong→Q) — **поля CharSelectedData берутся из
   канона, не из источника**; RequestAuthLogin plain-обрезка — Java trim() (≤ U+0020 с двух
   концов), интерлюд — TrimRight NUL/пробел. Сверяются в S7: порядок/типы полей всех 20
   пакетов, форматные константы (GG-константы Init, revision 0xC621, version 746, LoginOk
   unknown 0x3EA, ServerList unknown H(0)), полные списки кодов причин: LS LoginFailReason
   (байтовые; счёт — по канону, у интерлюда 40, у канона master меньше — точный счёт и
   расхождение фиксируются выпиской) и GS LoginFail (int32, 0–10) — выпиской в реестр.
   Атрибуция каждого
   файла-порта источником в комментарии.
9. **Фикстуры.** `testdata/login.json` + `testdata/handshake.json`, origin=generated: байты
   собираются из формата канона (Mobius) + выбранных значений полей независимо от наших
   писателей (правило F15/P1.3 — никакого круга писатель→фикстура→писатель; сборка —
   отдельным одноразовым скриптом по описанию формата, не нашим кодом). Вектор на каждый
   пакет (20 wire + 1 plain: dir=login-client, op=REQUEST_AUTH_LOGIN,
   name=REQUEST_AUTH_LOGIN_PLAIN — не имя каталога: блок не пакет, различим и от будущих
   captured-векторов P1.6; payload=128-Б блок; golden encode для plain-писателя сравнивает
   payload — опкода нет; машинная связка имя==каталог — только на wire-векторах);
   ServerList и CharSelectionInfo — по 2 записи (шаг/навигация) + непустой CharsToDelete;
   AuthLogin(C→GS) — с кириллицей; CharSelected — статовый блок канона пинится. Пополнение
   captured-векторами — P1.6.
10. **Тест-план (TDD, красная фаза отдельным коммитом).** «Красные против оракула» (калибровка
    КТ-2/F28 P1.3): ожидаемые байты фикстур собираются по формату канона до реализации
    писателей; красный прогон подтверждает, что ожидания зафиксированы независимо от
    писателей. На каждый пакет: golden encode (полный байт-образ писателя == опкод+фикстура,
    hex-сравнением; plain — payload без опкода), golden decode (представление над
    [опкод||фикстура] → поля таблицей; машинная связка fixture.Op == константа пакета и
    fixture.Name == имя каталога для каждого вектора), размер (константа/sizing-функция ==
    len). Свойства: sizing == результат писателя на таблице входов — все четыре sizing-функции
    (включая строковые длины вне фикс-вектора); 0 аллок фиксированных писателей;
    раундтрип-типы: Server(i)/Chars(i)/Char(i) == вход писателя. Отрицательная таблица:
    обрезанный payload каждого представления (min-1/0); **чужой опкод — вне зоны
    представления: конструктор опкод не проверяет (конвенция P1.3), дискриминация —
    диспетчер P1.5 по каталогу — осознанное отклонение от буквы p1.md, записано здесь**;
    переполненные длины строк: WriteRequestAuthLoginPlain(user>14/pass>16) → ошибка;
    строки без терминатора (AuthLogin, CharSelected, записи CharSelectionInfo) → ok=false;
    RequestAuthLoginView длины 129–256 (блоб короче new-method) → конструктор ok, работа
    только через RSABlock; счётчики записей: ServerList count>записей, CharSelectionInfo
    count=−1/0x7FFFFFFF → ok=false навигации, не паника; recover-тест на перечисленной пачке
    злых входов (все случаи выше + нулевое значение представлений — doc-контракт).
    Константы→каталог: 20 строк TestConstantsMatchCatalog. Example-пара: WriteInit →
    NewInitView → поля.
11. **Бенчи не вводятся.** Логин и хендшейк — холодный путь (раз за сессию), реестр горячих
    путей ADR-0005 не затрагивается; perf.md не активируется. 0-аллокационность писателей
    держится воротами (AllocsPerRun-тесты). Пересмотр — при появлении горячего потребителя.
12. **Скоуп-границы:** провода/фрейминг/диспетчер — P1.5; pcap captured-фикстуры — P1.6;
    fuzz пакетов — P1.7; new-method plain-разбор и RSABlock2/IsNewMethod, CHAR_TEMPLATES,
    PI-пакеты — по потребителю; таблицы причин — полный перенос из канона (LS байтовые —
    счёт по канону, S7-выпиской; GS int32 0–10) с машинной сверкой в S7-выпиской.
