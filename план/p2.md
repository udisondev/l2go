# p2 — План фазы 2: Статические данные — датапак и geodata

Исполнение [r2.md](../research/r2.md) §Фаза 2. Гео-дизайн — [r1.md](../research/r1.md); референсы —
[r4.md](../research/r4.md) (клоны `_refs/` вне репозитория) и GPL-каноны (Mobius/aCis). Карта
пакетов и реестр горячих путей — [ADR-0005](../docs/adr/0005-karta-komponentov.md): строки
`internal/data` и `internal/geo` уже в матрице (обе без зависимостей), правка ADR нужна только
для новых рёбер/подпакетов. Лицензионная гигиена — [ADR-0001](../docs/adr/0001-licenzionnaya-poziciya.md):
данные NCsoft-derived в репо не коммитятся. Конвейер — [ADR-0006](../docs/adr/0006-revyu-konveyer-zadach.md),
реестры находок — `ревью/<ID>.md`. Конвенции планов — [README.md](README.md).

**Цель фазы:** контент становится данными с машинной проверкой целостности. Парсеры датапака L2J
(предметы, NPC, спавны, дроплисты, зоны, скиллы) дают типизированные иммутабельные структуры и
**отчёт валидации**, где битая ссылка = ошибка сборки данных, а не строчка в логе. Геодата
раскладывается в off-heap представление из r1 (байты блоков + zero-copy лукапы), поверх него —
примитивы `canMove` / `getNearestZ` / `canSee` как чистые функции. Сборка и загрузка разделены:
валидация исходников — на сборке статики, рантайм грузит компилированный артефакт (release-сборка
владельца вшивает его в бинарарь). Фаза 3 получает на вход проверенную статику: walking skeleton
не отлаживает одновременно интеграцию и данные.

**Оценка:** 6–8 агентных сессий + контрольные точки владельца (источники данных, ручные полные
прогоны, приёмки ✅).

## Выход фазы (Definition of Done)

- [ ] `internal/data`: загрузчик категорий датапака в типизированные структуры; ссылочная
      целостность машинно проверяется (дроп→предмет, спавн→NPC, спавн→территория, скилл→предмет);
      нарушение = ошибка загрузки.
- [ ] Каркас отчёта валидации: записи (категория, файл, ID/строка, код), счётчики, коды выхода;
      один и тот же код работает в CI (синтетика), в локальном полном прогоне и при старте
      сервера (фаза 3).
- [ ] `cmd/l2data`: `check <корень данных>` — загрузить всё зарегистрированное, напечатать отчёт;
      тонкий wire-up без логики.
- [ ] Компилированный артефакт статики: `l2data build` (парсинг + валидация + компиляция) и
      быстрый `Load` без копирования в кучу; транспорт — mmap внешнего файла (dev/CI) и embed за
      build-тегом (release владельца: сервер = один файл); эквивалентность «артефакт == парсинг
      исходников» машинно проверяется; числа сборки/загрузки — в журнал.
- [ ] `internal/geo`: парсер L2J-геодаты → off-heap mmap-представление (region→block→cell→layers)
      с валидацией структуры; примитивы `canMove`/`getNearestZ`/`canSee` с бенчмарками
      (реестр ADR-0005 «Геодата: canMove/пасфайнд») и 0 аллокаций на лукапе.
- [ ] Синтетические фикстуры (сгенерированы проектом, не NCsoft-derived) в `testdata` для CI;
      реальные данные — вне репо, отсутствие в репо машинно проверяется по расширениям.
- [ ] Fuzz-смоук CI дополнен целями парсеров (малформленный XML, битые гео-блоки).
- [ ] Ноль внешних зависимостей (allowlist в checkdeps пуст).
- [ ] Ручные полные прогоны на реальном датапаке и геодате владельца — выжимки отчётов в журнал.

## Ключевые решения плана (с отвергнутыми альтернативами)

1. **Разделение сборки и загрузки: исходники XML парсятся и валидируются при сборке статики,
   рантайм грузит компилированный артефакт.** `l2data build/check` — парсинг дистрибутива и
   отчёт валидации (битая ссылка = красная сборка данных); сервер и тесты грузят артефакт — без
   XML и без файлового разбора на старте. Артефакт — одноразовый кэш, а не формат персистенции:
   несовпадение версии схемы или хэша входов = пересбор, миграций не существует как класса.
   Альтернативы отвергнуты: БД (pgx + goose референсов — персист-слой статике не нужен,
   зависимость и инфраструктура); парсинг при каждом старте (работа, не меняющаяся между
   запусками, оплачена каждым тестом и рестартом фаз 3–6); кодогенерация в Go-исходник
   (линк-налог на каждую сборку, NCsoft-derived в исходнике, перекомпиляция пакета на каждую
   правку поля).
2. **Формат-канон датапака — Mobius, ветка Interlude.** Уже канон проводов фазы 1 (сверка
   каталога опкодов — ноль расхождений значений) и XML-first: все категории читаются stdlib
   `encoding/xml`, ноль зависимостей сохраняется. aCis (микс SQL+XML) — второй оракул для
   выборочной сверки значений, но не формат-источник: SQL-дамп-парсер — новая поверхность без
   потребителя. Финальное слово за КТ-1: датапак на диске владельца может оказаться другим
   дистрибутивом.
3. **Данные живут вне репо.** Каталог вне git (путь — флаг/env, решается в S0 P2.1); в репо —
   только синтетические фикстуры и производные числа в журнале. Подмодуль или отдельный репо
   отвергнуты: усложнение CI против буквы ADR-0001 («в репо не коммитятся»). Полный прогон
   валидации — ручная КТ, CI работает на синтетике.
4. **Полнота типизации — по потребителю.** Скиллы фазы 2 — структурный каркас (id/уровень/цели/
   тайминги/флаги/цепочки уровней) с сохранением сырых параметров эффектов; глубина полей —
   фазам 4/6, где появляются потребители формул. Тот же принцип, что и типизация опкодов в
   фазе 1: поля без потребителя — источник агентских галлюцинаций.
5. **Примитивы гео — в фазе 2, не в фазе 3.** Чистые функции над иммутабленной статикой —
   идеальная агентская почва (оракул: синтетическая геометрия + семантика GeoEngine канона);
   фаза 3 остаётся тонкой интеграцией. Пасфайнд (A*, flow-field, граф слоёв) — анти-скоуп:
   r1/r2 относят его к фазам 4/6.
6. **Порядок задач — по критическому пути фазы 3, артефакт — последним.** Скелету нужны
   предметы, NPC+спавны, гео, `canMove` — это первые четыре задачи; зоны и скиллы потребуются
   позже и переносятся без переделок (входящих зависимостей нет). Артефакт (P2.7) — после того,
   как P2.1–P2.6 зафиксируют схемы всех категорий: формат компилируется один раз, а не
   эволюционирует шесть раз.
7. **Целостность = ошибка, неизвестное = счётчик.** Битая ссылка или дубликат ID роняет сборку
   данных (буква r2: «разрыв = ошибка сборки»); неизвестные enum-значения и непокрытые поля —
   счётчик с выпиской в отчёте: это широта данных, а не целостность. Политика уточняется в S2
   первой задачи.
8. **Транспорт статики — два, без копирования в кучу.** Исходники (XML) читаются через
   `io/fs.FS` (`os.DirFS` над путём — флаг/env). Артефакт: dev/CI — `syscall.Mmap` внешнего
   файла; release — embedded-байты за build-тегом `embedded` (файл-бэкированные страницы
   бинараря, спрос-пейджинг ОС, вне Go-кучи). Рабочий цикл владельца: подложить данные →
   `l2data build` → `go build -tags embedded` → сервер = один исполняемый файл. Решение
   владельца: бинарари не публикуются, сервер личный — лицензионная позиция ADR-0001 не
   затронута; появление дистрибуции — повод пересмотреть ADR. Сжатие артефакта не применяется
   (embed не сжимает; геодате нужен random access; размер владельца не беспокоит) —
   gzip-упаковка остаётся разрешённой эволюцией.

## Задачи

Формат: каждая задача — spec-first слайс для агента; проработка и уточнение — стадии S0–S4
конвейера. Критерии приёмки фальсифицируемы. Статусы: ⬜ не начата, 🔄 в работе, 👀 на ревью
человека, ✅ принято, ⛏ заблокирована.

### P2.1 Рамка датапака + категория «предметы» — internal/data, cmd/l2data — ⬜

**Спецификация.** Каркас загрузки статики и первая категория на нём:

- Корень данных: `io/fs.FS` (`os.DirFS` над путём — флаг/env; данные вне репо). Граница fs.FS
  фиксируется сразу: исходники читаются одинаково из каталога и из `embed.FS`. Пакет
  `internal/data` рождается с кодом (строка матрицы есть); раскладка плоская, подпакет — только
  явной нуждой, это правка ADR-0005.
- Манифест входов: детерминированный хэш состава данных (файлы + хэши содержимого),
  вычисляется при загрузке: идентичность версии данных для реплея (D1–D6) и основа кэша P2.7.
- Каркас: регистрация категорий, контекст загрузки (корень, счётчики), сквозная идентификация
  места ошибки (файл+строка или ID); политика «целостность = ошибка, неизвестное = счётчик».
- Категория «предметы»: типизированная структура (id, имя, тип, слоты, вес, цена, stackable,
  кристаллизация и т.п.) — набор полей по минимальному потребителю фазы 3 (инвентарь, дроп,
  подбор) плюс тривиальное из формата; дубли ID — ошибка.
- `cmd/l2data`: `check` — загрузить зарегистрированные категории, напечатать отчёт, код выхода
  0/1. Тонкий wire-up, логика в пакете.
- Синтетическая мини-фикстура предметов в `testdata` (наша, не из дистрибутива) — база CI.
- Машинная проверка «данные не в репо» (список расширений/масок дистрибутива) — тестом.

**Критерии приёмки.**
- Синтетика грузится, поля совпадают с ожиданием (golden путь загрузки).
- Манифест-хэш детерминирован: два прогона над одним составом — одинаковое значение (машинный
  тест).
- Таблица злых входов: битый XML, обрезанный файл, дубликат ID, неизвестный тип —
  детерминированная ошибка с местом, не паника; неизвестные значения — счётчик в отчёте.
- Fuzz-цель малформленного XML добавлена в CI-смоук; находки — регресс-тесты.
- `cmd/l2data check` на синтетике: зелёный отчёт, exit 0; на подложенной битой ссылке —
  exit 1 с перечнем.
- Ручной прогон владельца на полном датапаке — выжимка отчёта в журнал (КТ-3).
- Ворота зелёные; `internal/data` без зависимостей; внешних require нет.

**Ревью-профиль:** S2 — инвариантщик, безопасник, перформансер, прагматик; S8 — + доменщик,
тестировщик.

**Зависимости:** нет; первая задача фазы, в S0 закрывается КТ-1.

**Ссылки:** r2 §Фаза 2; ADR-0001 (данные вне репо, исключения только для фикстур протокола);
ADR-0005 (матрица: data без зависимостей; плоская раскладка); r4 (датапак-подходы референсов
отвергнуты — решение 1).

### P2.2 NPC, спавны, дроплисты — ⬜

**Спецификация.** Витрина ссылочной целостности фазы:

- NPC: id, имя, уровень, тип/фракция, аггро-флаги, радиусы (аггро/рассеяния) — поля по
  потребителю фаз 3–4 (спавн, таргетинг, аггро); дубли ID — ошибка.
- Спавны: npcID, точка или территория (имя), таймер респауна, количество. Ссылка спавн→NPC
  проверяется сразу; ссылка спавн→территория регистрируется как отложенная (территории —
  P2.5): каркас хранит реестр отложенных ссылок, в P2.5 он закрывается машинной проверкой.
- Дроплисты: npcID → itemID, шанс, min/max; ссылки дроп→предмет и дроп→NPC — ошибка при разрыве;
  шансы вне [0,1] (или [0,100] по формату канона) — ошибка.

**Критерии приёмки.**
- Синтетика с намеренно битыми ссылками (дроп→несуществующий предмет, спавн→несуществующий
  NPC, шанс вне диапазона) — каждая ловится отдельной записью отчёта, сборка красная; тест
  машинный.
- Реестр отложенных ссылок спавн→территория непуст и печатается в отчёте (до P2.5).
- Fuzz-цель на новых парсерах; злые входы — ошибка с местом, не паника.
- Ручной полный прогон — выжимка в журнал (КТ-3).

**Ревью-профиль:** S2 — инвариантщик, доменщик, перформансер, прагматик; S8 — + тестировщик.

**Зависимости:** P2.1 (каркас, предметы).

**Ссылки:** r2 §Фаза 2 (дроп→предмет, спавн→NPC); r4 (генераторы референсов — не переносим).

### P2.3 Геодата: формат, парсер, mmap-представление — internal/geo — ⬜

**Спецификация.**

- Формат L2J-геодаты; канон семантики чтения — GeoEngine канона (aCis/Mobius, порт с
  атрибуцией); константы и раскладка — из исходника канона, не по памяти (предупреждение r1:
  l2off и L2J форматы различаются). l2off — анти-скоуп.
- Представление: region→block (flat/complex/multilayer)→cell→layers, NSWE-флаги, высоты.
  Декодер работает над `[]byte` и не знает источника байтов: `syscall.Mmap` внешнего файла
  (Windows — платформа владельца, обязательная проверка в задаче) или embedded-байты артефакта
  P2.7. Лукап ячейки — индексная арифметика O(1) поверх байтов, без копирования и без syscall
  на ячейку.
- Валидация в общем каркасе отчётов: структура файла, типы блоков, размеры, счётчик слоёв,
  sanity NSWE; разрушенная структура — ошибка загрузки.
- Синтетические гео-блоки (наши байты): все три типа блоков, многослойность, границы регионов.

**Критерии приёмки.**
- Golden: синтетические байты ↔ декодированные структуры (все типы блоков, многослойность).
- Злые входы: обрезанный файл, неверный тип блока, слой вне лимита, выход за регион —
  детерминированная ошибка с местом, не паника; fuzz-цель в CI-смоуке.
- Лукап ячейки: 0 аллокаций, бенчмарк; представление не расширяет Go-кучу (маппинг вне кучи —
  фиксируется тестом/бенчем памяти).
- Ручной прогон владельца на реальной геодате: файлы открываются, отчёт валидации чист или
  выписан — выжимка в журнал (КТ-3).

**Ревью-профиль:** S2 — инвариантщик, безопасник, перформансер, прагматик; S8 — + доменщик,
тестировщик.

**Зависимости:** P2.1 (каркас отчётов — гео-валидация в том же формате).

**Ссылки:** r1 (структура geodata, mmap/off-heap, «сверять по парсеру-референсу»); AGENTS-инвариант
6 (статика read-only, off-heap); ADR-0005 (матрица: geo без зависимостей).

### P2.4 Геодата: примитивы движения и LOS — ⬜

**Спецификация.** Три чистые функции поверх представления P2.3:

- `canMove(from, to)` → дальняя достижимая точка: supercover-обход (Amanatides–Woo по r1),
  анти-срез диагонали (угловая ветка — оба ортогональных флага), кламп до последней валидной
  ячейки.
- `getNearestZ(x, y, z)`: резолв ближайшего слоя с step-height; в multilayer — ближайший
  связный слой (не «телепорт на мост»).
- `canSee(from, to)` (LOS): трек Z линии по ячейкам, рельеф выше линии → перекрытие.
- Канон семантики и порогов — GeoEngine канона (порт с атрибуцией); расхождения канонов —
  списком в реестр задачи (прецедент: канон паддинга P1.1).
- Тестовая геометрия — синтетические карты (P2.3): стена, L-угол, мост над проходом, лестница
  step, обрыв, плоский блок (broad-phase-случай).

**Критерии приёмки.**
- Таблица синтетических геометрий: ожидания детерминированы (кламп-точка, blocked, слой).
- Property-инварианты: возвращённая кламп-точка сама достижима из from; blocked ⇒ тест
  называет запрещающий фактор (NSWE/stepZ) — свидетельство в тесте, не «false и всё».
- Бенчмарки `canMove`/`canSee`/`getNearestZ` (реестр ADR-0005 «Геодата: canMove/пасфайнд»);
  0 аллокаций; baseline в журнал (benchstat-выписка).
- Диагональный срез угла невозможен — тест на L-стене (анти-чит-сценарий r1).

**Ревью-профиль:** S2 — инвариантщик, безопасник, доменщик, перформансер, прагматик; S8 — +
тестировщик.

**Зависимости:** P2.3.

**Ссылки:** r1 (DDA, три места типовых багов, LOS); r2 §Фаза 3 (гео-валидация движения —
потребитель); ADR-0005 (реестр путей).

### P2.5 Зоны — ⬜

**Спецификация.**

- Категория «зоны»: типы зон Interlude по канону (peace/combat, spawn-территории, города,
  урон и т.п. — состав по дистрибутиву), формы (полигон/прямоугольник/цилиндр), координаты,
  принадлежность точки зоне.
- Валидация: пустая/вырожденная геометрия — ошибка; закрытие отложенных ссылок P2.2 — каждый
  спавн ссылается на существующую территорию (реестр отложенных обнуляется; тест на битую
  территорию красный).
- Поля — по потребителю (спавн-территории фазы 3; прочие типы — данные без глубокой
  интерпретации, по решению 4).

**Критерии приёмки.**
- Point-in-zone: внутри/снаружи/граница — таблица тестов на каждой форме.
- Битая ссылка спавн→территория ловится (машинный тест, сборка красная); реестр отложенных
  ссылок пуст после загрузки синтетики полного состава.
- Fuzz-цель; злые входы — ошибка с местом; ручной полный прогон (КТ-3).

**Ревью-профиль:** S2 — инвариантщик, доменщик, прагматик; S8 — + тестировщик.

**Зависимости:** P2.1 (каркас), P2.2 (реестр отложенных ссылок).

**Ссылки:** r2 §Фаза 2 (зоны в составе категорий); ADR-0004 (AoI-сетка ≠ зоны — зоны остаются
датой, видимость их не импортирует).

### P2.6 Скиллы — структурный каркас — ⬜

**Спецификация.**

- Типизированная оболочка скилла: id, уровень, имя, тип/операция, цели, тайминги (каст,
  реюз, длительность), флаги, цепочка уровней (prev/next). Сырые параметры эффектов —
  сохраняются как есть (без глубокой типизации) для фаз 4/6.
- Валидация: дубли (id, level) — ошибка; разрыв цепочки уровней — ошибка; ссылки на предметы
  (consume/предметные скиллы) — через общий каркас целостности; неизвестные операции — счётчик
  с выпиской (решение 7).
- Синтетическая фикстура; ручной полный прогон — выжимка в журнал (КТ-3): счётчики unknown
  фиксируют фактическую широту датапака против каркаса.

**Критерии приёмки.**
- Целостность цепочек и ссылок машинно проверяется; тесты на подложенных разрывах красные.
- Каркас читает полный датапак канона (ручной прогон) без ошибок целостности; unknown-счётчики
  в отчёте.
- Fuzz-цель; злые входы — ошибка с местом, не паника.

**Ревью-профиль:** S2 — инвариантщик, доменщик, перформансер, прагматик; S8 — + тестировщик.

**Зависимости:** P2.1 (каркас, предметы для ссылок).

**Ссылки:** r2 §Фаза 2 (скиллы как таблицы) и §Фаза 6 (table-движок эффектов — потребитель
каркаса); решение 4 (полнота по потребителю).

### P2.7 Компилированный артефакт статики + embed-транспорт — ⬜

**Спецификация.** Разделение сборки и загрузки (решения 1 и 8), после фиксации схем всех
категорий:

- `l2data build`: загрузить всё (P2.1–P2.6) путём парсинга исходников, прогнать валидацию
  (отчёт = отчёт сборки; разрыв = красная сборка, артефакт не обновляется), скомпилировать
  единый плоский артефакт: манифест (версия схемы, хэш входов P2.1) + категории + геодата как
  есть (байты блоков, без перекодирования). Кодирование категорий — плоское собственное или
  `encoding/gob` (stdlib); выбор — бенчмарком в задаче.
- `Load` быстрый путь: сверить манифест → hit: байты артефакта без копирования в кучу (внешний
  файл — `syscall.Mmap`; embed — глобальный `[]byte` над rodata), категории декодируются в
  типизированные структуры, геодата отдаётся zero-copy поверх байтов; miss — прозрачный
  пересбор с логом. Парсинг исходников остаётся явным путём (`l2data check`) и в CI.
- embed-транспорт: артефакт складывается в gitignored-каталог внутри модуля; файл с
  `//go:embed` — за build-тегом `embedded`; цепочка владельца: подложить данные →
  `l2data build` → `go build -tags embedded` → сервер = один файл (Makefile-цель).
- CI: синтетика на обоих транспортах (внешний файл и embed); путь парсеров покрыт тестами
  `l2data check` всегда.

**Критерии приёмки.**
- Эквивалентность: статика из артефакта равна статике парсинга тех же исходников (машинный
  тест на синтетике полного состава).
- Битая ссылка в исходниках → `l2data build` красный, артефакт не обновлён.
- Чужая версия схемы/хэш входов → пересбор; цикл «изменил один XML → пересобрался артефакт»
  воспроизводим.
- Числа в журнал на полных данных: время `check` (парсинг), время `build`, время `Load` из
  артефакта (внешний файл и embed).
- Сборка с тегом `embedded` на синтетике: бинарарь содержит статику, загрузка без внешних
  файлов; сборка с тегом без артефакта падает внятной ошибкой.
- Гео-лукапы поверх embedded-байтов — 0 аллокаций (перенос критерия P2.3).
- Артефакт и gitignored-каталог в репо не попадают (машинная проверка); ноль внешних
  зависимостей; ворота зелёные.

**Ревью-профиль:** S2 — инвариантщик, безопасник, перформансер, прагматик; S8 — + тестировщик.

**Зависимости:** P2.1–P2.6 (схемы категорий зафиксированы — формат артефакта компилируется
один раз).

**Ссылки:** r2 §Фаза 2 (отчёты валидации); AGENTS-инвариант 6 (статика read-only, off-heap);
ADR-0001 (данные вне репо; решение владельца о непубликации бинарарей); ADR-0003 D1–D6
(идентичность данных для реплея — хэш манифеста).

## Порядок исполнения

```
P2.1 (рамка+предметы) → P2.2 (NPC/спавны/дроп) → P2.3 (гео-парсер) → P2.4 (примитивы)
→ P2.5 (зоны) → P2.6 (скиллы) → P2.7 (артефакт+embed)
```

- Первые четыре задачи — критический путь фазы 3 (скелету нужны предметы, NPC+спавны, гео,
  `canMove`); зоны и скиллы переносятся без переделок, если фазу придётся резать; артефакт —
  строго последним: формат компилируется один раз после фиксации схем всех категорий.
- Все задачи — полный конвейер ADR-0006; ведущая сессия ведёт по одной задаче за раз.
- Правка ADR-0005 в ходе фазы ожидается только на новые рёбра/подпакеты (появятся — правкой
  решения, как требует карта).

## Анти-скоуп (в фазу 2 НЕ входит)

- Пасфайнд: A*, иерархический A*, flow-field, граф переходов слоёв — фазы 4/6 (r1/r2).
- Оптимизация загрузки сверх артефакта (сжатие, распараллеливание парсинга, инкрементальные
  пересборы) — только по измерениям (perf.md). Сжатие не применяется: embed не сжимает,
  геодате нужен random access; gzip-упаковка артефакта — разрешённая эволюция.
- Runtime-кеш статики (LRU/вытеснение/TTL) — статика целиком в памяти и иммутабельна:
  вытеснение = латентные всплески повторной загрузки, TTL = недетерминизм без причины,
  LRU-счётчики = точка синхронизации на горячем пути (против lock-free шаринга инварианта 6).
  Постатейное вытеснение большого объёма уже делает ОС: страницы mmap/embed — LRU ядра, read-only,
  без кода. Кешироваться могут только производные вычисления (мемоизация пасфайнда/LOS) — фазы 4+,
  по измерениям, LRU без TTL и только для чистых функций (вытеснение влияет на скорость, не на
  результат).
- Публикация бинарарей со встроенными данными и любая дистрибуция наружу — не планируется
  (решение владельца: сервер личный); если появится — пересмотр ADR-0001.
- Типизация полей эффектов скиллов, формулы урона/статов — фазы 4/6 (каркас хранит raw).
- AI-правила и бихевиоры как данные, аггро-таблицы глубже флагов — фаза 6.
- l2off-формат геодаты, версии кроме Interlude, мультидатапачность — не поддерживаются.
- Серверный код и потребители статики (мир, спавн-движок, инвентарь) — фаза 3+.
- Правка самих данных датапака/геодаты и балансные решения — фаза 2 только читает и валидирует.
- Валидация «смысла» данных (баланс шансов, правильность цифр) — вне фазы: только структурная
  и ссылочная целостность.
