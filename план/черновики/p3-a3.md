# p3 (черновик a3) — План фазы 3: Walking skeleton — войти и пробежаться

Исполнение [r2.md](../../research/r2.md) §Фаза 3. Архитектура мира — [r0.md](../../research/r0.md),
гео/движение — [r1.md](../../research/r1.md), исполнение — [r3.md](../../research/r3.md). Решения:
[ADR-0002](../../docs/adr/0002-model-tika.md) (метроном без барьера),
[ADR-0003](../../docs/adr/0003-poryadok-soobscheniy-pri-khandoffe.md) (транспорт, владение,
D1–D6), [ADR-0004](../../docs/adr/0004-napravlenie-knownlist-aoi.md) (knownlist/AoI, ось 6 —
минимальная экспозиция), [ADR-0005](../../docs/adr/0005-karta-komponentov.md) (карта компонентов),
[ADR-0006](../../docs/adr/0006-revyu-konveyer-zadach.md) (конвейер, профиль в каждой задаче).
Лицензионная гигиена — ADR-0001. Конвенции планов — [README.md](../README.md).

**Входы фазы.** Готово и проверено (фазы 1–2, 7/7 и 7/7): криптодвижок (`internal/crypto`:
LoginCrypt, GameCrypt, RSA-блок), каталог 494 опкодов + писатели/представления логин-флоу и
game-хендшейка (`internal/protocol`: Init…PlayOk, ProtocolVersion…CharSelected, GSLoginFail),
headless-клиент с трафик-логом и сценарий-сервер (`internal/l2client`), тап (`internal/tap`,
`cmd/l2tap`); статика `internal/data` (предметы, NPC, спавны, территории, зоны, скиллы,
манифест-хэш) и `internal/geo` (`Map.ValidLocation`/`NearestZ`/`CanSee`, off-heap), компилированный
артефакт `internal/artifact` (LoadFile / embed за тегом `embedded`, `make embedded`). Каркасы
типов (транспорт-таксономия `Envelope/Kind/Domain`, `world.Entity/Suitcase/Portion`,
`replica.Snapshot/Advisory`, `gateway.Inbound`, `conn.Handler`, `encode.Frame`, `persist.Record`)
есть без реализаций — фаза 3 наполняет их. Внешних зависимостей в go.mod нет (allowlist
checkdeps пуст).

**Цель фазы:** минимальный игровой сервер end-to-end: авторизация → создание/выбор персонажа →
вход в мир → спавн → движение с гео-валидацией → видимость второго клиента (минимальный knownlist
по ADR-0004 ось 6) → чат → логаут с персистом. Один регион-актор, без боя. Каркас конкурентности
r0/ADR-0002/0003 в минимальной экспозиции, но настоящий: горутина региона, ящики, метроном,
свёртка над порциями, лог порций (D5) и реплей-харнесс (D6). Приёмка — реальный клиент Interlude
владельца: два клиента, второй видит первого. Статика — из компилированного артефакта P2.7
(embed у владельца, синтетика в CI).

**Оценка:** 12 задач, 12–16 агентных сессий + контрольные точки владельца (приёмки живым клиентом
после LS, после входа в мир, после взаимной видимости, финальная; ✅ на каждой задаче).

## Выход фазы (Definition of Done)

- [ ] Два процесса — `cmd/l2login` (LoginServer) и `cmd/l2go` (GameServer) — подняты по отдельности;
      реальный клиент владельца проходит полный флоу r2: логин → выбор персонажа → вход → бег →
      видимость второго клиента → чат → логаут; перезаход начинается с сохранённой позиции.
- [ ] `internal/transport`: карта `id → ящик`, MPSC-очередь с мигрирующим читателем и водяным
      знаком (этап-1: мьютекс в enqueue), контрольный ящик региона; стресс-тесты инвариантов
      И2/И4/И5 и компакции под `-race` (ADR-0003 §11 — обязательны с фазы 3); бенчмарки
      enqueue/изъятия в `benchmarks/`.
- [ ] `internal/world`: метроном (10 Гц, non-blocking send в cap-1, дроп-метрика) и регион-актор
      (drain → фаза A(dt) → фаза B(capped) → публикация → doneTick); D1 (dt = тики × период),
      D2 (RNG от regionID и tick), D3 (обход по сортированному слайсу id); лог порций D5
      (заголовки всегда, payloads по флагу).
- [ ] `internal/persist`: персист персонажей — плоский собственный формат, атомарная замена,
      persist-актор (единственный писатель файлов, запросы письмами); CREATE персонажа и CharList
      работают до входа в мир; аккаунты — авто-создание в LS с PBKDF2-хешем.
- [ ] `internal/login` + `internal/loginlink` + `cmd/l2login`: login-сервер с ServerList из
      зарегистрированных игровых серверов; стык LS↔GS — gRPC (RegisterSession/ValidateSession)
      по ADR-0005; первая внешняя зависимость зафиксирована правкой allowlist checkdeps.
- [ ] `internal/conn`, `internal/gateway`, `internal/encode`: провода, шлюз (предсессионная фаза +
      назначение пакетов в порции; настенные часы только здесь), энкод-стадия (per-client FIFO,
      lossless до disconnect, криптоблок вне тика).
- [ ] `internal/replica`: блоб per-owner (SoA-сегменты, dirty-манифест, свап указателя, стабильные
      слоты с детектом реюза по вечному id), join = view set (set-equality), уход из членства →
      DeleteObject, предикат видимости; синтетический join-бенч (проверка решения ADR-0004) —
      выписка в журнал.
- [ ] Движение: сервер-авторитетное, `geo.ValidLocation`-кламп (стена = остановка + коррекция),
      продвижение по пути в тике, токен-бакет скорости r1, ValidatePosition со snap-back.
- [ ] Чат SAY2 канала ALL в радиусе известности; NPC-население из спавнов статики (без AI)
      с NpcInfo.
- [ ] Реплей-харнесс (D6): прогон лога порций e2e-сессии через ту же свёртку — бит-в-бит
      идентичный дамп состояния; тест в CI.
- [ ] e2e-смоук в CI (`tests/e2e`): два headless-клиента на синтетическом артефакте — вход,
      взаимная видимость, обмен позами движения, чат, логаут с проверкой персиста; `-race` зелёный.
- [ ] Живые фикстуры из тапа приёмки владельца — в `internal/protocol/fixture` testdata;
      все порты семантики — с атрибуцией; ворота (`make check` / покомпонентно) зелёные.

## Ключевые решения фазы (что и почему; отвергнутое — с причиной)

1. **Один регион, всегда активный; хэндофф не исполняется.** Фаза 3 — минимальная экспозиция
   каркаса (r2): один регион-актор, активный с момента старта, сущности — игроки и NPC. Протокол
   хэндоффа (ADR-0003 §5: черновик/флип/затравка) не включается — нет второго региона, нет
   потребителя; типы `Suitcase` остаются каркасом. Отвергнуто: «зашить» второй регион ради
   упражнения хэндоффа — удвоение поверхности интеграции без валидатора (свой knownlist во втором
   регионе потребовал бы затравки/эпох — это фаза 4 с ботами и property-тестами ADR-0004).
   Диспетчер, тем не менее, рождается с активным сетом и коалесингом (не циклом «в лоб»), чтобы
   фаза 4 расширяла, а не переписывала.
2. **Топология: два процесса, gRPC-стык — исполнение ADR-0005, не пересматривается.**
   `cmd/l2login` (LoginServer, порт 2106) + `cmd/l2go` (GameServer, порт 7777), стык —
   `internal/loginlink` (gRPC; LS слушает внутренний порт 9011): RegisterSession при старте GS,
   ValidateSession ключей при входе игрока, Kick — метод протокола с заглушкой (повторный вход
   того же аккаунта в фазе 3 отклоняет GS локально по своему онлайн-списку). Цена принята
   осознанно: **первая внешняя зависимость** проекта (`google.golang.org/grpc` + protobuf;
   сгенерированный pb-код коммитится, protoc нужен только при изменении стыка) — allowlist в
   `scripts/checkdeps.sh` правится явно в задаче P3.4. Отвергнуто: самописный стык поверх
   TCP (вариант interlude/yamux — отвергнут r4/ADR-0005) и «один процесс на фазу 3» (противоречит
   зафиксированной топологии; склеивание процессов позже потребовало бы переделки жизненного
   цикла). Порты — канон L2J (2106/7777/9011), конфигурируются флагами.
3. **Сетевой ввод-вывод — шлюз; мировая логика видит только письма.** `conn` — провода (ридер на
   коннект, расшифровка, `conn.Handler`); `gateway` — предсессионная фаза (ProtocolVersion →
   KeyPacket → AuthLogin → CharList → CREATE → CharacterSelect) и назначение пакетов стационарной
   фазы в порции ближайшего тика (настенные часы — только здесь, ADR-0003 D1); `encode` —
   стейтлес-стадия энкода с per-client FIFO (ADR-0004 ось 1). После EnterWorld пакеты клиента —
   слепой push payload-байт в ящик сущности персонажа (ADR-0003 §2), разбор — на применении у
   владельца представлениями protocol. Исходящее: регион компонует кадры в тике (compose,
   single-writer) → очередь encode → провода. Отвергнуто: разбор пакетов в шлюзе (маршрутизация и
   знание мира в шлюзе — против ADR-0003 §4); исходящая запись из тика региона (крипта в тике —
   против ADR-0004 ось 1).
4. **Предсессионная фаза живёт в шлюзе; персист персонажей — актор.** Хендшейк и CharList —
   протокольная сессия, не мировое состояние: шлюз владеет ею. Доступ к файлам персонажей
   (CharList, CREATE, снимок при логауте) — через persist-актора: единственная горутина-писатель
   файлов, запросы и ответы — письма через транспорт (fromID шлюза; шлюз регистрирует свой ящик в
   карте, ответы дренит своим циклом). Single-writer персиста — по духу инварианта 3; мьютекс в
   шлюзе отвергнут (инвариант 3 допускает мейлбокс/atomic/статику — мьютексы нигде, кроме
   этапа-1 транспорта, не заводим). Таксономия transport расширяется явной правкой (Kind
   персист-запросов, класс reliable). Правки ADR-0005: рёбра `world → persist` и
   `gateway → persist` (типы снимка/запросов; файловый I/O — только у актора).
5. **Модель персонажа и персист: плоские файлы собственного формата, без БД.** Персонаж — поля на
   `world.Entity` (имя, класс/раса/пол/причёска, уровень, позиция, курсор и состояние движения);
   снимок на диск — плоский формат по прецеденту артефакта P2.7 (магия + версия схемы + чексумма,
   атомарная замена createTemp+rename), файл на аккаунт `chars/<account>.l2c`, до 7 персонажей
   (канон). Логаут — персист; рестарт с kill -9 теряет прогресс с последнего логаута —
   зафиксировано как цена (write-behind снапшоты и WAL — фаза 5, ADR-0003 §8). Аккаунты —
   авто-создание при первом входе (канон-опция), пароль — PBKDF2-HMAC-SHA256 (stdlib), файлы
   `accounts/<login>.l2a` в LS-каталоге. Отвергнуто: SQLite/pgx (зависимость и инфраструктура для
   ~30 полей; DB-центричная модель — против write-behind ADR-0003/r4); `encoding/gob`
   (не гарантирует совместимость формата между версиями Go при эволюции полей — фаза 5 добавит
   инвентарь; недетерминированный дамп мешает отладке).
6. **Движение — сервер-авторитетное по r1, поверх готовых примитивов P2.4.** `MOVE_TO_LOCATION` —
   намерение: регион валидирует путь `geo.Map.ValidLocation` (кламп до дальней достижимой),
   двигает сущность по пути в фазе A тика с серверной скоростью, бродкастит свою позицию
   (`CHAR_MOVE_TO_LOCATION`), не клиентскую. `VALIDATE_POSITION` — сверка с кинематикой:
   токен-бакет скорости на сущности (r1: CAP ~1–2 с хода, SLACK), дрейф сверх порога — snap-back
   (`VALIDATE_LOCATION`/`TELEPORT_TO_LOCATION` по канону). Спавн/вход — server-authored телепорт
   (флаг `pendingTeleport`, r1) — корректно гасит бакет. Скорость — константа базового персонажа
   канона (статы/баффы — фаза 4), пороги сверяются по канону с атрибуцией. Отвергнуто:
   «валидация пакета» вместо симуляции (r1 — главный принцип анти-чита); A* (кламп линейного
   сегмента достаточен для walking skeleton; обход лабиринтов — фаза 4/6).
7. **Минимальный knownlist — вырожденная конфигурация механики ADR-0004, не throwaway.** Ось 6:
   одна ячейка ≈ регион, join = «сущности региона в радиусе от наблюдателя», без LOD и бюджета
   (фаза 6). Но дисциплина — полная: per-owner блоб (SoA-сегменты, полные пейлоады, dirty-манифест,
   свап после шага, иммутабельность), стабильные плотные слоты с детектом реюза по вечному id,
   view set — пересобираемое outbound-состояние региона (недоступен игровой логике, в реплей не
   входит), два случая ухода из членства (маркер переезда в фазе 3 не возникает — хэндоффов нет;
   исчезновение записи → немедленный DeleteObject), предикат видимости пары — одна функция
   (в фазе 3 — тривиальная, расширяется флагами). Радиус известности и гистерезис enter/exit —
   числа канона (aCis KnownList; OQ-3 ADR-0004) — сверка с фиксацией в задаче. Синтетический
   join-бенч (проверка решения ADR-0004: константа ~7–11 нс/пара, порядок величины) — обязателен.
8. **NPC-население — из спавнов статики, без AI, отдельной задачей.** Спавны P2.2 (точечные +
   территориальные, RNG региона для точки территории) разворачиваются в сущности при старте
   региона; NPC стоят (бой/AI/респавн-таймеры — фазы 4/6), видны через NpcInfo, `Npc`-поля
   репликации уже типизированы в P2.2 (Name/Title/Level/Type/Collision*). Радиус AoI защищает
   клиента от лавины NpcInfo. Мир на приёмке живой, датапак P2 употреблён, задача убираема без
   переделок, если фазу придётся резать. Отвергнуто: пустой мир (интеграционный риск NPC-пакетов
   всё равно вскроется в фазе 4 — дешевле здесь, на двух клиентах); фильтр спавнов по стартовой
   зоне (лишняя конфигурация; счётчик сущностей и числа NpcInfo — в журнал на живом прогоне,
   разрезка — по числам).
9. **Реплей-харнесс — через шов шлюза; сверка свёртки, не исходящего потока.** Шов назначения
   порций (doc-контракт gateway) инъектируется харнессом: лог порций D5 (письма + границы тиков
   + advisory-входы + переезды) прогоняется через тот же fold. Критерий: два прогона одного лога →
   идентичные канонические дампы свёртки (порции/состояние региона); прогон лога живой e2e-сессии
   → идентичный дамп финального состояния. Исходящий поток потоку клиента не сравнивается — он
   недетерминирован по построению (ADR-0004 «Цена»); корректность исходящего — контракт-тесты
   ботов (нет двойников, DeleteObject в срок). RNG от (regionID, tick) делает стартовое разворачивание
   спавнов воспроизводимым без записи случайных выборов.
10. **Тест-драйверы — l2client (бот-режим), тап — источник живых фикстур.** `internal/l2client`
    расширяется представлениями пакетов мира (переиспользуются те же protocol-views, что пишет
    сервер) и лёгкими сценарными командами (движение, чат, логаут): e2e-тесты и CI-смоук — два
    бота против настоящего l2go (LS+GS in-process, стык — сетевой gRPC на localhost; разделение
    процессов — ручная КТ и CI-сборка обеих cmd). Сценарий-сервер остаётся для golden-юнитов
    протокола. Тап при ручной приёмке ставится между реальным клиентом и сервером: журнал сессии →
    новые golden-фикстуры (прецедент P1.6). Отвергнуто: отдельный «бот»-пакет сейчас (рой ботов —
    фаза 4); e2e только на моках (не снимает интеграционный риск — смысл фазы).
11. **CI-ворота фазы 3: race + e2e-смоук на синтетике + replay-тест.** `make check` (уже: build,
    lint, checkdeps, `-race` в CI) дополняется: e2e-смоук (2 бота, синтетический артефакт из
    testdata P2, asserts взаимной видимости/чата/персиста) и replay-тест (бит-в-бит свёртка на
    записанном логе) — оба как обычные `go test`, без новых CI-механик. Бюджеты p99 тика и
    нагрузочные смоуки — НЕ ворота фазы 3 (фаза 4 по ADR-0002/0004; join-бенч и счётчики —
    датчики в журнал).
12. **Правки ADR-0005 — только явные рёбра, перечислены заранее:** `world → persist` и
    `gateway → persist` (P3.3/P3.5 — типы снимка и запросов, файловый I/O у актора); allowlist
    внешних модулей += grpc/protobuf (P3.4). Пакеты `internal/login`, `internal/loginlink`,
    `internal/party`… уже строками матрицы — код рождается в них, правка не нужна; `cmd/l2login`
    покрывается строкой `cmd/*`. Тестовый каталог `tests/e2e` матрицей не проверяется
    (checkdeps фильтрует `internal|pkg`) — интеграционные тесты живут там.

## Задачи

Формат: spec-first слайс; проработка — стадии S0–S4 конвейера ADR-0006. Критерии фальсифицируемы.
Статусы: ⬜ не начата, 🔄 в работе, 👀 на ревью человека, ✅ принято, ⛏ заблокирована.

### P3.1 Транспорт: карта адресов и ящики — ⬜

**Спецификация.** Реализация `internal/transport` под существующую таксономию (конверт, классы,
домены — уже в коде):

- **Карта `id → ящик`:** запись при рождении сущности, перезапись запрещена; чтение — один
  atomic.Load без блокировок; запись — `atomic.Pointer` на COW-версию (этап-1 допустим sharded
  RWMutex — выбор в задаче с бенчмарком). Дисциплина отправителя: lookup → enqueue смежные
  операции, указатель между отправками не кешируется.
- **Ящик:** MPSC FIFO с мигрирующим читателем; этап-1 — мьютекс внутри enqueue (микросекунды,
  неблокирующий для читателя и отправителей на чтение), контракт уже lock-free-совместимый.
  Заголовок ящика рядом с записью сущности. Курсор-водяной знак двигает только подтверждённый
  читатель; изъятие = один атомарный store знака на границу; сбор сегментов — только ниже знака.
- **Деспавн:** dead-флаг ящика (проверка в enqueue под мьютексом этапа-1 — поздний страгглер
  получает классовый дроп + метрику, не тихую потерю), финальный дрен по классам, свап карты на
  синглтон «мёртв»; ID не переиспользуются (счётчик ID — monotonic).
- **Контрольный ящик региона** с приоритетной полосой и бюджетом; переполнение полосы — падение в
  обычный разбор, не дроп (ADR-0003 §5).
- **Единая декларация очередей** (ADR-0003 §4): ящик, контрольный ящик, — ограничение, политика
  переполнения по классам (fire-and-forget кап + метрика; reliable/transfer живому не дропаются),
  метрики глубины/латентности.
- Пер-тиковые API порций не вводится (это world); transport — только доставка.

**Критерии приёмки.**
- Стресс-тесты инвариантов И2/И4/И5 (ADR-0003 §11 — обязательны с фазы 3): ровно один читатель при
  миграции потребителя (инжектируемое шево теста); письмо — один push/одно изъятие (счётчики);
  порядок отправителя сохраняется при гонке продьюсеров и смене читателя; всё под `-race`.
- Компакция: страгглер в мёртвый ящик — классовый дроп + метрика (машина: счётчики по классам).
- Модельный тест переполнения: fire-and-forget дропается по капу, reliable/transfer живому
  копятся — память ограничена окном обработки читателя.
- Бенчмарки enqueue и изъятия (реестр ADR-0005 «Enqueue/изъятие ящика», «Отправка письма»);
  baseline → `benchmarks/`; 0 аллокаций на enqueue вне роста очереди.
- Fuzz/злые входы не применимы (внутренний API) — вместо этого property-тесты на инварианты.

**Ревью-профиль:** S2 — инвариантщик, конкурентщик, перформансер, прагматик; S8 — + тестировщик.

**Зависимости:** нет; первая задача фазы.

**Ссылки:** ADR-0003 (§3–§7, §11, И1–И12); ADR-0005 (матрица: transport без зависимостей; реестр
путей); r0 (актор-меш, мейлбокс).

### P3.2 Метроном и регион-актор: свёртка тика — ⬜

**Спецификация.** Реализация `internal/world` (типы Entity/Suitcase/Portion — уже в коде):

- **Метроном** (ADR-0002): одна горутина, `time.Ticker` с периодом `time.Second/worldTickHz`
  (константа конфигурации, 10 Гц; хардкод «100 мс» запрещён); активный сет; на такт N —
  non-blocking send номера тика в cap-1 канал региона; провал = дроп-метрика; вотчдог-метрика
  (текущийТик − doneTick > k → slog, счётчики; никакой блокировки).
- **Регион-актор:** `select {мейлбокс, тик}`; дисциплина шага — drain-mailbox(bounded) → фаза A(dt)
  → фаза B(capped) → публикация снапшота → `doneTick.Store(n)`. dt = (число тиков с прошлого
  шага) × период — по счётчику тиков, не по настенным часам (D1; дропнутый тик даёт dt = 2×период
  — тест обязателен). Обход сущностей — по сортированному слайсу id (D3; итерация по map в игровой
  логике запрещена — правило пакета). RNG региона — `math/rand/v2` с PCG-сидом от (regionID, tick)
  (D2); общий RNG отсутствует.
- **Порции и лог (D5):** изъятие писем на границе тика → `Portion`; лог порций: для каждого ящика
  последовательность (письма, границы тиков с номерами) + advisory-входы + лог переездов;
  заголовки — всегда, payloads — по флагу (кольцевой буфер или файл; формат — детерминированный,
  реверсивный). Шов инъекции порций (для реплей-харнесса P3.11) — часть контракта свёртки:
  fold(тик, состояние, порции) — чистая функция шага, отделяемая от доставки.
- **Политика паники:** `recover` в шаге → тик провален, счётчик; повторные — заморозка региона +
  slog-алерт (деградирует регион, не процесс; полная лестница T1–T3 — фаза 4+).
- Сущности фазы 3: игроки и NPC на общем каркасе; чемодан — только тип (миграция не исполняется).
- `world.TickHz`/период — конфигурация; включение/выключение тикования региона по активному сету
  (в фазе 3 регион всегда активен — но через общий механизм сета, не отдельной веткой).

**Критерии приёмки.**
- Детерминизм: два прогона одной и той же последовательности порций через fold → идентичные
  канонические дампы состояния региона (машина; дамп — детерминированная сериализация по
  возрастанию id).
- D1-тест: искусственный дроп тика (кап-1 занят) → следующий шаг получает dt = 2×период;
  дроп-метрика инкрементирована.
- D2/D3-тест: RNG воспроизводим от (regionID, tick); обход детерминирован (порядок применения
  портций не зависит от map-итераций — фиксируется порциями в порядке id).
- Порядок: письма одного отправителя применяются в порядке push (инвариант И5) на живом
  регионе-цикле с несколькими продьюсерами (`-race`).
- Паника в обработчике письма → recover, тик провален, регион жив (тест с инъекцией паники).
- Бенчмарк тика региона (реестр «Тик региона / SoA-проход») на синтетическом населении
  (100/1000/10000 сущностей): baseline → `benchmarks/`.
- Лог порций: запись → чтение → реконструкция последовательности порций (раундтрип формата).

**Ревью-профиль:** S2 — инвариантщик, конкурентщик, прагматик (+ перформансер — горячий путь);
S8 — + тестировщик.

**Зависимости:** P3.1 (ящики, изъятие).

**Ссылки:** ADR-0002 (метроном, дисциплина шага, коалесинг); ADR-0003 (§4 разбор на границе тика,
D1–D5, И10); r3 §1–§2; AGENTS-инварианты 7–8.

### P3.3 Персонаж, аккаунт, персист-актор — ⬜

**Спецификация.** Модель и минимальный персист фазы 3 (без предметов — фаза 5):

- **Персонаж:** поля на `world.Entity` (Name, ClassID, Race, Sex, Face/Hair, Level, Exp/SP,
  курсор/heading — набор по минимальному потребителю: CharSelectionInfo, CharInfo/UserInfo
  репликации); чемодан несёт всё состояние (проверяется тестом наравне с P2-прецедентом).
  Стартовая позиция/внешность нового персонажа — дефолты канона (порт с атрибуцией: координаты
  стартовой деревни, поля создания).
- **Формат персиста:** плоский собственный (магия, версия схемы, поля, чексумма — прецедент
  P2.7), файл на аккаунт `chars/<account>.l2c` (снимки всех персонажей аккаунта), атомарная
  замена createTemp+rename; версия схемы не совпала → явная ошибка (миграций нет как класс —
  персональный сервер, пересоздание допустимо; фиксируется в doc).
- **Persist-актор:** единственная горутина-писатель файлов; запросы (CharList, CreateChar,
  SaveSnapshot) и ответы — письма через транспорт (fromID = шлюз/регион); шлюз регистрирует свой
  ящик в карте (шлюз — легитимный адресат, ADR-0003 глоссарий). Правка таксономии transport:
  Kind персист-запросов (reliable) — явная правка реестра Kind с обоснованием в реестре задачи.
- **Аккаунты (LS-сторона, `internal/login`):** авто-создание при первом входе; пароль —
  PBKDF2-HMAC-SHA256 (stdlib `crypto/pbkdf2`), соль на аккаунт, файлы `accounts/<login>.l2a`
  (плоский формат, чексумма); неверный пароль → LoginFail(reason) по канону. Каталоги
  данных/персиста — флаги/env (прецедент P2).
- **Правка ADR-0005:** ребро `internal/world → internal/persist` (типы снимка; I/O — только у
  актора); правка `scripts/checkdeps.sh` синхронно. (Ребро `gateway → persist` — в P3.5.)

**Критерии приёмки.**
- Golden: снимок → файл → чтение → идентичный снимок (раундтрип); битый файл/чужая версия схемы/
  чужая чексумма — детерминированная ошибка, не паника.
- Атомарность: kill между createTemp и rename не оставляет частичный файл (тест симулирует отказ
  на шве записи).
- Persist-актор: конкурентные запросы от N «шлюзов» — все ответы корректны и не интерливятся
  (`-race`); ответы адресуются отправителю (fromID).
- Аккаунты: авто-создание; верный/неверный пароль; повторный вход с тем же паролем — PBKDF2
  верифицируется за разумное время (бенчмарк в журнал, итерации — параметр).
- Ворота зелёные; checkdeps с новым ребром зелёный.

**Ревью-профиль:** S2 — инвариантщик, безопасник (учётные данные), прагматик; S8 — + тестировщик.

**Зависимости:** P3.1 (транспорт для писем актора).

**Ссылки:** ADR-0003 (§8 — персист как потребитель выходного потока; фаза 5 — WAL/write-behind);
ADR-0005 (правка матрицы); r4 (DB-модель референсов отвергнута); решения 4–5.

### P3.4 LoginServer и gRPC-стык — internal/login, internal/loginlink, cmd/l2login — ⬜

**Спецификация.** Login-сервер (протокольные писатели/представления — всё из P1.4, кроме их
композиции ничего нового в protocol не типизируется):

- `internal/login`: слушатель 2106; флоу: Init (RSA-модуль, Blowfish-ключ, session ID) →
  AUTH_GAME_GUARD → GG_AUTH(ok) → REQUEST_AUTH_LOGIN (RSA-блоб: разбор `RequestAuthLoginView` +
  RSA-дешифрация, сверка с учётками P3.3) → LOGIN_OK → REQUEST_SERVER_LIST → ServerList (из
  зарегистрированных GS; поля IP/порт — конфиг) → REQUEST_SERVER_LOGIN → PLAY_OK (пара ключей
  сессии — генерация, хранение в состоянии LS до истечения). Ошибки: LOGIN_FAIL/PLAY_FAIL по
  причинам канона; таймауты/лимиты коннектов (простые, конфиг).
- `internal/loginlink`: gRPC-протокол стыка LS↔GS (ADR-0005 п.2): `RegisterSession` (GS → LS при
  старте: адрес, hexID мира, имя), `ValidateSession` (GS → LS: аккаунт + 4 ключа → вердикт),
  `Kick` (LS → GS; в фазе 3 — метод протокола, реализация-заглушка с журналом). Прото-файл и
  сгенерированный код коммитятся; protoc в сборке не нужен. LS — сервер стыка (9011), GS — клиент;
  повторная регистрация GS — замена по hexID.
- `cmd/l2login`: wire-up (учётки, loginlink-сервер, слушатель 2106; graceful shutdown).
- **Зависимость:** `google.golang.org/grpc` + `google.golang.org/protobuf` — первая внешняя;
  правка allowlist `scripts/checkdeps.sh` (список: grpc, protobuf, genproto, и их транзитивные
  минимумы — фактически зафиксированный `go list -m all` хвост), фиксация цены в реестре задачи и
  журнале.

**Критерии приёмки.**
- Интеграционный тест: l2client (LoginClient) против in-process LS — полный happy-path (Init →
  PlayOk), лог golden; злые пути: неверный пароль → LOGIN_FAIL; неизвестный GS → PLAY_FAIL;
  мусорный RSA-блоб → детерминированный отказ без паники.
- Стык: GS-заглушка регистрируется → ServerList содержит адрес; ValidateSession на валидных/
  невалидных ключах → вердикт; обрыв стыка → GS исчезает из ServerList (тест).
- Автоматика повторного входа: второй логин того же аккаунта в LS допустим (канон: замена сессии);
  полигон «один онлайн на аккаунт» — GS-сторона, P3.6.
- Ворота зелёные с расширенным allowlist; в CI собираются оба процесса.
- Ручная КТ-2: реальный клиент владельца видит сервер в списке и получает PlayOk.

**Ревью-профиль:** S2 — инвариантщик, безопасник, доменщик, прагматик; S8 — + тестировщик.

**Зависимости:** P3.3 (учётки).

**Ссылки:** r4 (топология владельца, gRPC-стык, yamux отвергнут); ADR-0005 (п.2 топология,
матрица: login, loginlink); r2 §Фаза 1 (флоу логина — фактура P1.4); ADR-0001 (порты с атрибуцией).

### P3.5 Провода, шлюз, энкод-стадия — internal/conn, internal/gateway, internal/encode — ⬜

**Спецификация.** Сетевой контур GameServer до выбора персонажа включительно:

- `internal/conn`: accept-цикл; на коннект — ридер-горутина (deadlines, TCP_NODELAY, разрез
  потока `protocol.NextFrame`, расшифровка GameCrypt) и писатель (очередь кадров); события —
  через `conn.Handler` (шов уже определён). Криптодвижок — на соединение, без внутренней
  синхронизации (владелец — соединение; P1.1-контракт).
- `internal/gateway`: реализует `conn.Handler`. Предсессионная фаза (стейт-машина на коннект):
  ProtocolVersion (746; чужая → KeyPacket(result=0) + разрыв) → KeyPacket (генерация game-ключа,
  включение шифрования) → AuthLogin (4 ключа; валидация сессии — инъектируемый интерфейс
  `SessionValidator`, реализация из loginlink, wire-up в cmd; шлюз не импортирует loginlink) →
  CharList (письмо persist-актору, ответ — в ящик шлюза; таймаут → GSLoginFail) → CHARACTER_CREATE
  (view + минимальная валидация имени канона; создание — persist-актором; CharCreateOk/Fail) →
  CharacterSelect → CharSelected. Назначение: предсессионные пакеты обрабатывает сам шлюз;
  стационарные (после EnterWorld) — слепой push в ящик сущности (P3.6); настенные часы — только
  здесь (тик назначения для порции).
- `internal/encode`: стейтлес-стадия: per-client FIFO кадров (lossless до disconnect — рост только
  глубина; коалесинг — только в compose тика, не в очереди; ADR-0004 ось 1); слэб на кадр из
  `pkg/bufpool`, криптоблок, запись в conn; метрика глубины/латентности compose→socket.
  Пакеты-писатели protocol пишут прямо в слэб (конвенция фазы 1).
- Новые пакеты protocol (по канону Mobius Interlude, с атрибуцией): представления C→S
  (CharacterCreate, EnterWorld, CharacterDelete — если вошло в скоуп по канону флоу) и всё
  недостающее для GS-предсессии; golden-фикстуры — синтетика по канону (живые — с КТ).
- **Правка ADR-0005:** ребро `internal/gateway → internal/persist` (типы запросов/ответов).

**Критерии приёмки.**
- Интеграционный тест: l2client проходит GS-хендшейк + CharList + CREATE + выбор персонажа против
  in-process контура (с persist-актором и заглушкой SessionValidator); повторный вход тем же
  аккаунтом при живом первом — GSLoginFail (полигон «один онлайн», состояние шлюза).
- Злые входы: мусорные/обрезанные кадры, чужая версия протокола, AuthLogin мимо валидатора,
  CREATE с инвалидным именем/9-м персонажем — детерминированные ответы канона или разрыв, без
  паники (таблица).
- Энкод: два клиента, FIFO не перемешивает кадры одного клиента (`-race`); потеря кадра в очереди
  исключена (lossless — тест на переполнение-имитацию: очередь растёт, disconnect по порогу
  тиков).
- Бенчмарк энкод-кадра/криптоблока на потоке N клиентов (реестр «Энкод/композиция кадра»);
  baseline → `benchmarks/`.
- Ворота зелёные; checkdeps с новым ребром зелёный.

**Ревью-профиль:** S2 — инвариантщик, конкурентщик, безопасник, прагматик; S8 — + доменщик,
тестировщик.

**Зависимости:** P3.1 (ящик шлюза), P3.3 (persist), P3.4 (SessionValidator-семантика).

**Ссылки:** ADR-0004 (ось 1: граница compose/энкод, lossless, per-client FIFO); ADR-0005 (матрица
conn/gateway/encode); r3 §2 (стейтлес-стадии); решения 3–4.

### P3.6 Вход в мир, спавн, логаут — ⬜

**Спецификация.** Замыкание флоу EnterWorld → Logout (набор пакетов — по канону EnterWorld-flow
Mobius Interlude, состав фиксируется в S0 сверкой с каноном и фиксируется в реестре):

- **EnterWorld:** C→S (view); шлюз — слепой push в ящик... адресата ещё нет: сущность персонажа
  создаёт/поднимает регион по контрольному письму EnterWorld{connID, account, charID, ключи}
  (шлюз отправляет после CharSelected+EnterWorld; сущность появляется в регионе: спавн на
  сохранённой/стартовой позиции, бинд исходящего потока connID ↔ EntityID в состоянии региона;
  pendingTeleport-флаг r1). Self-набор клиенту по канону: UserInfo, CharInfo, пустые ItemList /
  ShortCutInit / SkillList и обязательные системные пакеты EnterWorld-флоу (состав — S0;
  расхождение канонов — списком в реестр, прецедент P1.1).gameTime — из счётчика тиков мира (D1).
- **Логаут:** Logout C→S → регион: снимок персонажа письмом persist-актору (reliable; ответ не
  блокирует выход — таймаут с повтором на следующем тике), деспавн (в фазе 3 наблюдателей нет —
  DeleteObject появится в P3.8; контракт деспавна закладывается: dead-маркер ящика, grace-окно,
  финальный дрен — P3.1-механика), LeaveWorld → шлюз закрывает коннект; повторный вход тем же
  аккаунтом после деспавна разрешён (полигон «один онлайн» — по живому бинду, не по файлу).
- **Аномалии:** разрыв коннекта без Logout = тот же путь деспавна (dead-детект сокета →
  контрольное письмо региону); рестарт сервера с живыми сессиями — персист последнего логина не
  гарантируется (зафиксировано; write-behind — фаза 5).
- Новые S→C писатели protocol: UserInfo, CharInfo (самовидимость по канону), ItemList (пустой),
  ShortCutInit, SkillList, системные пакеты входа; SystemMessage (минимум для ошибок).
- Минимальное расширение l2client для e2e этой задачи: ожидатель self-набора (ждать опкод с
  таймаутом по трафик-логу); полный бот-набор (команды движения/чата, ожидатели knownlist) —
  P3.12 и последующие задачи по потребности.

**Критерии приёмки.**
- e2e-тест (l2client): вход персонажем, созданным в P3.5; клиент получил self-набор (ассерты по
  опкодам и полям позиции/имени); логаут → чистое закрытие; файл персонажа обновлён (позиция
  сохранена — чтение файла тестом).
- Перезаход: повторный вход после логаута — позиция = сохранённая (round-trip персиста на живом
  контуре).
- Двойной вход тем же аккаунтом: второй — GSLoginFail/разрыв; после закрытия первого — вход
  разрешён.
- Разрыв сокета без логаута — регион деспавнит сущность (dead-флаг ящика выставлен; grace-окно
  истекло — счётчики) — тест с таймером на шве.
- Тик без сущностей: пустой регион стабильно тикает/спит по активному сету (метрика).
- Ворота зелёные.

**Ревью-профиль:** S2 — инвариантщик, доменщик, безопасник, прагматик; S8 — + тестировщик.

**Зависимости:** P3.2 (регион), P3.3 (снимок), P3.5 (контур).

**Ссылки:** r2 §Фаза 3 (флоу входа/логаута); ADR-0003 (§3 рождения/деспавн, §8 персист); r1
(pendingTeleport); канон Mobius EnterWorld (атрибуция).

### P3.7 Движение и гео-валидация — ⬜

**Спецификация.** Сервер-авторитетное движение поверх P2.4 (канон семантики — GeoEngine/Movement
канона, порты с атрибуцией):

- `MOVE_TO_LOCATION` (view): намерение {target, origin}; регион в фазе B (кап) валидирует сегмент
  `geo.Map.ValidLocation` → кламп; фаза A продвигает позицию по валидированному пути со скоростью
  сущности (run-константа базового персонажа канона; walk/run — ChangeMoveType2 view, минимум);
  продвижение — чистая арифметика без гео-трейса между запросами (r1 «коаст»).
- Бродкаст своей позиции: `CHAR_MOVE_TO_LOCATION` (писатель), `STOP_MOVE` на остановке/клампе;
  `CANNOT_MOVE_ANYMORE` (view) принимается как стоп-сигнал (не как позиция).
- `VALIDATE_POSITION` (view): сверка с кинематикой — токен-бакет скорости на сущности
  (speedBudget += maxSpeed·dt до CAP; списание дистанции; SLACK-порог) + pendingTeleport-флаг
  (вход/спавн); дрейф сверх порога → коррекция сервера (VALIDATE_LOCATION / TELEPORT_TO_LOCATION
  по канону — snap-back), зачёт бакета; самовольный «телепорт» без флага = коррекция (r1-схема).
- `START_ROTATING`/`FINISH_ROTATING` — только heading-поля (view + отражение в Entity), если
  канон требует для отображения; наблюдатели получат heading в апдейтах P3.8.
- Скорость и пороги — константы канона с атрибуцией; таблица порогов (CAP/SLACK/step-height) —
  в конфиг с дефолтами.
- Расширение l2client по потребности: команда MoveToLocation + ожидатель валидаций/коррекций
  (переиспользуются в P3.8/P3.12).

**Критерии приёмки.**
- Синтетическая геометрия (фикстуры P2.3/P2.4): движение в стену → позиция = кламп-точка
  `ValidLocation`, клиенту STOP_MOVE на клампе (юнит-тест свёртки: письмо Move → тики → дамп
  позиции).
- Speedhack: scripted-валидации с завышенной дистанцией → snap-back + счётчик флагов
  (property-таблица: допустимый джиттер проходит, 2× скорость — коррекция).
- dt-дисциплина: дропнутый тик не ломает кинематику (тест P3.2 + бакет).
- e2e (l2client): бот шлёт движение к точке на синтетической карте, доходит, шлёт
  ValidatePosition по пути — ни одной коррекции (чистый путь); второй сценарий — движение в стену:
  остановка у стены.
- Бенчмарк фазы A продвижения на 100/1000/5000 движущихся сущностей (реестр «Тик региона»
  пополняется) → `benchmarks/`.
- Ворота зелёные.

**Ревью-профиль:** S2 — инвариантщик, доменщик, безопасник, перформансер; S8 — + тестировщик.

**Зависимости:** P3.6.

**Ссылки:** r1 (серверная авторитетность, токен-бакет, телепорты-флаг, батчинг фаз A/B); r2 §Фаза 3;
P2.4 (`ValidLocation`); канон GeoEngine/Movement (атрибуция).

### P3.8 Минимальный knownlist — internal/replica — ⬜

**Спецификация.** Ось 6 ADR-0004 — вырожденная конфигурация той же механики (не throwaway):

- **Блоб:** регион в конце тика публикует один иммутабельный per-owner блоб (свап указателя):
  SoA-сегменты по ячейкам (в фазе 3 ячейка ≈ регион — сетка присутствует типами, конфигурация
  вырождена), полный заголовок членства (битмап слотов, генерация), полные пейлоады записей
  (позиция, heading, внешний вид, тип записи: игрок/NPC), dirty-манифест чтения. Стабильные
  плотные слоты; реюз слота после деспавна детектируется вечным id (O(1) array-indexed).
  Аллокация блоба на каждый тик (переиспользование — фаза 6).
- **Join у владельца наблюдателя:** view set (кого клиент знает) + last-sent — пересобираемое
  outbound-состояние региона; каждый тик: join по dirty + членству, радиальная фильтрация
  гистерезисом enter/exit (радиусы — канон aCis KnownList; OQ-3 — сверка с фиксацией в реестре),
  предикат видимости пары — одна функция (фаза 3: тривиальная; каркас для флагов) → compose:
  вводы (CharInfo/NpcInfo), удаления (DeleteObject — «запись исчезла без маркера»), позиционные
  апдейты. Эпохи/hold-last — типы присутствуют, в фазе 3 не срабатывают (хэндоффов нет) —
  property-тест фазы 4.
- **Advisory-API:** инкапсуляция снапшот-типов в replica (уже каркас); потребители игровой логики
  фазы 3 — только сам join (свой блоб); шов логирования чтений готов (D4), трассировка — фаза 4.
- **Синтетический join-бенч** (ADR-0004 «Проверка решения»): заглушка-блоб + join-цикл; константа
  нс/пара — порядок величины 7–11 нс, выписка в журнал; не ворота.
- Референс-обязательства ADR-0004 (фаза 3): числа гистерезиса enter/exit (aCis), мгновенность
  DeleteObject при телепорте (OQ-6 — телепорт-спавн фазы 3), идемпотентность спавн-пакетов по
  живому клиенту (OQ-5 — КТ-4), дистанционность известности (OQ-8 — сверка по канону, фиксация).

**Критерии приёмки.**
- Set-equality: население известности клиента = view set = фильтр населения региона по радиусу
  (машина, на синтетическом населении с движением через границу радиуса).
- Уход из членства → DeleteObject ровно один раз; повторный вход через enter-радиус → спавн-пакет;
  осцилляция на краю радиуса гасится гистерезисом (счётчик churn-событий в тесте).
- Дисциплина публикации: блоб публикует только владелец, после шага, свапом; иммутабельность —
  читатель (join в тесте) не видит мураций (`-race`).
- View set недоступен игровой логике: пакетная инкапсуляция (компилятор) + тест-гейт.
- Join-бенч записан; доля join-стадии в тике — датчик в журнал.
- e2e (2 l2client, KT-4): второй клиент видит первого (CharInfo), видит его движение
  (CHAR_MOVE_TO_LOCATION), исчезновение при логауте (DeleteObject).
- Ворота зелёные.

**Ревью-профиль:** S2 — инвариантщик, конкурентщик, перформансер, доменщик; S8 — + тестировщик.

**Зависимости:** P3.7 (позиции/движение — вход join).

**Ссылки:** ADR-0004 (все оси, особенно 6; тест-обязательства фазы 3; OQ-3/5/6/8); r3 §3
(видимость ≠ владение); r0 (снапшоты).

### P3.9 Чат — SAY2 в радиусе известности — ⬜

**Спецификация.** Минимальный чат канона:

- `SAY2` C→S (view): {type, text, target?}; домен фазы 3 — только канал ALL (обычная речь,
  радиус известности); прочие типы канала (shout/trade/party/clan/tell) — явный SystemMessage
  «канал недоступен»/игнор с журналом (анти-скоуп: глобальные каналы и internal/chat — фаза 6).
- Обработка: регион-владелец (сущность-отправитель): валидация (длина текста, пустая строка,
  антиморзе-минимум отсутствует — фаза 6), broadcast `SAY2` S→C наблюдателям в радиусе речи
  (через view set P3.8; радиус речи — константа канона), включая отправителя (канон).
- Детали пакета: цвет/имя/objectId отправителя — по канону (атрибуция); writer + view + golden.

**Критерии приёмки.**
- e2e (2 клиента): сообщение первого видно второму и первому; за радиусом речи — не видно
  (синтетическая дистанция).
- Таблица злых входов: пустой текст, превышение длины, неизвестный type канала — детерминированное
  поведение канона/игнор с журналом, не паника.
- Golden encode/decode SAY2 (обе стороны).
- Ворота зелёные.

**Ревью-профиль:** S2 — доменщик, безопасник, прагматик; S8 — + тестировщик.

**Зависимости:** P3.8 (view set).

**Ссылки:** r0 (чат — non-spatial слой; ALL-речь — локальный broadcast регионом, глобальные
каналы — фаза 6); r2 §Фаза 3; канон Say2 (атрибуция).

### P3.10 NPC-население из статики — ⬜

**Спецификация.** Живой мир для приёмки (убираемая задача — режется без переделок):

- Разворачивание спавнов P2.2 при старте региона: точечные записи → позиция как есть;
  территориальные → случайная точка полигона/минмакс-Z (RNG от (regionID, стартовый tick) — D2,
  воспроизводимо в реплее); Count — N сущностей; banned-узлы исключаются (P2.5-геометрия).
  FakePlayersSkipped (80000–89999) — уже исключены статикой P2.2.
- NPC — сущности транспорта (ящики аллоцируются — прецедент для фазы 4), без AI: стоят,
  не двигаются, бессмертны (смерть/респавн — фаза 4+). Поля репликации — из P2.2 (Name, Title,
  Level, Type, Race, Collision*).
- `NPC_INFO` (writer, канон): полный набор полей канона для Interlude (внешность из NPC-шаблона,
  скорость — константы, title, имя); golden на синтетике.
- Показ: join P3.8 (радиус известности отсекает дальних); счётчик сущностей региона и NpcInfo на
  клиента при входе — в журнал (живой прогон КТ).

**Критерии приёмки.**
- Синтетика: N спавнов (точечный + территориальный + count + banned) → позиции в границах
  территорий, вне banned, ровно count сущностей (машина по дампу региона).
- Детерминизм разворачивания: одинаковый сид (regionID, tick=0) → идентичные позиции (два прогона).
- e2e: клиент при входе получает NpcInfo только для NPC в радиусе (счётчик пакетов в тесте);
  логаут/вход — повторный набор идентичен по id.
- Golden NPC_INFO.
- Ворота зелёные; бенчмарк тика региона с NPC-населением 1k/10k (фаза A по стоячим — копеечная)
  пополняет baseline P3.2.

**Ревью-профиль:** S2 — инвариантщик, доменщик, прагматик (+ перформансер при 10k); S8 — +
тестировщик.

**Зависимости:** P3.8 (видимость), P3.3 нет — P2.2 (статика).

**Ссылки:** r2 §Фаза 3 (живой мир); ADR-0003 §3 (рождения и спавны — состояние региона); P2.2
(NpcSpawn/Territory); решение 8.

### P3.11 Реплей-харнесс — D6 — ⬜

**Спецификация.** Продукционная фича детерминизма (ADR-0003 D6, AGENTS-инвариант 9):

- Формат лога порций (P3.2, D5) фиксируется как вход харнесса: письма + границы тиков с номерами
  + advisory-входы + лог переездов; payloads — по флагу записи (для реплея e2e-сессии флаг
  включается тестом).
- Харнесс: инъекция порций через шов шлюза/свёртки (P3.2) — тот же fold, та же статегия региона;
  выход: канонический дамп свёртки (последовательность порций + финальное состояние региона).
- Сверка: (а) идентичность двух прогонов одного лога (бит-в-бит дамп); (б) прогон лога живой
  e2e-сессии (вход двух клиентов + движение + чат + логаут) → дамп финального состояния равен
  дампу состояния живого прогона; (в) каждая находка «расхождение» = красный тест.
- Ретенция/размер: файл лога на запуск, payloads-флаг; ротация/тайм-тревел — OQ-8 ADR-0003,
  осознанно вне фазы 3 (фиксация в doc).
- Инструмент: минимальный `go run ./cmd/l2go -replay <лог>` или тестовый хелпер (выбор в S0;
  cmd-флаг предпочтителен — тот же бинарарь).

**Критерии приёмки.**
- Тест CI: записанный лог фиксированной e2e-сессии (в testdata, наша синтетика) — реплей
  бит-в-бит (дамп свёртки совпадает; повторный прогон — тоже).
- Живая e2e-сессия (тест генерирует и записывает) → реплей → равенство финальных состояний.
- Мутационная проба: изменение одного письма в логе → дамп меняется (харнесс чувствителен).
- Недетерминизм-проба: прямой map-обход в тике (временно подставленный) роняет детерминизм-тест
  (гатлинг D3) — или фиксируется невозможность пробы с аргументом в реестре.
- Ворота зелёные.

**Ревью-профиль:** S2 — инвариантщик, конкурентщик, прагматик; S8 — + тестировщик.

**Зависимости:** P3.2 (лог/шов), P3.6–P3.10 (полный флоу как предмет реплея).

**Ссылки:** ADR-0003 (D1–D6, §16 — «фаза 3 обязана родиться с реплей-харнессом»); ADR-0004
(«Цена»: реплей — свёртка, не outbound); решения 9.

### P3.12 E2E-харнесс, CI-ворота и приёмка фазы — ⬜

**Спецификация.** Сборка активов проверки фазы и приёмка владельца:

- `tests/e2e` (каталог вне матрицы checkdeps — только `_test.go`): поднятие LS+GS in-process
  (синтетический артефакт из testdata P2; стык — сетевой gRPC на 127.0.0.1:0), два l2client-бота:
  полный сценарий r2 — логин → создание/выбор → вход → взаимная видимость → движение обоих →
  встречное движение → чат → логаут первого (DeleteObject у второго) → логаут второго →
  персист-проверка позиций; asserts по трафик-логу клиентов.
- Расширение l2client: представления пакетов мира (переиспользуют protocol views/writers),
  сценарные команды (MoveToLocation, Say2, Logout), ожидатели (ждать CharInfo/NpcInfo/
  DeleteObject по опкоду с таймаутом). Сценарий-сервер P1.5 не трогается.
- CI: e2e-смоук (те же тесты, `-race` уже в CI), replay-тест P3.11; сборка `cmd/l2login` +
  `cmd/l2go` (в т.ч. `-tags embedded` на синтетике — прецедент P2.7).
- Makefile: цели `run-login`/`run-game` (dev-прогоны с путями), дополнение embedded-цепочки
  владельца: `make embedded` → запуск обоих процессов.
- **Приёмка владельца (КТ-5):** два реальных клиента Interlude против процессов владельца
  (dev-артефакт или embedded): полный сценарий; тап между клиентом и сервером — журнал сессии →
  новые golden-фикстуры протокола (прецедент P1.6); числа (счётчики сущностей, NpcInfo на вход,
  join-доля, тик) — выжимка в журнал. Расхождения живого клиента с ожиданием — реестр находок
  задачи (источник — тап-журнал).

**Критерии приёмки.**
- e2e-смоук зелёный в CI (включая `-race`), время теста в бюджете CI (число — в журнал).
- Трафик-логи ботов детерминированы по составу пакетов (повторный прогон — тот же набор опкодов
  на сценарий; тайминги не сравниваются).
- Оба процесса собираются в CI (обычная и embedded-сборка).
- КТ-5 исполнена: журнал приёмки с выжимками; живые фикстуры в testdata; ✅ фазы — за владельцем.
- Ворота зелёные.

**Ревью-профиль:** S2 — инвариантщик, прагматик, тестировщик; S8 — + тестировщик, доменщик
(облегчённый по составу, но полный по протоколу).

**Зависимости:** P3.1–P3.11.

**Ссылки:** r2 §Фаза 3 (критерий фазы — реальный клиент); ADR-0006 (S9); r4 (e2e-паттерны la2go —
форма, не модель); решения 10–11.

## Порядок исполнения

```
P3.1 (ящики) → P3.2 (метроном+регион) → P3.3 (персонаж+персист) → P3.4 (LS+gRPC-стык)
→ P3.5 (провода+шлюз+энкод) → P3.6 (вход/спавн/логаут) → P3.7 (движение+гео)
→ P3.8 (knownlist) → P3.9 (чат) → P3.10 (NPC) → P3.11 (реплей) → P3.12 (e2e+CI+приёмка)
```

- Порядок — критический путь end-to-end с ранними живыми контрольными точками: после P3.4 клиент
  уже логинится в живой LS (КТ-2), после P3.6 — в мире (КТ-3), после P3.8 — центральная веха r2
  (КТ-4). Интеграционный риск снимается порционно, а не одним большим Bang.
- P3.3 и P3.4 частично параллелизуемы, P3.9/P3.10 независимы между собой — при необходимости
  владелец может переставить (все зависимости указаны); конвейер ведёт по одной задаче за раз
  (прецедент p1/p2).
- Если фазу придётся резать: P3.10 (NPC) и P3.9 (чат) убираемы без переделок; P3.11 (реплей)
  обязателен по D6/ADR-0003 §16 — режется последним из всех.
- Правки ADR-0005/таксономии: рёбра world→persist, gateway→persist (P3.3/P3.5), allowlist grpc
  (P3.4), Kind персиста (P3.3) — каждая в своей задаче, синхронно с checkdeps.

## Анти-скоуп (в фазу 3 НЕ входит)

- **Бой целиком:** атака, урон, смерть/трупы, XP/SP-начисление, аггро, таргет-механика,
  ApplyDamage/KillCredit-письма — фаза 4 (таксономия уже готова, исполнения нет).
- **Предметы и экономика:** инвентарь (ItemList непустой), дроп/подбор, трейд, WAL, 2PC,
  transfer-журналы — фаза 5 (reserve→commit-письма не исполняются).
- **Второй регион и хэндофф:** граница с гистерезисом, директория владения, чемоданы, черновики,
  затравки, эпохи, hold-last, слуги — фаза 4 (типы присутствуют, протокол не исполняется).
- **Сон регионов и нагрузочная изоляция:** активный сет есть, квиесценция/будильные таймеры —
  фаза 4+; полный надзор T1–T3 (фриз/пейдж/graceful-лестница) — фаза 4+, здесь recover+лог.
- **AI мобов и респавн-таймеры** (мобы бессмертны и стоят), патруль — фаза 6.
- **AoI-производительность:** LOD-тиры, per-client outbound budget, дельта-пейлоады, пулы блобов,
  encode-once, бюджеты p99 как ворота, рой ботов и нагрузочные смоуки — фазы 4/6 (join-бенч —
  датчик, не ворота).
- **Чат вне ALL-канала:** shout/trade/tell/party/clan, internal/chat-пакет, анти-спам — фаза 6.
- **Скиллы, каст, стат-движок, баффы** (каркас скиллов P2.6 — данные без интерпретации) — фазы 4/6.
- **Админ/GM-команды, admin-API, harness-управление ботами** (строки матрицы ждут своей фазы).
- **Мультиверс/мульти-датапак, l2off-геодата, версии протокола кроме 746** — не поддерживаются.
- **Мастер-аккаунты, баны, kick через стык** (метод протокола есть, реализация — заглушка с
  журналом) — фаза 4+.
- **День/ночь SunRise/SunSet, погода, соц-действия, посадка (ChangeWaitType), таргет-анимации** —
  косметика следующих фаз (gameTime-поле уже корректно).
