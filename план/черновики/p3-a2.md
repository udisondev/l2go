# p3 — План фазы 3: Walking skeleton — войти и пробежаться (черновик a2)

Исполнение [r2.md](../../research/r2.md) §Фаза 3; архитектура мира — [r0.md](../../research/r0.md)
и [r3.md](../../research/r3.md), гео-дизайн — [r1.md](../../research/r1.md). Исполняемые решения:
ADR-0002 (метроном без барьера), ADR-0003 (транспорт/владение v10.2, И1–И12, D1–D6),
ADR-0004 (knownlist/AoI, ось 6 — минимальная экспозиция), ADR-0005 (карта компонентов — все
строки фазы 3 уже в матрице, новых пакетов план не заводит), ADR-0006 (ревью-конвейер; профиль —
в каждой задаче), ADR-0001 (порты семантики — с атрибуцией). Конвенции планов —
[README.md](../README.md); реестры находок — `план/ревью/<ID>.md`.

**Входы (что реально существует после фаз 1–2, 7/7 + 7/7).** Протокол: каталог 494 опкодов,
примитивы кодека, типизированные пакеты логин-флоу (Init/LoginOk/ServerList/PlayOk/…),
game-хендшейка (ProtocolVersion/KeyPacket/AuthLogin/CharSelectionInfo/CharSelected/Logout/
CharacterSelect) и Attack; golden-фикстуры + fuzz. Клиент: `internal/l2client` — полный флоу
(DialLogin → … → SelectChar → Run стационарной фазы с детерминированным трафик-логом) и
сценарий-сервер для тестов; `internal/tap`/`cmd/l2tap` — живые дампы. Статика: `internal/data`
(предметы, NPC, спавны, территории, зоны, скиллы — манифест входов), `internal/geo`
(парсер, `ValidLocation`/`NearestZ`/`CanSee`, 0 аллокаций), `internal/artifact` (артефакт
~1 ГБ, mmap/embed, `artifact.LoadFile`). Каркасы типов без реализации: `transport`
(конверт, Kind, классы — карты id→ящик нет), `world` (Entity/Suitcase/Portion — горутины
региона и метронома нет), `replica` (advisory-шов, Snapshot — блоба и join нет), `conn`
(Frame/Handler), `gateway` (Inbound), `encode` (Frame), `persist` (Record). `cmd/l2go` —
заглушка версии.

**Цель фазы:** минимальный игровой сервер end-to-end — авторизация → выбор/создание
персонажа → вход в мир → спавн → движение с гео-валидацией → видимость второго клиента
(knownlist по оси 6 ADR-0004) → чат → логаут с персистом — на каркасе конкурентности r0/r3
в минимальной экспозиции: одна горутина региона, ящики, метроном ADR-0002, реплей-харнесс
(D6). Приёмка — реальный клиент Interlude владельца: второй клиент видит первого. Статика —
только из компилированного артефакта P2.7 (embed/mmap).

**Оценка:** 11 задач, 13–17 агентных сессий + контрольные точки владельца (состав пакетов
входа в мир, персист-каталог, чеклист приёмки живым клиентом, приёмки ✅).

## Выход фазы (Definition of Done)

- [ ] `cmd/l2go` — один процесс, два слушателя (login 2106, game 7777 — флаги): `go build`
      и `make embedded` дают запускаемый сервер; статики грузится только артефактом
      (`artifact.LoadFile`/embed), исходники XML на старте не читаются.
- [ ] End-to-end интеграционный тест в CI (`internal/l2client` × 2 против in-process
      сервера на ephemeral-портах): логин обоих → CharCreate → CharSelect → вход в мир →
      A получил CharInfo(B) и B получил CharInfo(A) → движение A доведено до B
      (CharMoveToLocation) → чат доставлен обоим → логаут A дал DeleteObject у B →
      повторный вход A стоит в точке логаута (персист).
- [ ] Гео-валидация движения: на синтетической геометрии стена клампит путь (ValidLocation),
      speedhack-бюджет ловит рывок и корректирует (TeleportToLocation назад); тесты
      машинные.
- [ ] Известность по ADR-0004 ось 6: join = set-equality «население региона ∩ радиус
      наблюдателя»; уход из членства → DeleteObject; блоб публикует только владелец, свап
      после шага, иммутабелен; view set игровой логике недоступен (машинные тесты).
- [ ] Транспорт: карта id→ящик, MPSC с водяным знаком (этап-1 ADR-0003 §11 — мьютекс в
      enqueue), контрольный ящик региона, классовые политики дропа; стресс-тесты И2/И4/И5
      на инжектируемом шве + `-race` в CI; бенчмарки enqueue/изъятия (реестр ADR-0005).
- [ ] Метроном ADR-0002: 10 Гц из конфигурации, non-blocking send в cap-1, коалесинг-дроп
      + метрика, doneTick, вотчдог; dt = тики × период (D1); RNG (regionID, tick) (D2);
      обход по сортированному слайсу id (D3) — машинные тесты детерминизма.
- [ ] Реплей-харнесс (D6): лог порций (D5) пишется всегда; CI-тест прогоняет записанный
      лог сценария через тот же fold — свёртка бит-в-бит совпадает.
- [ ] Фазз входящих пакетов мира (малорменные C→S: Say2, MoveToLocation,
      ValidatePosition, CharacterCreate…) — детерминированный дроп, не паника; в CI-смоуке.
- [ ] Бенчмарки реестра ADR-0005 родились вместе с кодом: enqueue/изъятие, отправка письма,
      тик региона, публикация блоба, join AoI, энкод/композиция кадра — baseline в журнал.
- [ ] Ручная контрольная точка владельца: реальный клиент Interlude проходит чеклист
      приёмки (КТ-3); расхождения отлажены (l2tap-дамп по желанию).
- [ ] Все порты семантики — с атрибуцией; NCsoft-данных в репо нет (машина уже проверяет).

## Ключевые решения фазы (защита «что и почему»)

1. **Один процесс, два TCP-слушателя, стык login↔game in-process.** Login (:2106) и game
   (:7777) — разные сетевые сущности (клиент требует два коннекта), но один процесс
   `cmd/l2go`; стык — интерфейс с семантикой RegisterSession/Kick (ADR-0005 п.2), в фазе 3
   исполненный in-process (`internal/loginlink`, строка матрицы уже есть): login после
   PlayOk регистрирует сессию {account, playKey}, game при AuthLogin сверяет ключ.
   Альтернатива «два процесса + gRPC сразу» отвергнута: gRPC — первая внешняя зависимость
   проекта (сейчас ноль, allowlist пуст), protobuf-инфраструктура и двухпроцессный запуск в
   каждом тесте — цена без единого потребителя при одном мире. Буква ADR-0005 «стык всегда
   сетевой» осознанно исполняется поэтапно: сетевой транспорт loginlink поднимается с
   появлением второго мира или удалённого логина (фаза 6+, отдельная правка ADR-0005);
   в P3.6 в ADR-0005 вносится приписка о стадийности (правкой решения, не молча).
2. **Один сим-регион на весь мир, всегда активный.** Грид регионов, хэндофф, гистерезис,
   спящие регионы (r0) — фаза 4; skeleton их не отрабатывает и не имитирует. Регион —
   настоящая горутина-актор с мейлбоксом и тиком (не «объект в главном цикле»): каркас
   конкурентности r0 ставится здесь в минимальной экспозиции (r2). Отвергнуто «N регионов
   сразу, чтобы не переделывать»: хэндофф без боя и knownlist-дедупа по эпохам нечем
   проверить, а код-поверхность (чемоданы, директория, граничная известность) — это фаза 4
   целиком; вырожденный «регион без границ» не требует ни одной из этих частей.
3. **Транспорт — этап-1 по ADR-0003 §11: мьютекс внутри enqueue, контракт тот же.** MPSC с
   мигрирующим читателем и водяным знаком — нетривиальный lock-free код; этап-1 даёт
   контракт (один push/одно изъятие, FIFO, курсор, dead-флаг, классовые дропи) при
   микросекундном мьютексе, неблокирующем читателя и отправителей на чтение. Lock-free —
   фаза 4 по измерениям (решение ADR-0003, не пересматривается). Обязательные
   модель/стресс-тесты И2/И4/И5 на инжектируемом шве + `-race` — с этой фазы (реплей
   транспорт не полисит: лог пишется после очереди).
4. **Персист персонажей — файл на аккаунт, собственный плоский кодек, атомарная замена;
   пишет только владелец, на логауте.** Формат: один файл на аккаунт (аккаунт + персонажи)
   в серверовом каталоге данных (вне репо; путь — флаг), кодирование — плоский
   детерминированный кодек по образцу data/artifact (gob stdlib — допустимый выбор задачи,
   решается бенчмарком в S0–S4), запись temp+rename, чексумма. Write-behind/WAL/transferID —
   фаза 5 (ADR-0003 §8 прямо относит персист-слой туда); фаза 3 фиксирует цену: kill -9
   откатывает персонажа к последнему логауту/созданию — приемлемо для скелета, записано
   явно. Альтернативы отвергнуты: SQLite/БД — внешняя зависимость и инфраструктура ради
   двух записей в минуту; один бинарный блоб всех аккаунтов — точка отказа и роста;
   отложка персиста целиком в фазу 5 — ломает критерий фазы «логаут с персистом» из r2.
5. **Персонаж: полный CharacterCreate + CharacterSelect, инвентарь пуст.** Приёмка живым
   клиентом невозможна с чистой установки без создания персонажа (у владельца нет персов),
   поэтому CharCreate входит; CharDelete — осознанная заглушка (ответ-ошибка): удаление
   без предметов тривиально, но не нужно скелету. Стартовые позиции/статы/скорости
   новичка — маленькая Go-таблица порта character_templates канона (атрибуция; категория
   датапака отсутствует по факту P2). Предметы, инвентарь, дроп — фаза 5: ItemList
   отправляется пустым. Отвергнуто «заселить аккаунт персонажами CLI-флагом вместо
   CharCreate»: живой клиент обязан уметь пройти весь флоу сам, CLI-обход скрывал бы дыру
   входа.
6. **Известность: вырожденная подписка + настоящее членство по радиусу.** По оси 6
   ADR-0004: одна ячейка-весь-мир, без LOD/бюджета/стенсила — но членство фильтруется
   радиусом известности с гистерезисом enter/exit (числа — референс aCis/L2J KnownList,
   OQ-3, задача P3.7): без радиуса второй клиент при входе получит десятки тысяч NpcInfo
   (в датапаке 11 875 точечных спавнов) — пакетный шторм и смерть клиента, т.е. радиус —
   не оптимизация, а корректность репликации. Join исполняется у владельца наблюдателя
   поверх per-owner блоба; предикат пары — одна функция-каркас (входов-флагов в фазе нет;
   переоценка тестируется синтетическим швом), гео-LOS в известности отсутствует
   (дистанционность живого Interlude — проверить по референсу, OQ-8). Отвергнуто
   «спавнить всех NPC мира»: 12k сущностей в SoA-тике скелета бессмысленны без AI —
   спавнится конфигурируемый срез по зоне (стартовый город), полный мир — фаза 4+ с
   много regionalностью и спящими регионами.
7. **Тик — дословно ADR-0002/r3:** диспетчер-метроном (конфиг-частота 10 Гц), non-blocking
   send номера тика в cap-1 канал активных регионов, провал = дроп + метрика, doneTick —
   атомарный ack, вотчдог-наблюдатель; шаг: drain-mailbox (bounded) → фаза A (dt) →
   фаза B (capped) → публикация блоба → ack; dt = (счётчик тиков) × период (D1), хардкод
   времени запрещён (инвариант 7). Отвергнуто «тик-луп в главной горутине» и «тик по
   wall-clock dt»: оба ломают D1 и воспроизводимость реплея, а первый — ещё и шаблон,
   который фаза 4 масштабирует на сотни регионов.
8. **Шлюз: стейт-машина входа — в шлюзе per-conn; после EnterWorld — только письма.**
   Провода (ProtocolVersion/KeyPacket/крипта), AuthLogin (сверка playKey через loginlink),
   CharList/CharCreate/CharSelect — стейт-машина коннекта в шлюзе: это аутентификация и
   выбор, не события между сущностями мира (D4 их не касается). Рождение сущности —
   валидный EnterWorld: аллокация ящика, запись в карту, контрольное письмо региону;
   дальше каждый входящий кадр назначается шлюзом в порцию тика (wall-clock — только
   здесь) и уходит слепым push в ящик игрока. Исходящее — компоновка в тике региона
   (владелец наблюдателя, ADR-0004 ось 1) → encode-стадия вне тика (per-client FIFO,
   lossless до disconnect, слэбы на кадр). Отвергнуто «сущность-сессия с ящиком с момента
   TCP-коннекта»: пустой ящик и доспавн-логика ради формального «всё через ящики» —
   сложность без потребителя; граница «вход в мир» — семантическая (персонаж выбран) и
   совпадает с границей реплея.
9. **Чат фазы 3 — general-say в радиусе, репликацией региона-владельца.** Say2 (type=0)
   валидируется у владельца (длина, UTF-16) и рассылается CreatureSay всем наблюдателям в
   радиусе чата (референс) — это исходящий поток поверх известности, не домен. Отдельный
   `internal/chat`-домен (каналы trade/hero, PM, клан) — фаза 5+ (матрица уже содержит
   строку; код рождается со своим доменом). Отвергнуто «сразу chat-актор»: non-spatial
   домен ради одного типа пакета — слой без нагрузки; PM как письма между сущностями
   появится вместе с первым реальным потребителем.
10. **Тестовый актив — расширение `internal/l2client` до активного клиента.** Добавляются
    действия-писатели C→S (MoveToLocation, Say2, ValidatePosition), ожидатели пакетов
    (wait-for CharInfo/NpcInfo/DeleteObject/CreatureSay с таймаутом) и сравнение лога со
    сценарием; интеграционные тесты поднимают in-process сервер на 127.0.0.1:0. Сценарий
    -сервер остаётся для юнит-тестов клиента; боты-нагрузка — фаза 4. `cmd/l2tap` —
    инструмент владельца на приёмке живым клиентом (дамп расхождений), не CI.
11. **CI-ворота фазы 3:** (а) существующий `make check` (build/lint/checkdeps/-race — race
    гоняет CI, локально нет gcc — оговорка в PR); (б) интеграционный end-to-end smoke двух
    клиентов (тот же тест, что в DoD, — быстрый, ephemeral-порты); (в) replay-тест
    бит-в-бит; (г) фазз-цели шлюза в общий смоук-список; (д) fuzz/bench/load из r2 остаются
    по фазам: бюджеты бенчей и нагрузочный смоук с ботами — фаза 4 (заглушки ci.yml
    снимаются тогда). Новых машинных ворот сверх перечисленного фаза не вводит — до
    бенчмарк-бюджетов нет базовой линии под нагрузкой.

## Задачи

Формат: каждая задача — spec-first слайс для агента; проработка — стадии S0–S4 конвейера
ADR-0006. Критерии приёмки фальсифицируемы. Статусы: ⬜ не начата, 🔄 в работе, 👀 на
ревью человека, ✅ принято, ⛏ заблокирована.

### P3.1 Транспорт: карта id→ящик, MPSC с водяным знаком — internal/transport — ⬜

**Спецификация.** Первая реализация каркаса: конверт/Kind/классы уже в пакете; добавляется
исполнительная часть ADR-0003 §3–4, §11:

- Карта `id → ящик`: запись при рождении сущности, запись через COW-`atomic.Pointer` (или
  sharded RWMutex — выбор в задаче), чтение — один atomic.Load; дисциплина отправителя
  «lookup → enqueue смежные операции, не кешировать». Деспавн: dead-флаг (классовый дроп
  позднему страгглеру + метрика) → финальный дрен по классам → свап в синглтон «мёртв»;
  порядок под одним мьютексом этапа-1.
- Ящик: MPSC FIFO этапа-1 (мьютекс внутри enqueue; читателя и отправителей на чтение не
  блокирует), курсор-водяной знак (двигает только подтверждённый читатель), изъятие — один
  атомарный store знака на границу; пер-боксовый кап fire-and-forget с коалесингом/дропом
  и метрикой; transfer/reliable живому не дропаются никогда (ADR-0003 §4/§7).
- Контрольный ящик региона (чемоданы/ack/затравки) — та же структура, читатель — регион.
- Кодек payload писем: бинарные encode/decode для типов таксономии фазы 3 (движение,
  валидация позиции, чат, вход/выход, персист-команды) — реестр закрыт, новый Kind — правка
  таксономии; пишется по потребителям последующих задач, каркас (Kind→кодек) здесь.
- Инжектируемый шов (пересборка очередей/времени) для модель-тестов.

**Обоснование.** Этап-1 (мьютекс) вместо lock-free — решение ADR-0003 §11, не
пересматривается: контракт тот же, цена — микросекунды вне читателя. Payload []byte в
конверте уже зафиксирован каркасом — кодек в transport, рядом с реестром Kind.

**Критерии приёмки.**
- Стресс-тесты И2 (один читатель/ноль в окне), И4 (ровно один push = одно изъятие),
  И5 (FIFO отправителя) на инжектируемом шве; гонка под `-race` (CI) с десятками
  писателей и мигрирующим читателем; счётчики доставленных/дропнутых сходятся точно.
- Переполнение: fire-and-forget дропается по капу с метрикой; reliable/transfer живому
  копятся (тест на границе); dead-ящик: классовый дроп + метрика, не тихая потеря.
- Деспавн-порядок (флаг → дрен → свап) — модельный тест: страгглер после деспавна получает
  дроп по классу, дубль компакции исключён.
- Бенчмарки реестра: enqueue, изъятие порции, отправка письма (lookup+enqueue) — с
  baseline в журнал (benchstat-выписка).
- Ворота зелёные; transport без импортов (кроме stdlib) — матрица ADR-0005.

**Ревью-профиль:** S2 — инвариантщик, конкурентщик, перформансер, прагматик; S8 — +
тестировщик.

**Зависимости:** нет; первая задача фазы.

**Ссылки:** ADR-0003 (§3–4, §7, §11, §16 — P0.9-компонент); ADR-0005 (матрица: transport
без зависимостей; реестр путей — enqueue/изъятие, отправка).

### P3.2 Регион-актор, метроном, свёртка и лог порций — internal/world — ⬜

**Спецификация.** Каркас конкурентности r0/ADR-0002/r3 в минимальной экспозиции:

- Метроном: горутина-диспетчер, `time.Ticker` с периодом из конфигурации (дефолт 10 Гц;
  хардкод времени запрещён), активный сет, non-blocking send тика в cap-1 канал региона,
  провал — дроп + счётчик-метрика; doneTick — атомарная запись регионом после шага;
  вотчдог-функция (лаг > k тиков → лог) — наблюдатель, не исполнитель; debug-барьер за
  флагом («ждать ack'и N») для dev-проверок инвариантов.
- Регион: `for { select { mailbox: контрольные письма; tick: шаг } }`; шаг = drain-mailbox
  (bounded, по сортированному слайсу id сущностей — D3) → фаза A (dt: интерполяция
  движения, бакеты) → фаза B (capped: очереди событий — line-walk и пр.; излишек дальше)
  → публикация снапшота (шов replica; в этой задаче — пустой блоб, точка вызова
  обязательна) → doneTick. Паника шага — recover: тик провален, счётчик, повторные —
  заморозка региона + slog-алерт.
- dt = (число тиков с прошлого шага) × период метронома (D1) — по счётчику тиков, не по
  настенным часам; настенные часы в мире запрещены (шлюз — позже).
- RNG региона: сеется от (regionID, tick) (D2); никакой общий RNG не заводится.
- Рождение/деспавн сущностей: аллокация ящика всегда (P3.1), установка читателя-региона,
  вставка в сортированный слайс, смерть — маркер, деспавн — порядок P3.1; конверт payload
  — кодек P3.1. Один RegionID (константа) на весь мир — решение 2.
- Лог порций (D5): на каждый ящик региона — последовательность писем с границами тиков и
  их номерами; payloads — по флагу (кольцевой буфер/файл), заголовки — всегда;
  advisory-входы — всегда (появятся в P3.7). Формат лога — стабильный: его читает
  реплей-харнесс P3.10.
- Свёртка: чистая функция шага (state, порция, advisory-входы) → новое состояние +
  исходящие события; фактическая игровая логика минимальна (перемещение по валидированному
  пути из Entity.Dest, heartbeat), наращивается последующими задачами.

**Обоснование.** Порядок «регион раньше репликации и шлюза» — свёртка и лог порций
сквозные контракты (D1–D5): всё, что мутирует состояние, обязано родиться внутри них,
иначе реплей бит-в-бит недостижим ретроспективно. Публикация блоба — точка вызова здесь,
реализация — P3.3: дисциплина шага (ADR-0002 п.5) фиксируется целиком сразу.

**Критерии приёмки.**
- Детерминизм: два прогона одного сценария (письма по тикам) дают побитово равные логи
  порций и равное финальное состояние — машинный тест.
- Коалесинг: заблокированный регион (инъекция долгой фазы B) получает дропнутые тики,
  dt следующего шага = 2×периода (D1) — тест с швом времени.
- Дисциплина шага: порядок drain → A → B → publish → ack наблюдаем в тесте (счётчики
  фаз); кап фазы B переносит излишек на следующий тик.
- Паника обработчика: регион деградирует на тик, мир не падает; N повторных — заморозка +
  алерт (тест).
- Бенчмарк тика региона (реестр ADR-0005) на синтетической популяции; baseline в журнал.
- Ворота зелёные; world импортирует только transport/replica/encode/data/geo (матрица).

**Ревью-профиль:** S2 — инвариантщик, конкурентщик, перформансер, прагматик; S8 — +
тестировщик.

**Зависимости:** P3.1 (ящики, конверты).

**Ссылки:** r0 (регион-актор, select), r3 §1–2 (= ADR-0002), ADR-0003 (D1–D5, порция,
контрольный ящик), ADR-0005 (реестр — тик региона/SoA-проход).

### P3.3 Репликация/AoI минимальной экспозиции: блоб, join, view set — internal/replica — ⬜

**Спецификация.** Ось 6 ADR-0004 — вырожденная конфигурация той же механики, не throwaway:

- Per-owner SoA-блоб: один иммутабельный блоб на тик (аллокация заново на кадр), сегменты
  по ячейкам (фаза 3 — одна ячейка = весь регион), полный заголовок членства (битмап
  слотов, генерация) + полные пейлоады записей + dirty-манифест чтения; стабильные плотные
  слоты, реюз слота детектируется вечным id (O(1) array-indexed доступ на пару, хеш на
  пару запрещён — контракт доступа ADR-0004 ось 3); свап `atomic.Pointer` после шага
  (вызывается из P3.2-шва), публикует только владелец.
- Join у владельца наблюдателя: view set («кого клиент знает» + исходящая подписка) —
  пересобираемое outbound-состояние региона; членство = население региона ∩ радиус
  известности наблюдателя с гистерезисом enter/exit (радиусы — порт KnownList канона,
  числа фиксируются в задаче с атрибуцией; OQ-3). События членства: пересечение радиуса,
  спавн/деспавн — без пересканирования толпы каждый тик (детект O(#ячеек) — здесь одна
  ячейка, но форма — событийная, не «каждый тик полный скан»: скан только dirty).
- Два случая ухода: пропажа записи без маркера → немедленное DeleteObject у клиента
  (деспавн, выход из радиуса — одинаково); маркер переезда/hold-last — каркас типа в
  MembershipHeader уже есть, в фазе 3 не порождается (переездов нет) — юнит-тест на
  пустоту порождения.
- Предикат видимости — одна функция пары (наблюдатель, цель) для репликации и advisory;
  входы-флаги фазы 3 отсутствуют → предикат true, но переоценка при изменении входов
  исполняется и тестируется синтетическим флагом через шов (обязательство ADR-0004
  «Последствия»).
- Advisory-API (D4): чтения для игровой логики — только через него, каждое чтение
  логируется в порцию; снапшот-типы инкапсулированы в пакете (прямой дереференс
  невозможен физически); шов инъекции для реплея.
- Гео-LOS в известности отсутствует — документированное исключение (ось 4); параллельно в
  задаче закрывается OQ-8: сверка по референсу (aCis/Mobius), что живой Interlude ведёт
  известность дистанционно (сущность за стеной видна) — выжимка в реестр задачи.

**Обоснование.** Join у владельца наблюдателя, блоб, слоты, два случая ухода, предикат —
несущие части ADR-0004, без которых фаза 4 механически не расширяется; откладывать их на
фазу 4 значило бы строить бой поверх несуществующей репликации. Радиус членства — не
LOD-оптимизация, а корректность (решение 6): без него пакетный шторм NpcInfo.

**Критерии приёмки.**
- Тест-обязательства ADR-0004 фазы 3: join = set-equality «население ∩ радиус»; уход из
  членства → DeleteObject; дисциплина публикации (только владелец, свап после шага,
  иммутабельность после публикации — тест на попытку мутировать опубликованный блоб);
  view set недоступен игровой логике (компилируемость + тест шва).
- Гистерезис: бег по дуге на краю радиуса не осциллирует spawn/despawn (тест
  детерминированной траекторией); радиусы из референса зафиксированы с атрибуцией.
- Переоценка предиката: синтетический флаг через шов → →true/→false дают ввод/удаление —
  машинный тест.
- Advisory: каждое чтение даёт запись в порцию (реплей-инъекция подменяет значение — тест
  шва).
- Синтетический join-бенч (ADR-0004 «Проверка»): ~7–11 нс/пара — порядок величины и тренд
  в журнал, не ворота; бенчмарки публикации блоба и join (реестр ADR-0005).
- Ворота зелёные; replica импортирует только transport (матрица).

**Ревью-профиль:** S2 — инвариантщик, конкурентщик, перформансер, прагматик; S8 — +
тестировщик, доменщик.

**Зависимости:** P3.1, P3.2 (шов публикации, порции).

**Ссылки:** ADR-0004 (оси 1–4, 6; «Последствия» — фаза 3; OQ-3/OQ-8); ADR-0003 (D4,
§16 — advisory в модуле репликации); ADR-0005 (реестр — advisory, публикация блоба, join).

### P3.4 Персист персонажей и аккаунтов — internal/persist — ⬜

**Спецификация.** Минимальный персист (решение 4):

- Модель: Account{login, passwordHash (соль+sha-256/scrypt — stdlib), персонажи []Char};
  Char — поля, предписанные протоколом CharSelected/CharSelectionInfo (имя, раса, класс,
  пол, внешность, X/Y/Z, heading, уровень, exp/sp, HP/MP, базовые статы) + created/lastSeen;
  предметных полей нет (фаза 5).
- Хранилище: каталог данных сервера (вне репо, gitignored; путь — флаг/env), один файл на
  аккаунт; кодирование — плоский детерминированный кодек (по образцу data) или
  encoding/gob — выбор бенчмарком/простотой в S0–S4; запись атомарна (temp+rename),
  чексумма; чтение при старте и по требованию (лениво по аккаунту).
- Интерфейс владельца: пишет только регион-владелец (или шлюз на этапе входа — до
  рождения сущности; после EnterWorld — только регион): CharCreate, финальный персист на
  логауте, персист на graceful-shutdown (T3-набросок: стоп логинов, flush, exit — без
  полного надзора ADR-0003 §9, его фазы 4+). Формат WAL/снапшотов фазы 5 — анти-скоуп;
  Record-тип пакета остаётся на будущее.
- Регистрация аккаунтов: логин-сервер создаёт аккаунт при первом входе (без пароля —
  конфиг-флаг «открытый вход» для скелета; решение в КТ-1) или чтение существующего.

**Обоснование.** Один файл на аккаунт переживает добавление персонажей и полей без
миграций (версия схемы + пересборка не нужна — файл просто перезаписывается новым
поколением); пишет мало и редко. Альтернативы — в решении 4.

**Критерии приёмки.**
- Раундтрип: CharCreate → персист → рестарт-загрузка → поля равны (golden-тест); пустой
  каталог — чистый старт.
- Атомарность: kill на середине записи (инъекция) → на диске либо старое, либо новое
  поколение, не битое (чексумма детектит подмену — тест злого файла).
- Пароли: открытый текст не хранится (тест), неверный пароль — отказ входа (тест).
- Фазз/злые входы: битый файл аккаунта, чужая версия, усечённый — детерминированная
  ошибка с местом, не паника; изолированный аккаунт не валит остальные.
- Ворота зелёные; persist импортирует только transport (матрица — внешних зависимостей
  нет).

**Ревью-профиль:** S2 — инвариантщик, безопасник, прагматик; S8 — + тестировщик.

**Зависимости:** P3.1 (интерфейс владельца-писателя — типы писем персиста); контентно
использует protocol-типы CharSelectedData через шлюз (импорт — только transport, поэтому
модель Char своя, конвертация — в шлюзе/world).

**Ссылки:** ADR-0003 §8 (персист — потребитель выходного потока; WAL/write-behind — фаза
5); r2 §Фаза 3 (логаут с персистом) и §Фаза 5 (граница); ADR-0005 (матрица).

### P3.5 Провода игрового сервера и шлюз входа — internal/conn, internal/gateway, internal/encode — ⬜

**Спецификация.** Game-сторона проводов (login — P3.6):

- `conn`: TCP-слушатель :7777 (флаг), per-conn горутина чтения: TCP_NODELAY, read
  deadlines, разрез потока на кадры (protocol.NextFrame), расшифровка (crypto), handshake
  KeyPacket; Frame → Handler (шов уже определён). Злые входы: мусор/обрыв/битая крипта →
  закрытие коннекта с slog, не паника (безопасник).
- `gateway`: стейт-машина коннекта до входа в мир (решение 8): ProtocolVersion →
  KeyPacket → AuthLogin (сверка account/playKey против зарегистрированных сессий — стык
  loginlink, в этой задаче — интерфейс, реализация P3.6; юнит-тесты на фейковой) →
  CharSelectionInfo (из персиста) → NewChar/CharacterCreate (создание персонажа:
  валидация имени/класса/внешности по доменам канона, стартовая позиция из таблицы
  character_templates — таблица порта живёт в gateway или data-сыром виде по решению
  задачи) → CharacterSelect → рождение сущности игрока: аллокация ящика (P3.1),
  контрольное письмо региону EnterWorld{payload: персист-снапшот персонажа}.
- Назначение в порции: после рождения шлюз на каждом тике метронома собирает накопленные
  кадры коннекта и пушит их письмами слепым push в ящик игрока (wall-clock — только здесь:
  тик назначения по часам чтения); drain-кап на коннект, переполнение — коалесинг по
  типу пакета (MoveToLocation — последний побеждает) + метрика. OnClose → письмо
  LinkDead в ящик игрока.
- `encode`: стейтлес-стадия исходящего: per-client FIFO (lossless до disconnect — дроп
  кадра = вечный фантом, запрещён), энкод криптоблока и запись в коннект вне тика;
  слэбы аллоцируются на кадр (пул — фаза 6); вход — Frame из компоновки региона;
  backpressure = TCP + порог disconnect в тиках.
- Пакеты protocol (писатели S→C + представления C→S) по потребителю задачи: ValidatePosition,
  MoveToLocation, Say2, EnterWorld, CharCreate/CharDelete-ответы, Telegraph? — нет:
  TeleportToLocation (коррекция), SystemMessage-минимум; golden encode/decode на каждый,
  опкоды константами из каталога P1.3; сверка полей с Mobius/aCis с атрибуцией.

**Обоснование.** Стейт-машина входа в шлюзе, а не в регионе: до выбора персонажа нет
сущности и нет мира — обрабатывать эти пакеты в свёртке значило бы раздувать реплей
провода́ми. Граница «рождение сущности = EnterWorld» совпадает с границей свёртки и
реплея — чистый срез D4/D5.

**Критерии приёмки.**
- Интеграционный тест (in-process, ephemeral-порт): `l2client.DialGame` → Handshake →
  Auth (фейковый loginlink-реестр) → CharCreate → CharSelectionInfo показывает персонажа →
  SelectChar → сущность родилась (письмо региону получено, ящик в карте).
- Таблица злых входов на каждый C→S пакет задачи: обрезанный payload, мусорные опкоды,
  строки не по домену → детерминированный дроп/ошибка, не паника; фазз-цель в CI-смоук.
- Исходящее: per-client FIFO — порядок кадров одного клиента сохраняется под параллельной
  энкод-стадией (тест с интерливингом); lossless до disconnect (метрика глубины).
- Коалесинг входящих MoveToLocation под лавиной — тест (последний побеждает, метрика).
- Бенчмарк энкод/композиция кадра (реестр ADR-0005); baseline в журнал.
- Ворота зелёные; conn ← protocol/crypto, gateway ← conn/protocol/transport, encode ←
  protocol/crypto/bufpool — по матрице.

**Ревью-профиль:** S2 — инвариантщик, безопасник, конкурентщик, прагматик, перформансер;
S8 — + тестировщик, доменщик.

**Зависимости:** P3.1 (ящики), P3.2 (тик для назначения порций), P3.4 (CharCreate/CharList
в персисте).

**Ссылки:** ADR-0003 (§1 — шлюз: wall-clock и назначение порций; И12), ADR-0004 (ось 1 —
граница compose/энкод, lossless-очередь), ADR-0005 (матрица и реестр — энкод), r4
(`_refs/interlude` — фактура стейт-машины входа).

### P3.6 Login-сервер и стык loginlink — internal/login, internal/loginlink, cmd/l2go — ⬜

**Спецификация.** Логин-сторона (решение 1):

- `internal/login`: TCP-слушатель :2106 (флаг), полный серверный флоу поверх готовых
  писателей: Init (sessionID, scrambled modulus, BF-ключ) → AuthGameGuard/GGAuth →
  RequestAuthLogin (RSA-блок → аккаунт/пароль; авто-создание аккаунта по конфигу КТ-1) →
  LoginOk → ServerList (один мир: game-хост из конфига) → PlayOk (playKey выдаётся).
  Повторный вход того же аккаунта — Kick предыдущей сессии через loginlink (письмом, не
  прямым доступом).
- `internal/loginlink`: регистрация сессии {account, playKey} login-сервером; потребление
  game-шлюзом при AuthLogin (однократное изъятие ключа — replay-защита); Kick — слепой
  push письма в ящик игрока/шлюза. In-process реализация; gRPC-транспорт — фаза 6+
  (приписка стадийности в ADR-0005 — правка решения в этой задаче).
- `cmd/l2go`: wire-up — конфиг (файл/флаги: порты, частота тика, каталог персиста,
  артефакт), загрузка статики артефактом (mmap; embed — build-тег, уже готов), запуск
  login + game + региона + метронома; graceful-shutdown (сигналы: стоп логинов,
  финальный персист, exit).

**Обоснование.** Логин после game-шлюза: стык определяется потребителем (game валидирует
playKey) — интерфейс loginlink рождается в P3.5, здесь реализуется. Логин-сервер
протокольно закрыт фазой 1 (клиент и писатели готовы) — тонкий слайс.

**Критерии приёмки.**
- Интеграционный тест: полный `l2client`-флоу через оба слушателя (login → ServerList →
  PlayOk → game-AuthLogin по playKey) — оба клиента DoD-сценария P3.9 стартуют здесь.
- Неверный пароль → LoginFail; занятый аккаунт → повторный вход кикает первого (письмо
  получено, коннект закрыт) — тесты.
- playKey одноразовый: второй AuthLogin с тем же ключом — отказ (тест).
- `cmd/l2go` собирается и стартует на синтетическом артефакте (CI); конфиг частоты тика
  реально доходит до метронома (тест на нестандартном периоде).
- Ворота зелёные; login ← protocol/crypto, loginlink ← transport (матрица).

**Ревью-профиль:** S2 — инвариантщик, безопасник, прагматик; S8 — + тестировщик.

**Зависимости:** P3.5 (потребитель стыка), P3.4 (аккаунты).

**Ссылки:** ADR-0005 п.2 (топология; стадийность стыка — приписка), r2 §Фаза 3
(авторизация), r4 (флоу логина клиента/сервера).

### P3.7 Вход в мир и спавн NPC — internal/world, internal/replica — ⬜

**Спецификация.** Первая игровая функциональность в свёртке:

- Обработка EnterWorld-письма регионом: установка сущности из персист-снапшота, первичный
  join известности (все члены → вводы клиенту), исходящий слиток входа. Состав слитка —
  по фактуре канона (Mobius EnterWorld): UserInfo, пустой ItemList/SkillList, SystemMessage
  welcome и прочее необходимое клиенту для рендера — перечень фиксируется в S0–S4 по
  референсу (доменщик), golden-писатели protocol на каждый пакет слитка.
- NpcInfo/CharInfo/DeleteObject/CharMoveToLocation-писатели protocol (+ golden, сверка с
  каноном с атрибуцией); objectId клиента = EntityID транспорта (вечный ID — И1).
- Спавн NPC: из статики `data.Spawns()` — конфигурируемый срез (имя зоны/радиус вокруг
  стартовой точки; решение 6), точечные записи → сущности {NpcDef из data.Npc: name, level,
  collision…}, территориальные — точка в территории (RNG региона D2); без AI, без
  респавнов (живут вечно). NpcInfo вводится известностью по радиусу (P3.3).
- Смерть/движение NPC отсутствуют — NPC статичны; их SoA-присутствие в фазе A — noop.
- Тест-двойник гео-мира: синтетический артефакт (маленькая flat-карта) для CI;
  реальный артефакт — ручные прогоны (КТ-2/КТ-3).

**Обоснование.** Спавн из готовой статики P2.2 без валидации new — она уже прошла при
сборке артефакта; региону остаётся инстанцирование. Срез по зоне — решение 6.

**Критерии приёмки.**
- Интеграционный тест: один клиент входит в мир на синтетическом артефакте → получает
  UserInfo и NpcInfo всех NPC в радиусе; NPC вне радиуса не присланы; join = set-equality
  (пересечение с P3.3-тестами).
- Второй клиент входит → у первого CharInfo второго (первое появление парной видимости).
- Логаут/LinkDead первого → у второго DeleteObject.
- Golden-тесты на всех новых писателях; поля сверены с каноном (расхождения — в реестр
  задачи, прецедент P1.1).
- Тик с популяцией NPC: доля join-стадии в шаге — в журнал (первоклассный датчик с фазы
  4 закладывается здесь); синтетический join-бенч P3.3 подтверждён на живом блобе.
- Ворота зелёные; статика — только артефакт (машинная проверка: исходники не читаются).

**Ревью-профиль:** S2 — инвариантщик, доменщик, перформансер, прагматик; S8 — +
тестировщик.

**Зависимости:** P3.3 (известность), P3.5 (шлюз, пакеты), P3.6 (полный флоу входа).

**Ссылки:** r2 §Фаза 3 (спавн); ADR-0004 (ось 6, тест-обязательства); r4/Mobius EnterWorld
(состав слитка); ADR-0001 (атрибуция портов).

### P3.8 Движение с гео-валидацией — internal/world — ⬜

**Спецификация.** Ядро r1 в свёртке региона:

- Письмо MoveToLocation{dest}: валидация фазой B — `geo.ValidLocation(pos, dest)` →
  кламп до достижимой точки (или отказ при нулевом пути), установка Entity.Dest; исходящий
  CharMoveToLocation наблюдателям (своя позиция+кламп — серверная авторитетность r1).
- Фаза A (dt): интерполяция по валидированному пути со скоростью сущности (база из таблицы
  character_templates/NPC-статики); достижении цели — стоп; SoA-проход по сортированному
  слайсу.
- Кинематика: speedBudget-токен-бакет на сущность (r1: пополнение maxSpeed·dt, CAP ~1–2 с
  хода); письмо ValidatePosition: сверка смещения против бюджета + гео (Z — NearestZ,
  непрерывность); дрейф > SLACK → флаг + коррекция TeleportToLocation на авторитетную
  позицию (перезапись бакета); легитимных скачков фаза не имеет (телепортов нет —
  pendingTeleport-флаг каркасно в модели, не исполняется до фаз 4+).
- Broadcast: движение наблюдателям — через dirty-поток блоба (позиция в пейлоаде записи),
  коалесинг в компоновке (последняя позиция в кадре).

**Обоснование.** Серверная авторитетность позиции — фундамент r1 (wall/fly/tp структурно
невозможны); ValidLocation уже написан и обложен тестами P2.4 — здесь только интеграция.
Кинематика обязательна с фазы 3: без неё скорость клиента не проверяется вовсе.

**Критерии приёмки.**
- Синтетическая геометрия: стена клампит (тест на L-стене/прямой стене), обрыв — refusal
  либо кламп, подъём > step — стоп; возвращённая точка достижима из from (property-тест,
  перенос P2.4).
- Speedhack: инъекция ValidatePosition со смещением > CAP+SLACK → флаг + коррекция
  (TeleportToLocation получен клиентом — тест l2client-ожидателем); джиттер внутри SLACK
  ложняков не даёт (тест траекторией).
- Движение двух сущностей: фаза A сходится в цель за expected-тики (dt-арифметика, D1);
  дроп тика удваивает dt — интеграционный тест со швом времени.
- Broadcast: наблюдатель получает CharMoveToPosition-поток с частотой ≤ тика и коалесингом
  (тест: одна позиция на кадр).
- Бенчмарк фазы A на популяции (реестр — тик региона): аллокации/тик в журнал.
- Ворота зелёные.

**Ревью-профиль:** S2 — инвариантщик, доменщик, перформансер, прагматик; S8 — +
тестировщик, доменщик.

**Зависимости:** P3.7 (сущности в мире, известность), P3.3 (dirty-поток).

**Ссылки:** r1 (симуляция вместо ловли пакета; токен-бакет; батчинг фаз A/B; DDA),
ADR-0002 (фазы A/B, dt), ADR-0004 (позиция — dirty-запись блоба).

### P3.9 Чат, логаут с персистом, полный DoD-сценарий — internal/world — ⬜

**Спецификация.** Замыкание сценария скелета:

- Письмо Say2: валидация у владельца (тип = general, длина/UTF-16 по доменам канона,
  фильтр пустых), рассылка CreatureSay наблюдателям в радиусе чата (порт канона, атрибуция)
  — компоновка в исходящие кадры региона (репликация, не chat-домен — решение 9);
  отправителю — эхо его же сообщения (как в живом L2).
- Логаут: письмо Logout → регион: остановка движения, финальный персист персонажа (P3.4),
  DeleteObject наблюдателям, деспавн сущности (порядок P3.1: dead-флаг → дрен → свап
  карты), контрольное письмо шлюзу «закрыть коннект»; LinkDead (обрыв TCP) — тот же путь,
  персист тоже (персонаж не теряется), таймаут-окно в тиках перед деспавном (short,
  конфиг; защищает от мигания Recon).
- Полный интеграционный DoD-сценарий (см. DoD фазы): 2 клиента × полный флоу до логаута и
  повторного входа; включается в CI как smoke (быстрый, ephemeral-порты, синтетический
  артефакт).

**Обоснование.** Чат через репликацию: general-say — радиальное событие известности,
не домен; PM/каналы — фаза 5+ (решение 9). Персист при LinkDead обязателен: обрыв
соединения — нормальный случай живого клиента.

**Критерии приёмки.**
- DoD-сценарий зелёный в CI (полный чек-лист сценария — asserts на каждый шаг).
- Чат: оба клиента в радиусе получили CreatureSay; вне радиуса — не получил (тест);
  переполнение длины/битый UTF-16 — дроп с метрикой, не паника (фазз-цель).
- Логаут: персонаж в файле (точка = последняя авторитетная позиция), повторный вход — в
  той же точке (assert); LinkDead — то же; таймаут-окно держит сущность (recon-тест).
- Ворота зелёные; -race на CI прогоняет сценарий.

**Ревью-профиль:** S2 — инвариантщик, доменщик, прагматик; S8 — + тестировщик.

**Зависимости:** P3.7, P3.8, P3.4, P3.5.

**Ссылки:** r2 §Фаза 3 (чат, логаут с персистом), ADR-0003 (смерть ≠ деспавн — здесь только
деспавн логаута; И1), r4 (Say2/CreatureSay фактура).

### P3.10 Реплей-харнесс и CI-ворота фазы — internal/world (тестовый харнесс) — ⬜

**Спецификация.** D6 как продукционная фича:

- Читатель лога порций (формат стабилен с P3.2) → прогон тех же писем/advisory-входов
  через тот же fold с инъекцией тиков → сравнение финального состояния и исходящих
  событий (пакеты игрокам не сравниваются — недетерминизм outbound по ADR-0004 «Цена»).
- Адаптивность D5: payloads по флагу; advisory-входы — всегда; ретенция лога (кольцевой
  буфер / файл с ротацией) — минимальная, инструментарий тайм-тревела — фаза 3+ по
  надобности (OQ-8 ADR-0003).
- CI-активация: replay-тест (запись живого прогона DoD-сценария → бит-в-бит прогон),
  интеграционный smoke P3.9, фазз-цели шлюза — в workflows (снятие заглушек — только эти;
  нагрузочные и bench-бюджеты остаются фазой 4).
- «Каждый производственный баг = воспроизводимый тест»: формат работы с находками
  описан в README плана (прикладывается к реестру задачи).

**Обоснование.** Харнесс обязан родиться в фазе 3 (ADR-0003 §16, D6): дальше — фаза 4
(бой, боты) — без реплея её баги неконвертируемы в тесты. Дешевле всего строится сейчас:
сворачивает уже дисциплинированные D1–D5 входы.

**Критерии приёмки.**
- Бит-в-бит: лог записанного DoD-сценария, прогнанный через fold, даёт равную свёртку
  (машинный тест в CI); мутация входного лога (перестановка двух писем) даёт расхождение —
  детектор не слеп (negative-тест).
- Реплей работает на обоих источниках тика (реальный и шов времени) — тест.
- CI-шаги активны и зелёные; список fuzz-целей пополнен шлюзом; заглушки фазы 4 не тронуты.
- Документация: как записать/прогнать реплей локально (README плана/журнал, не отдельный
  файл).

**Ревью-профиль:** S2 — инвариантщик, конкурентщик, прагматик; S8 — + тестировщик.

**Зависимости:** P3.2 (лог), P3.9 (полный сценарий как источник записи).

**Ссылки:** ADR-0003 (D5–D6, §13 OQ-8), ADR-0004 («Цена» — реплей не полисит outbound),
план/p0.md P0.2 (таблица активации ворот).

### P3.11 Приёмка живым клиентом владельца — ⬜

**Спецификация.** Доведение до критерия фазы r2: «реальный клиент Interlude владельца»:

- Подготовка: `make embedded DATA=… GEO=…` → `bin/l2go` (конфиг: мир, спавн-зона,
  каталог персиста); инструкция запуска — в журнале (без нового файла).
- Чек-лист приёмки (КТ-3, исполняет владелец): вход аккаунтом → создание персонажа →
  вход в мир (слиток входа, рендер мира, NPC в стартовой зоне) → второй клиент: взаимная
  видимость (видят друг друга и NPC) → бег: гео-кламп на стенах/рельефе, Z корректен,
  коррекций при честной игре нет → чат: сообщения видны обоим → логаут/повторный вход:
  позиция и персонаж сохранены.
- Отладка расхождений: l2tap-дамп живой сессии по желанию владельца (фикстуры — только
  производные байты по ADR-0001); каждый найденный баг — фикс + regression (реплей или
  интеграционный тест) — «баг = тест».

**Обоснование.** Отдельная задача: живой клиент вскрывает фактуру, невидимую l2client
(тайминги слитка, GG-поведение, допущения клиента) — бюджет на честную доводку, а не
«останется на потом».

**Критерии приёмки.**
- Чек-лист пройден владельцем полностью; результат и находки — в журнал.
- Все баги приёмки закрыты тестами (перечень тестов в реестре задачи).
- `make check` зелёный покомпентно (race — CI, оговорка в PR).

**Ревью-профиль:** облегчённый режим (самопроверка + ворота + один ревьюер + владелец).

**Зависимости:** P3.1–P3.10.

**Ссылки:** r2 §Фаза 3 (приёмка реальным клиентом), ADR-0001 (дампы не в репо).

## Порядок исполнения

```
P3.1 (транспорт) → P3.2 (регион+метроном+лог) → P3.3 (репликация/AoI)
→ P3.4 (персист) → P3.5 (game-провода+шлюз) → P3.6 (login+стык+cmd/l2go)
→ P3.7 (вход в мир+спавн) → P3.8 (движение+гео) → P3.9 (чат+логаут+DoD-сценарий)
→ P3.10 (реплей+CI) → P3.11 (приёмка живым клиентом)
```

- Критический путь: транспорт → регион → репликация → шлюз → вход в мир; персист (P3.4)
  контентно независим от P3.2–P3.3 и может исполняться параллельной сессией после P3.1
  (нужен к P3.5).
- P3.1–P3.3 — «ядро» (инварианты и детерминизм): полные конвейеры без послаблений; P3.11 —
  облегчённый режим; остальные — полный конвейер с профилями.
- Отладочная петля «зашёл l2client'ом» появляется в P3.5 и удешевляет все последующие
  задачи — поэтому провода раньше логина (логин-флоу клиента и так протестирован против
  сценарий-сервера фазы 1).
