# p0 — План фазы 0: Инфраструктура доверия

Исполнение [r2.md](../research/r2.md) §Фаза 0. Теория: [r0.md](../research/r0.md) (архитектура),
[r1.md](../research/r1.md) (geodata). Конвенции ведения планов: [README.md](README.md).

**Цель фазы:** к концу фазы любой агент (и человек) клонирует репозиторий, выполняет одну команду
и получает зелёный результат всех ворот; каждый архитектурный вопрос из r2 §«Открытые вопросы»,
блокирующий следующий заход, закрыт решённым ADR.

**Оценка:** 1–3 сессии агентной работы + человеческие решения (лицензия, аппрувы ADR).

## Выход фазы (Definition of Done)

- [ ] Репозиторий — git, корень = `la2/` (research/ и план/ живут внутри), `make check` зелёный
      на чистом клоне.
- [ ] CI на каждый PR: build + vet + staticcheck + `go test -race`; ворота доказанно краснеют на
      сломанном коммите (проверено один раз намеренным сбоем).
- [ ] ADR-процесс и шаблон зафиксированы; ADR-0001…0004 в статусе accepted.
- [ ] AGENTS.md содержит инварианты r0 и PR-чеклист.
- [ ] [прогресс.md](прогресс.md) ведётся по конвенциям README.
- [ ] Три блокирующих вопроса r2 закрыты ADR: модель тика (0002), FIFO хэндоффа (0003),
      направление knownlist (0004).
- [ ] Архитектурный рубеж (P0.9–P0.10): карта компонентов с компилируемыми Go-скелетами
      интерфейсов + таксономия сообщений и модель сущности.

## Задачи

Формат: каждая задача — готовый spec-first слайс для агента (текст раздела = спецификация).
Критерии приёмки фальсифицируемы. Статусы: ⬜ не начата, 🔄 в работе, 👀 на ревью человека,
✅ принято, ⛔ заблокирована.

### P0.1 Скелет репозитория — ✅ (2026-09-08)

**Спецификация.** `git init` в корне `la2/`. Go-модуль (имя — параметр; по умолчанию
`github.com/<owner>/la2`, фиксируется при исполнении). Минимальный layout — без пустых
заготовок под будущие фазы (они создадут сами фазы):

```
la2/
├── cmd/            # точки входа (сейчас — ни одной или тривиальная)
├── internal/       # весь код; наружу не экспортируется
├── docs/adr/       # каталог ADR
├── research/       # r0–r2 (уже есть)
├── план/           # планы и прогресс (уже есть)
├── Makefile        # цели: build, test, race, lint, check
├── AGENTS.md       # P0.4
├── go.mod, .gitignore, README.md
```

Makefile-цель `check` = `build + vet + staticcheck + test -race` — единственная команда,
которую запускают агент и CI. Один тривиальный smoke-тест, чтобы `-race` имел что гонять и
ворота были не пустыми. README: что за проект, как собрать, как проверить, ссылки на research/.

**Критерии приёмки.**
- `git status` чист после initial commit; в истории ≥1 коммит.
- На чистом клоне: `make check` → exit 0.
- `go vet ./...` и `staticcheck ./...` без замечаний.
- В дереве нет пустых директорий-заготовок и нет кода игровой логики (анти-скоуп, см. ниже).

**Статус (2026-09-08):** исполнено. Коммиты 0fab8f2 (скелет) и b4842ff (CI, P0.2) запушены в
`git@github.com:udisondev/l2go.git`, модуль `github.com/udisondev/l2go`. Ограничение локальной
машины: нет `make` и gcc (CGO_ENABLED=0) — ворота проверены покомпонентно (vet/build/test/
staticcheck@v0.8.1 зелёные; staticcheck пиннут по версии модуля: 2025.1 не читает export data
Go 1.27); полный `make check` с `-race` докажет первый прогон CI. Git-идентичность задана
локально в репо (udisondev / noreply) — поправь при желании.

**Зависимости:** нет. **Ссылки:** r2 §Фаза 0.

### P0.2 CI-конвейер — ✅ (2026-09-08; защита ветки main остаётся за владельцем)

**Спецификация.** GitHub Actions (допущение — при другом хостинге заменить, задача не меняется).
Workflow на PR и push в main: checkout → setup-go (версия пиннится по go.mod) → `make check`.
`concurrency: cancel-in-progress` для PR. Конвейер должен падать быстро и понятно.

Ворота активируются по фазам — в фазе 0 ставится каркас и честный минимум, остальное
помечено в workflow комментариями-заглушками (иначе карго-культ из всегда-зелёных шагов):

| Ворота | Статус в фазе 0 | Активация |
|---|---|---|
| build / vet / staticcheck / test -race | активно | фаза 0 |
| fuzz-смоук | заглушка | фаза 1 (протокол) |
| бюджеты бенчмарков (p99 тика) | заглушка | фаза 4 |
| нагрузочный смоук с ботами | заглушка | фаза 4 |

**Критерии приёмки.**
- Зелёный прогон на main после initial commit.
- Доказательство, что ворота краснеют: один тестовый коммит с заведомо сломанным тестом →
  красный PR → revert (фиксируется в прогрессе).
- (Человек) Включена защита ветки main: мерж только через PR.

**Статус (2026-09-08):** `.github/workflows/ci.yml` закоммичен и запушен (b4842ff): make check
на push/PR, setup-go по go-version-file, cancel-in-progress, заглушки fuzz/bench/load с датами
активации. Зелёный прогон: все коммиты main — success (проверено через API). Доказательство
красного: 46886ea (намеренно сломанный тест) → **failure**, 40c4694 (revert) → **success**.
Отклонение от плана: красный доказан пушем в main, а не PR — gh-токена у агента нет. Защита
ветки main (мерж только через PR) — за владельцем: до её включения правило «только PR»
advisory.

**Зависимости:** P0.1. **Ссылки:** r2 §Фаза 0, §Агентская система качества п.4.

### P0.4 AGENTS.md — инварианты и PR-чеклист — ✅ (2026-09-08)

**Спецификация.** AGENTS.md в корне — то, что читает каждая агентская сессия. Обязательные
разделы:

1. **Инварианты r0** (нарушение = реджект PR):
   - мутация сущности — только в горутине региона-владельца (single-writer);
   - кросс-региональное воздействие — сообщение владельцу (action-to-owner), не прямой доступ
     к чужой памяти;
   - внутри региона мьютексов нет; допустимая синхронизация: мейлбокс, atomic-свап снапшота,
     глобальная иммутабельная статика (geodata/датапак);
   - двойного владельца сущности не бывает ни на тик (хэндофф: migrating → flip →
     grace-forwarding);
   - передача ресурсов (предметы/деньги) — только reserve→commit/abort; fire-and-forget
     запрещён;
   - геодата и датапак — read-only после загрузки, off-heap/mmap.
2. **Структура пакетов** и правило зависимости (internal/, кому можно кого импортировать).
3. **Требования к тестам:** логика без теста не мержится; новые пакеты пакета protocol — с
   golden-тестами (фаза 1+).
4. **PR-чеклист:** ссылка на ADR (или «ADR не нужен, потому что …»), `make check` зелёный
   локально, слайс тонкий, вторая сторона-агент отревьюила против инвариантов.
5. **Как работать:** локальный запуск ворот, где ADR, где планы (план/), как фиксировать
   прогресс.

**Критерии приёмки.**
- Все шесть инвариантов из r0 воспроизведены дословно по смыслу; файл ссылается на research/.
- PR-чеклист применим к фиктивному PR из P0.2 (красный тест поймался бы чеклистом на шаге
  «make check локально»).

**Статус (2026-09-08):** [AGENTS.md](../AGENTS.md) создан: 7 инвариантов (6 из r0 + dt-дисциплина
и запрет прикладного пула из ADR-0002), секция «Референсы и лицензии» по ADR-0001 (закрывает
хвост P0.8), структура кода, требования к тестам, PR-чеклист, правила ревью и карта документов.
PR-чеклист применим: сломанный тест из red-proof поймался бы на шагах 2 и 4. Хвост P0.8 закрыт —
переводится в ✅.

**Зависимости:** P0.1 (формально), контентно — r0. **Ссылки:** r2 §Фаза 0, r0 §Ключевый инвариант.

### P0.5 ADR-0002 «Модель тика» — ✅ (2026-09-08, формальный акцепт владельца)

**Спецификация.** Закрыть противоречие r0 (§«Где живёт изоляция осады» vs §«Стоимость акторов»):
воркер-пул с барьером на кадр против goroutine-per-region. Анализ в ADR обязан ответить на
вопрос-разделитель: **что конкретно ломается, если снапшоты соседей разъезжаются на тик?**
(Персональная гипотеза для проверки: ломается мало что — тогда барьер не нужен, остаётся общий
pacing: диспетчер одновременно рассылает тик N активным регионам, никто никого не ждёт; канал
тика — cap-1 с коалесингом/generation, чтобы отставший регион не копил догоняющие тики.)
Зафиксировать: кто шлёт тик, семантику под отставанием, что с осадой/инстансами (отдельный бюджет —
уже решено в r0), критерий выбора при сомнении (измерение ботами в фазе 4 — записать в ADR как
проверку решения).

**Критерии приёмки.** ADR-0002 accepted (после ревью человека): выбран один вариант, перечислены
отвергнутые альтернативы, цена решения, и как решение будет проверено в фазе 4.

**Статус (2026-09-08):** защита проведена в дизайн-сессии — анализ альтернатив, фальсификация,
цены; полный разбор в [r3.md §1](../research/r3.md), текст решения в
[docs/adr/0002](../docs/adr/0002-model-tika.md). Формально акцептовано владельцем 2026-09-08.

**Зависимости:** P0.3. **Ссылки:** r2 §Открытые вопросы п.1, r0 §§ «Где живёт изоляция осады»,
«Стоимость акторов и сон регионов».

### P0.6 ADR-0003 «Порядок сообщений при хэндоффе» — 🔄 (v9.4, ревью-цикл идёт)

**Спецификация.** Закрыть дыру FIFO: directory flip + grace-forwarding допускает инверсию
порядка (m1 → RB по старой директории буферизуется, m2 → RC по новой применяется раньше). Для
урона терпимо, для предметов/трейда — дюп. Сравнить варианты: (а) seq-numbers per entity; (б)
drain-before-flip — флип только после ack RC и опустошения буфера RB; (в) epoch в директории.
Учесть: куда адресуется hit по сущности в состоянии `migrating`; совместимость с гистерезисом и
ghosting из r0.

**Критерии приёмки.** ADR-0003 accepted: выбран вариант, показано на сценарии (трейд посреди
хэндоффа), что инверсия исключена; цена решения.

**Зависимости:** P0.3. **Ссылки:** r2 §Открытые вопросы п.3, r0 §«Тонкое место — хэндофф во
время боя».

### P0.7 ADR-0004 «Направление knownlist/AoI» — ⬜

**Спецификация.** Уровень — направление, не детальный дизайн (детальный — фаза 4/6 по
измерениям). Определить: механика подписки AoI (кандидаты из r2: ячеечный pub/sub мельче региона,
distance-LOD, capped knownlist + справедливость), и что из этого определяет **форму снапшота**
(per-entity против per-region блоба — вопрос GC-давления из r2 связан с этим напрямую).
Зафиксировать критерий окончательного выбора: нагрузочный сценарий ботами в фазе 6.

**Критерии приёмки.** ADR-0004 accepted: направление выбрано, следствие для формата снапшотов
записано явно, детализация отложена с датчиком («решаем в фазе 6 по метрикам X, Y»).

**Зависимости:** P0.3. **Ссылки:** r2 §Открытые вопросы п.2, r0 §«Следующие шаги» (б).

**Пополнение по ADR-0003 v9 (2026-09-08):** knownlist/AoI обязан нести: дедупликацию по
entity-ID **и composite-ключу слуг** `(ownerID, slot)` — слуги не являются отдельными
маршрутизируемыми сущностями, публикуются в `servants[]` снапшота хозяина под стабильным
протокольным objectId; выбор источника при двойной публикации в окне хэндоффа (замороженный у
старого владельца vs живой у нового) — по max-epoch; трупы слуг и их AoI-видимость — в зоне
ответственности снапшота хозяина.

### P0.9 Карта компонентов и контрактные интерфейсы — ⬜

**Спецификация.** Архитектурный рубеж (добавлен по итогам обсуждения r2): средний уровень
проектирования — между картой системы (есть: r0/r1) и внутренностями компонентов (отложено в
свои фазы). Два артефакта: (1) документ-карта компонентов и правил зависимостей — gateway/net,
protocol, world/regions, non-spatial сервисы (пати, чат, клан, маркет), persistence,
data/geo-пайплайн, harness/headless-клиент, админ; кому можно импортировать кого; (2)
**компилируемые Go-скелеты интерфейсов** на межкомпонентных границах — контракт в коде, а не на
диаграмме: проверяется компилятором и не расходится с реальностью молча. Ключевая мотивация:
агенты принимают структурные микрорешения с первого коммита фазы 1 — без единой карты каждая
сессия решает их заново, связность становится лотереей.

**Ограничители против BDUF:** глубина — до потребностей walking skeleton и боя (фазы 1–4), не
до всего Интерлюда; всё, что хочется дорисовать глубже, — бэклог-кандидаты в ADR на месте;
время-бокс — дни.

**Критерии приёмки.** Документ карты закоммичен; `internal/` собирается со скелетами интерфейсов
(пустые реализации за фичей-флагом или `_ = var` заглушки); правила зависимостей выражены
проверяемо (раскладка пакетов + ревью-чеклист; опционально линтер импортов).

**Зависимости:** P0.1, P0.3. **Ссылки:** r2 §Фаза 0; обсуждение «почему нет фазы архитектуры»
(сессия 2026-09-08).

### P0.10 Таксономия сообщений и модель сущности — ⬜

**Спецификация.** Вторая половина архитектурного рубежа: типы сообщений по категориям r0/r3
(action-to-owner, публикация снапшота, сервисные/пати-события, хэндофф-протокол: Adopt/ack/
forwarding); модель сущности и владения (что входит в состояние сущности — включая боевое
состояние и состояние движения из r1: authPos, speedBudget, пейлоад хэндоффа = «всё состояние»);
черновик формата снапшота (per-entity vs per-region — завязано на ADR-0004). Оформляется как
Go-типы в скелетах P0.9 + пояснительный документ.

**Критерии приёмки.** Категории сообщений и поля сущности закоммичены как типы; каждый тип
сообщения отнесён к категории с обоснованием «почему eventual/почему 2PC»; черновик снапшота
согласован с ADR-0004 (или помечен блокировкой на него).

**Пополнение по ADR-0003 (2026-09-08, v9):** таксономия обязана нести: классы доставки
(fire-and-forget / reliable-until-delivered / transfer — полный реестр типов по классам),
**composite-адресацию слуг `(ownerID, slot)` — слуги не являются отдельными маршрутизируемыми
сущностями**, атрибуты конверта (в т.ч. «интент привязан к позиции/моменту»), домен-политику
(whitelist-enum advisory, default deny), поля конверта {to, fromID, returnTo, epoch, seq, class,
attrs} (fromID — для шардированных сервисов адресует шарду), политику гвардов. В карту
компонентов P0.9 включается **общий транспортный компонент** (конверт, outbox+seq,
директория-стаб с CAS-ассертом, redirect-стаб forward, draft/TTL-модель хэндоффа, инжектируемый
шов для детерминированных тестов — требование живёт с фазы 3).

**Зависимости:** P0.9; контентно — ADR-0002 (принят), ADR-0003/0004 (могут вестись параллельно).
**Ссылки:** r0 §«Кросс-региональное взаимодействие», r3 §3–4.

## Человеческие контрольные точки

| # | Что решает человек | Задача |
|---|---|---|
| 1 | Имя модуля, хостинг репо (допущение: GitHub), защита ветки main | P0.1–P0.2 |
| 2 | Лицензионная позиция и правила агентов с GPL-референсами | P0.8 |
| 3 | Аппрув ADR-0002/0003/0004 после агентного анализа | P0.5–P0.7 |

## Порядок исполнения

```
P0.1 → P0.2 → (P0.3, P0.4 — параллельно) → (P0.5–P0.8, P0.9 → P0.10 — параллельно)
```

P0.9 → P0.10 идут после P0.3 (нужен ADR-процесс) и до старта фазы 1 — карта компонентов должна
существовать раньше первого пакета протокола.

P0.5–P0.7 — идеальные первые «исследовательские» агентные задачи: чтение r0/r2, анализ, письмо.
Они же — обкатка ADR-процесса до появления кода.

## Анти-скоуп (в фазу 0 НЕ входит)

- Никакого кода игровой логики, протокола, геодаты — их фазы создадут свои пакеты сами.
- Никакого каркаса акторов/регионов — он ставится в фазе 3 в минимальной экспозиции.
- Fuzz/bench/load-ворота реально не активируются (каркас + заглушки) — активация по таблице
  в P0.2.
- Настройка «на вырост» (матрица ОС, кеши, релизные пайплайны) — когда появится нужда.
